# Tool and Configuration Reference

Use [README.md](../README.md) for quick start and client setup. Use [docs/examples.md](examples.md) for concrete request payloads.

Use this document when you need the exact input conventions, outputs, resource URIs, mapping rules, migration notes, operational pitfalls, or the full environment-variable matrix.

## Tool catalog

The catalog tools are a flat set of focused tools, listed ahead of the 8.x tools in `tools/list`. Each answers one kind of question and all of them share the conventions below. Each catalog entry lists the 8.x tools it replaces and where every 8.x input went, and [Migration from 8.x](#migration-from-8x) indexes those entries by 8.x tool.

The 8.x tools are deprecated aliases, to be removed in 10.0.0 at the earliest. They take their 8.x requests and return their 8.x replies unchanged, except that every reply, success or error, adds `meta.deprecated: { replacedBy, removeIn: "10.0.0" }` naming the catalog tools to use instead (see [Meta fields](#meta-fields)). `tools/list` shows each one after the catalog tools as a minimal entry: the description `Deprecated 8.x tool, removed in 10.0.0; use <catalog tools>.` (the five multiplexed tools add `(one per task)`), the input schema `{ "type": "object" }` instead of its 8.x input schema, its 8.x annotations, and `_meta.deprecated` with the same `replacedBy` and `removeIn`. The inputs an alias still accepts are its 8.x inputs: the "From 8.x" notes of the catalog entries name every one of them, and [Deprecated 8.x tools](#deprecated-8x-tools) describes many in more detail. Set `MCP_DEPRECATED_TOOLS=off` to leave the aliases out (see [Operational toggles](#operational-toggles)).

The server also sends AI agents a short primer as its MCP `instructions`, in both protocol eras (the `initialize` result and the `server/discover` result, see [MCP Protocol Support](#mcp-protocol-support)). It sums up the conventions below in a few sentences: the catalog tools are listed first and reject unknown argument keys, `target` says where to look, `mapping` names the namespace of the names in a call, and replies are `{ result, meta }` or `{ error, meta }`, with follow-up calls in `meta.nextActions` and warnings in `meta.warnings`. While the 8.x tools are served, its last sentence says that they are deprecated aliases, removed in 10.0.0, whose replies name the catalog tools to use in `meta.deprecated.replacedBy`; with `MCP_DEPRECATED_TOOLS=off` that sentence is left out. Each tool's description stands on its own, so a client that does not show `instructions` misses nothing the tools need.

### Shared conventions

**`target`** says where to look: a `kind` plus the fields of that kind. A field the kind does not take is rejected. Each tool lists the kinds it accepts, and a tool whose work has no use for an optional field of a kind leaves it out (its entry says which).

| `kind` | Required | Optional |
| --- | --- | --- |
| `artifact` | `artifactId` (reuse a resolved artifact without resolving it again; the reply reports the version it serves and its namespace, without a version approximation) | |
| `version` | `version` | `projectPath` (Loom cache discovery), `scope` |
| `jar` | `jarPath` | |
| `coordinate` | `coordinate` (`group:artifact:version`) | |
| `workspace` | `projectPath` | `scope` |
| `dependency` | `group`, `name`, and `dependencyVersion` or `projectPath` | |

`scope` is `vanilla`, `merged` or `loader`. For `dependency`, an explicit `dependencyVersion` wins; with only `projectPath`, the version is read from the project's Gradle files. A `dependency` target with neither fails with `ERR_INVALID_INPUT` on `target.dependencyVersion`. A `workspace`, `dependency` or `coordinate` target is resolved as the 8.x target of the same kind, so its version detection, default `scope`, coordinate rules, a dependency's `mappingApplied: "obfuscated"` with `dependency-mapping-unverified`, and the errors `ERR_WORKSPACE_VERSION_UNRESOLVED`, `ERR_DEPENDENCY_VERSION_UNRESOLVED` and `ERR_COORDINATE_PARSE_FAILED` are as described in [Workspace and dependency target shapes](#workspace-and-dependency-target-shapes), where the fields carry their 8.x names (`value` for `coordinate`, `version` for `dependencyVersion`).

**Resolution options** (`sourcePriority`, `gradleUserHome`, `preferProjectVersion`, `strictVersion`) are inputs of `artifact-resolve` only. To read with those options, call `artifact-resolve` first and pass `target: { kind: "artifact", artifactId }`. `allowDecompile` (default `true`) is also an input of `source-read` and `source-export`, governing their initial resolution and later source fallback. Options belong to each call; an `artifactId` does not retain them, so repeat `allowDecompile: false` on subsequent source reads and exports when needed. Existing indexed decompiled source remains readable. Legacy Mojang binary remapping on obfuscated releases retains its service behavior and may still run Java.

**`mapping`** names the namespace of the names a tool takes and returns: `obfuscated`, `mojang`, `intermediary` or `yarn`. `artifact-resolve`, `source-read`, `source-export` and `member-list` take it, and apply it when they resolve the `target`; omitted, the artifact's own namespace is used. `source-search` resolves its `target` the same way and takes `mapping` as the namespace of its query; its hits are in the artifact's namespace. The symbol tools (`symbol-check`, `symbol-map`, `class-mappings`, `symbol-trace`) require it: they look names up in a version's mapping data, and a name looked up in the wrong namespace is simply not found, so they never assume one (`analyze-symbol` assumed `obfuscated`). `class-diff` requires it for the same reason (`diff-class-signatures` assumed `obfuscated`). `symbol-map` also takes `toMapping`, the namespace to translate into. `mixin-validate` and `project-validate` take `mapping` for the mixins' names; omitted, it is read from the build scripts under `projectPath`, and a call that needs it and cannot read it is blocked instead of running as `obfuscated`. `access-validate` requires it for the names in the file, with `srg` as a further value for access transformers; it overrides a widener header's namespace. `mixin-verify-target` requires it for the target's names and translates them into the artifact's namespace when that differs (`autoRemap`, default `true`).

**`detail`** (`summary`, `standard`, `full`) exists only on tools whose reply can be shortened. Its default is advertised in the input schema. Every level keeps the primary result key and any `status`.

**Strict input.** Every control object, at the top level and inside `target`, rejects unknown and misplaced keys with `ERR_INVALID_INPUT`. `error.fieldErrors[]` holds `{ path, code, message, suggestions? }`; `path` names the key (`target.verison`), and `suggestions` lists declared keys within edit distance 3. Inside `target`, those are `kind` and the fields of the `kind` the request gives (every `target` field when `kind` is missing or one the tool does not take), and the 8.x locator `value` is answered with the field that kind takes instead: `artifactId`, `version`, `jarPath`, `coordinate`, `projectPath`, or `group` and `name` for `dependency`. Number inputs also accept numeric strings (`"20"`); nothing else is converted. The NBT tools' `typedJson` and `patch` operations are data documents: their own format validates them, so a member the format does not define is not an unknown key (see `nbt-encode` and `nbt-patch`).

**Replies** are `{ result, meta }` on success and `{ error, meta }` on failure, as JSON text and as `structuredContent`. Every reply a tool returns has `requestId`, `tool` and `durationMs` in `meta`; the replies the server itself puts in place of a tool's reply (a long-running call that timed out, a worker restart, a full request queue) carry `synthetic: true`, `syntheticSource: "supervisor"` and `meta.timeout`, `meta.restart` or `meta.queue` instead (see [Errors](#errors) and [Meta fields](#meta-fields)). `meta` may add:

- `warnings`: `[{ code, severity: "info" | "warning", message }]`, without duplicates. Routine notices are left out: the decompiled-source notice, the "Resolved Minecraft … from …" notice, the "Resolved source-backed artifact from Loom cache candidate: …" notice, the "Detected source jar; searching Java entries directly without decompilation." notice of `mod-search` and the "Result served from cache." notice of `mod-remap`, which `mod-remap` reports as `remap.fromCache` instead.
- `nextActions`: `[{ tool, params, reason?, template? }]`, naming catalog tools only. An entry without `template` validates against that tool's input schema and can be sent as is; a `template: true` entry has `<placeholder>` values to fill in. Error replies carry their recovery calls here, not in `error`.
- `pagination`: `{ hasMore, nextCursor? }`; pass `nextCursor` as `cursor`.
- `truncation`: `[{ field, limitedBy }]` when a limit cut a field of `result`.
- `stageBudgetExhausted`, `budgetMs`, `elapsedMs` on `ERR_STAGE_BUDGET_PRE_PARSE` errors, as for the 8.x tools.

**`status`** sits in a different place per tool: at the top of `result` (`result.status`), inside the tool's primary block (such as `result.diff.status`), or on each work item (`items[].status`), and each tool's Result line shows where. A tool whose Result line shows no `status` reports none; a reply without `error` is its answer.

**Work items.** `source-read`, `source-export` and `member-list` take `classes`, a list of 1–50 fully qualified class names, resolve the `target` once and read every class from that artifact. `symbol-check` and `symbol-map` take `symbols`, a list of 1–50 `{ kind, className, memberName?, descriptor? }` (`kind` `class` with `className` only; `field` and `method` with `className`, the owner, and `memberName`, the member's simple name: a `memberName` with `.`, `(`, `)`, `/` or `;` fails with `ERR_INVALID_INPUT`, while `<init>`, `<clinit>` and `$` are accepted; `descriptor` only with `method`, and on a `class` or `field` it fails with `ERR_INVALID_INPUT` naming `symbols.<i>.descriptor`), and report `items: [{ symbol, status, … }]` the same way. A symbol whose lookup answered carries the answer as its `status`, without `error`: `ok`, `not_found`, `ambiguous`, or `unavailable` when the version's mapping data cannot answer (it has no mapping between the two namespaces, or the version's metadata, which locates its mapping files, could not be fetched, which a `mapping-fetch-failed` warning says). A symbol whose lookup failed carries `error` and `status` `invalid` (a lookup the service rejects, such as a malformed descriptor), `not_found`, `unavailable` or `error`. `startLine`, `endLine` and `cursor` address a position inside one class, so they are accepted only with exactly one class (`ERR_INVALID_INPUT` naming the field otherwise). The reply has `items: [{ className, status, … }]` in request order and `counts: { total, ok, failed }`: `ok` counts the items with `status: "ok"` and `failed` the items that carry an `error`, so an item with another status and no `error` (a symbol answered `not_found`, `ambiguous` or `unavailable`, a `member-list` class that is `partial` or `unavailable`) is counted in neither. A class that cannot be read is an item with `status` `not_found`, `ambiguous`, `unavailable` or `error` and `error: { code, detail, retryClass, issueOrigin, hints?, didYouMean? }`. This holds for every failure while reading a class, including an internal error (`ERR_INTERNAL`) or a database failure (`ERR_DB_FAILURE`) in that class; the call itself fails only when the input is invalid or the `target` cannot be resolved. The recovery calls the server suggests for a failed class (for example `class-find` for a missing class, or one `artifact-resolve` call per nested jar for a class bundled in several) are in `meta.nextActions`. A `source-read` or `source-export` item read from another artifact than `result.artifact` (a class redirected into a nested jar, or served by a binary fallback) carries its own `artifactId`, and an item whose names are in another namespace than `result.artifact.mappingApplied` carries its own `mappingApplied`.

**`result.artifact`.** Every tool that resolves its `target` to an artifact returns `artifact: { artifactId, version?, mappingApplied?, requestedVersion?, versionApproximated? }`. The symbol tools read mapping data instead of a source artifact and return the Minecraft `version` they used, without `artifact`. Pass `artifactId` back as `target: { kind: "artifact", artifactId }` to skip resolution. When no source jar of the requested version exists and the server served another version's sources, the reply is never plain success: `versionApproximated: true`, `requestedVersion` is the version you asked for, `version` is the served version (absent when unknown), and `meta.warnings` has a `version-mismatch` warning with severity `warning`. `artifact-resolve` with `strictVersion: true` fails instead. A call with `target: { kind: "artifact", artifactId }` names no version, so its `artifact` carries the served `version` and no `requestedVersion`, `versionApproximated` or `version-mismatch` warning: several requested versions can share one artifact, and the call that names the version reports the approximation. A suggested call that would need a version the server cannot fill in is a `template: true` entry with `"<version>"`; take the version from `version-list`.

### `version-list`

List Minecraft versions from Mojang's version manifest, releases first and then snapshots, each newest first, with the latest release and snapshot and the versions cached locally.

- Inputs: `includeSnapshots` (default `false`), `limit` (1–200 per release type, default `20`).
- Result: `versions: [{ version, type: "release" | "snapshot", unobfuscated, cached }]`, `latest: { release?, snapshot? }`, `cached`, `totalAvailable`.
- Example: `{ "includeSnapshots": true, "limit": 5 }`
- Replaces (8.x): `list-versions`; `inspect-minecraft` `task: "versions"`.
- From 8.x `list-versions`: `includeSnapshots` → `includeSnapshots`; `limit` → `limit` (a value above 200 fails validation instead of being clamped with a warning). The reply lists releases and snapshots in one `versions` array instead of `releases` and `snapshots`.
- From 8.x `inspect-minecraft` `task: "versions"`: `includeSnapshots`, `limit` → same names, as for `list-versions`; the task reads no `subject`. `detail` and `include` → dropped: `version-list` returns every listed version at every call, where 8.x showed only the first five releases at its default `detail`.

### `artifact-resolve`

Resolve a target to a source artifact whose `artifactId` the other tools reuse. Read-only.

- Inputs: `target` (kinds `version`, `jar`, `coordinate`, `workspace`, `dependency`), `mapping`, `sourcePriority` (`loom-first` | `maven-first`), `allowDecompile` (default `true`), `gradleUserHome`, `preferProjectVersion` (use the Minecraft version of `target.projectPath`), `strictVersion` (fail instead of serving another version), `detail` (default `summary`).
- Result: `artifact` with `artifactId`, `version`, `mappingApplied`, `requestedMapping`, `artifactAlias`, `origin`, `isDecompiled`, `qualityFlags`, and `requestedVersion`/`versionApproximated` when approximated. `standard` adds `artifactContents`, `binaryJarPath`, `resolvedSourceJarPath`, `adjacentSourceCandidates`, `coordinate`, `repoUrl`; `full` adds `provenance` and `sampleEntries`.
- Errors: a `strictVersion: true` mismatch fails with `ERR_VERSION_NOT_FOUND`; `meta.nextActions` offers the same call with `strictVersion: false` (its `target`, `mapping` and other inputs unchanged).
- Example: `{ "target": { "kind": "version", "version": "1.21.10" } }`
- Replaces (8.x): `resolve-artifact`; `inspect-minecraft` `task: "artifact"`.
- From 8.x `resolve-artifact`:
  - `target: { kind: "version" | "jar" | "coordinate", value }` → `target: { kind: "version", version }`, `{ kind: "jar", jarPath }`, `{ kind: "coordinate", coordinate }`.
  - `target: { kind: "workspace", scope?, strict? }` with `projectPath` → `target: { kind: "workspace", projectPath, scope? }`. `strict` is dropped: it changed no resolution and was only echoed in one error's details.
  - `target: { kind: "dependency", group, name, version?, versionFromProject? }` → `target: { kind: "dependency", group, name, dependencyVersion }`, or `{ kind: "dependency", group, name, projectPath }` for `versionFromProject: true`.
  - `projectPath` → `target.projectPath` for `version`, `workspace` and `dependency` targets; `scope` → `target.scope` for `version` and `workspace` targets. For `jar` and `coordinate` targets both are dropped: those kinds take neither, and in 8.x they only shaped recovery hints.
  - `mapping`, `sourcePriority`, `allowDecompile`, `gradleUserHome`, `preferProjectVersion`, `strictVersion`, `detail` → same names.
  - `include` → dropped: there are no field groups; `detail: "standard"` returns the paths and the contents summary, `detail: "full"` also `provenance` and `sampleEntries`.
- From 8.x `inspect-minecraft` `task: "artifact"`: `subject: { kind: "version", version }` → `target: { kind: "version", version }`, and a workspace subject `{ kind: "workspace", projectPath }` → `target: { kind: "workspace", projectPath }`; the subject's `scope` and `projectPath` → `target.scope` and `target.projectPath` for the kinds that take them, and its `mapping`, `gradleUserHome`, `preferProjectVersion`, `strictVersion` → same names. `subject: { kind: "artifact", artifact: { type: "resolve-target", target } }` → `target` as for `resolve-artifact`; with `artifact: { type: "resolved-id", artifactId }` the artifact is already resolved, so pass `target: { kind: "artifact", artifactId }` to the tool that reads it. `detail` and `include` shaped the summary-first reply and are dropped; the `detail` of `artifact-resolve` picks its own fields.

### `artifact-index`

Rebuild the cached file and symbol index of an artifact. Writes the cache: `readOnlyHint: false`, `destructiveHint: false`, `idempotentHint: true`.

- Inputs: `target` (all kinds), `force` (default `false`; rebuild even when the index is current). A target that is not cached yet is resolved and indexed first.
- Result: `artifact` with the `result.artifact` fields plus `reindexed`, `reason`, `counts: { files, symbols, ftsRows }`, `indexedAt`.
- Example: `{ "target": { "kind": "artifact", "artifactId": "<artifactId>" }, "force": true }`
- Replaces (8.x): `index-artifact`.
- From 8.x `index-artifact`: `artifactId` → `target: { kind: "artifact", artifactId }`; `target` → `target` in the catalog shape (its `kind`, `value`, `scope`, `strict`, `group`, `name`, `version` and `versionFromProject` as for `resolve-artifact`; `{ kind: "artifact", artifactId }` is unchanged); `projectPath` → `target.projectPath` for the kinds that take it (dropped for `jar` and `coordinate` targets); `force` → `force`. The indexing `durationMs` of the 8.x result is left out; `meta.durationMs` times the call.

### `file-list`

List the file paths inside an artifact, optionally under a path prefix.

- Inputs: `target` (all kinds), `prefix`, `limit` (1–2000, default `200`), `cursor`.
- Result: `files` (paths), `artifact`. `meta.pagination` reports `hasMore` and `nextCursor`, and `meta.nextActions` holds the call for the next page.
- Example: `{ "target": { "kind": "artifact", "artifactId": "<artifactId>" }, "prefix": "net/minecraft/world/item/" }`
- Replaces (8.x): `list-artifact-files`; `inspect-minecraft` `task: "list-files"`.
- From 8.x `list-artifact-files`: `artifactId` → `target: { kind: "artifact", artifactId }`; `target` → `target` in the catalog shape (its `kind`, `value`, `scope`, `strict`, `group`, `name`, `version` and `versionFromProject` as for `resolve-artifact`; `{ kind: "artifact", artifactId }` is unchanged); `projectPath` → `target.projectPath` for the kinds that take it (dropped for `jar` and `coordinate` targets); `prefix`, `cursor` → same names (the cursor comes from `meta.pagination.nextCursor` instead of `result.nextCursor`); `limit` → `limit` (a value above 2000 fails validation instead of being clamped). `detail` and `include` are dropped: the reply has no field that a shorter level would leave out; the contents summary they controlled is part of `artifact-resolve` at `detail: "standard"`.
- From 8.x `inspect-minecraft` `task: "list-files"`: the subject → `target` as for `task: "artifact"` under `artifact-resolve`, or as for `source-read` for a class, file or search subject; `limit`, `cursor` → same names (`limit` at most 2000). `detail` and `include` → dropped: `file-list` returns the whole page, where 8.x showed only ten paths at its default `detail`. `prefix` is new to this task. In the reply, `meta.pagination.returnedCount` is dropped: `files` is the whole page.

### `file-read`

Read one file inside an artifact: a source file, or a resource or data file of the backing jar.

- Inputs: `target` (all kinds), `filePath`, `maxBytes`.
- Result: `content`, `filePath`, `contentBytes`, `deliveryMode?`, `contentOmittedReason?`, `artifact`. A `maxBytes` cut is reported as `meta.truncation: [{ field: "content", limitedBy: "maxBytes" }]`.
- Example: `{ "target": { "kind": "artifact", "artifactId": "<artifactId>" }, "filePath": "net/minecraft/world/item/Item.java" }`
- Replaces (8.x): `get-artifact-file`; `inspect-minecraft` `task: "file"`.
- From 8.x `get-artifact-file`: `artifactId` → `target: { kind: "artifact", artifactId }`; `target` → `target` in the catalog shape (its `kind`, `value`, `scope`, `strict`, `group`, `name`, `version` and `versionFromProject` as for `resolve-artifact`; `{ kind: "artifact", artifactId }` is unchanged); `projectPath` → `target.projectPath` for the kinds that take it (dropped for `jar` and `coordinate` targets); `filePath`, `maxBytes` → same names. In the reply, `truncated` becomes `meta.truncation`, `returnedNamespace` (always equal to `mappingApplied`) becomes `artifact.mappingApplied`, and `artifactContents` is not returned; `artifact-resolve` with `detail: "standard"` reports it. With an unknown `artifactId`, the call reports the unknown artifact before it checks `filePath`; 8.x checked the path first.
- From 8.x `inspect-minecraft` `task: "file"`: `subject.filePath` (or a workspace subject's `focus.filePath`) → `filePath`, and the subject's artifact and workspace fields → `target` as for `source-read`. `detail` and `include` → dropped: `file-read` returns `content` at every call, where 8.x left it out at its default `detail` unless `include` had `source`. `maxBytes` is new to this task.

### `class-find`

Find fully qualified class names by simple or qualified name in an artifact, including classes inside nested jars.

- Inputs: `target` (all kinds), `className` (simple such as `Blocks`, or fully qualified), `limit` (1–200, default `20`).
- Result: `status` (`ok` for one class, `ambiguous` when several classes match, even if `limit` returns only one, `not_found`), `classes: [{ className, filePath, line, symbolKind, nested?, enclosingClass? }]`, `artifact`. When more classes match than `limit` returns, `meta.truncation` holds `{ field: "classes", limitedBy: "limit" }`.
- Lookup: the same lookup as 8.x `find-class`: a qualified name must match the full enclosing-type chain of its source file, with `.` or `$` between nested types, and the nested `.class` inventories of a Jar-in-Jar shell are searched, skipping a nested jar that cannot be read or exceeds the nested-entry size cap (see [Essential Conventions](#essential-conventions)).
- Workspace fallback: for a `workspace` target whose sources omit `net.minecraft`, a vanilla class the index cannot find is looked up in the binary jar with the workspace's mapping; a hit returns `status: "ok"` with `classes: [{ className, binaryOnly: true }]` and a `binary-fallback` info warning.
- Example: `{ "target": { "kind": "version", "version": "1.21.10" }, "className": "Blocks" }`
- Replaces (8.x): `find-class`; the class lookup and binary fallback of `inspect-minecraft` `task: "class-overview"`.
- From 8.x `find-class`: `artifactId` → `target: { kind: "artifact", artifactId }`; `target` → `target` in the catalog shape (its `kind`, `value`, `scope`, `strict`, `group`, `name`, `version` and `versionFromProject` as for `resolve-artifact`; `{ kind: "artifact", artifactId }` is unchanged); `projectPath` → `target.projectPath` for the kinds that take it (dropped for `jar` and `coordinate` targets); `className` → `className`; `limit` → `limit` (a value above 200 fails validation instead of being clamped). `matches[].qualifiedName` becomes `classes[].className`, and `total` is reported through `status` and `meta.truncation`. `class-find` looks up one match beyond `limit` to tell a cut list from a complete one; because the candidate pool is slightly larger, a small `limit` can return a top-level class that 8.x `find-class` missed at the same limit. At the 200-match cap the lookup cannot look ahead, so a full page of 200 is reported in `meta.truncation` as possibly cut.
- From 8.x `inspect-minecraft` `task: "class-overview"`: `subject.className` (or a workspace subject's `focus.className`) → `className`, and the subject's artifact and workspace fields → `target` as for `source-read`. 8.x looked up at most 10 matches; `limit` (default `20`) sets the number now. A found class's `filePath` is in `classes[]`; its `totalLines` comes from `source-read` with `mode: "metadata"`. `detail` and `include` → dropped: `class-find` returns its matches at every call.

### `source-read`

Read the Java source of 1–50 classes from one artifact: a Minecraft version, a dependency, or a mod jar through a `jar` target. Read-only; `source-export` writes files.

- Inputs: `target` (all kinds), `classes`, `mapping` (namespace of the class names; default the artifact's served namespace, even when its original request named another), `allowDecompile` (default `true`; `false` declines source decompilation during resolution and binary or nested-JAR source fallback), `mode` (`metadata` (default): a member outline; `snippet`: a line window, 200 lines unless `startLine`, `endLine` or `maxLines` is set; `full`: the whole file), `startLine`, `endLine` (one class only), `maxLines`, `maxChars`, `withProvenance` (default `false`).
- Result: `items: [{ className, status, sourceText, totalLines, returnedRange?, outOfRange?, artifactId?, mappingApplied? }]`, `counts`, `artifact`. `returnedRange: { start, end }` is present in `snippet` and `full` mode. `outOfRange: true` marks a `startLine` past the end of the file. `withProvenance: true` adds `provenance`, `qualityFlags` and `artifactContents` to each item.
- Statuses: `ok`; `not_found` for a class missing from the artifact; `ambiguous` for a class found in several nested jars; `unavailable` when a mapping cannot be applied; `error` otherwise.
- Cuts: a `maxLines` or `maxChars` cut is reported as `meta.truncation: [{ field: "items[<i>].sourceText", limitedBy: "maxLines" | "maxChars" }]`, and so is the default 200-line `snippet` window. When the cut leaves whole lines to read, `meta.nextActions` holds a `source-read` call for that class with the next `startLine`, the namespace used for its class name, any explicit `allowDecompile`, and the same window (`maxLines`, including the default 200, `endLine` and `maxChars`). Applicable source and resolution recovery calls preserve `allowDecompile: false` too. A cut with no line to resume from, such as a `maxChars` cut of the `metadata` outline or one inside the first line, has no continuation; raise `maxChars` instead.
- A nested class name (`a.b.Outer$Inner`) returns the source file of its top-level class.
- Example: `{ "target": { "kind": "artifact", "artifactId": "<artifactId>" }, "classes": ["net.minecraft.world.item.Item"], "mode": "snippet" }`; a mod jar: `{ "target": { "kind": "jar", "jarPath": "/path/to/mod.jar" }, "classes": ["com.example.mod.ExampleMod"], "mode": "full" }`
- Replaces (8.x): `get-class-source` and `batch-class-source` (reading); `get-mod-class-source`; `decompile-mod-jar` with `className`; `inspect-minecraft` `task: "class-source"`; `analyze-mod` `task: "class-source"`.
- From 8.x `get-class-source`:
  - `className` → `classes: [className]`; `target` → `target` in the catalog shape (its `kind`, `value`, `scope`, `strict`, `group`, `name`, `version` and `versionFromProject` as for `resolve-artifact`; `{ kind: "artifact", artifactId }` is unchanged); `mapping`, `mode`, `startLine`, `endLine`, `maxLines`, `maxChars` → same names (`mode` keeps the default `metadata`).
  - `projectPath` → `target.projectPath` and `scope` → `target.scope` for the kinds that take them; dropped for the other kinds.

### `source-export`

### `source-search`

Search the indexed source of one artifact: declarations by name, text inside files, or file paths. Read-only.

- Inputs: `target` (all kinds), `query`, `intent`, `match`, `queryMode`, `packagePrefix` (`net.minecraft.world.item` or `net/minecraft/world/item`), `fileGlob` (matched against the whole path: `*` within a directory, `**` across directories, `?` one character); both are matched against the artifact's paths, so they are written in the artifact's namespace, not in `mapping`'s, `symbolKind` (`class` | `interface` | `enum` | `record` | `method` | `field`; only with `intent: "symbol"`, `ERR_INVALID_INPUT` naming `symbolKind` otherwise), `mapping`, `limit`, `cursor`, `detail` (default `standard`).
- `intent`: `symbol` (default) matches the simple names of indexed class, interface, enum, record, method and field declarations; `text` matches file contents; `path` matches file paths.
- `match`: `prefix` (default), `contains` and `regex` ignore case; `exact` matches case exactly. A `text` search treats `prefix` as `contains`. A `regex` query is at most 200 characters (`ERR_INVALID_INPUT` otherwise, as for an invalid expression).
- `queryMode` (`auto` (default) | `token` | `literal`) shapes `text` searches only: `auto` and `token` pick candidate files from the index by whole words (the index splits text at every character that is not a letter or digit, `.`, `_` and `$` included, and ignores case) and check each candidate for the query; `literal` checks every file for the query as a substring, so `Entity` also finds `LivingEntity`. With `match: "regex"`, `auto` scans every file and `token` fails with `ERR_INVALID_INPUT` naming `queryMode` (a token search runs no regular expression). With the index switched off (`MCP_ENABLE_INDEXED_SEARCH=false`), `auto` scans every file and `token` returns no hits.
- `limit`: hits per page, 1–200, default `20`; at most `100` with `match: "regex"` (`ERR_INVALID_INPUT` naming `limit` above it). A server started with a lower `MCP_MAX_SEARCH_HITS` returns at most that many per page; a higher setting does not raise the 200.
- `mapping` is the namespace the query is written in. The `target` is resolved with it, as `source-read` does, so with a `version`, `workspace` or `jar` target, `intermediary` or `yarn` fails with `ERR_MAPPING_NOT_APPLIED` before Minecraft 26.1 (26.1+ serves its runtime names with a warning); to search with such names, call `artifact-resolve` without `mapping` and pass `target: { kind: "artifact", artifactId }` with `mapping`. When the artifact's namespace differs (an `artifact` target named in another namespace), a `symbol` query that is a fully qualified class name is translated into the artifact's namespace, reported as `result.translatedQuery: { original, translated, fromNamespace, toNamespace }`, and searched by its simple name inside its package; in the artifact's own namespace a fully qualified name is searched the same way without translation, and nothing else is reported (on a Minecraft 26.1+ runtime, stored as `obfuscated` and reported as `mojang`, `mapping: "mojang"` is the artifact's own namespace). In another namespace, a simple name, a `text` or `path` query, and a name that cannot be translated are searched as given, with a warning that says why. Without `mapping`, the query is searched as given, so a fully qualified `symbol` query matches no declaration (declarations are indexed by simple name). Hits are always in the artifact's namespace, `result.artifact.mappingApplied`.
- Result: `status`, `hits: [{ filePath, matchedIn: "symbol" | "content" | "path", symbol?: { symbolKind, symbolName, qualifiedName?, line }, line?, context?, enclosingSymbol?: { symbolKind, symbolName, startLine, endLine }, score?, reasonCodes? }]` (best match first), `translatedQuery?`, `artifact`, and `artifactContents` at `full`. Content hits carry `line`, the 1-based line of the first match in the file, and `context`, that line with the line before and after it; symbol hits carry their line in `symbol.line`; path hits carry neither. Content hits also carry `enclosingSymbol`, the innermost declaration whose line range contains `line`: `startLine` is the declaration's own line, the line a `symbol` search reports for it, so annotation lines above it are outside the range; `endLine` is the line of the brace that closes its body, or of the `;` that ends a field or a method without a body. A constructor appears as `symbolKind: "method"` named after its class. Lambdas, anonymous classes, enum constants, initializer blocks and compact record constructors are not declarations here, so a match inside one names the member or type that holds it. `enclosingSymbol` is absent when no declaration contains the line, such as a match in the package line, an import or the file's header comment. Pass `startLine` and `endLine` to `source-read` with `mode: "snippet"` to read that declaration.
- `detail`: `summary` leaves out `context`; `standard` keeps it; `full` adds each hit's `score` and `reasonCodes`, and `result.artifactContents`. Every level keeps `status`, `hits` and `translatedQuery`.
- Statuses: `ok` when hits were found; `not_found` when none were; `unavailable` when no hit was found by a search that could not have found the class: the artifact is a Jar-in-Jar shell, whose own index holds none of the classes it bundles, or a `symbol` search in another namespace than the artifact's could not translate its query from `mapping` (the artifact has no recorded version, the version has no mapping data, the mappings do not hold the name or hold several, the lookup failed, or the query is not a fully qualified class name), so the name may exist under its translated name; `partial` when the search was cut short, with or without hits: the indexed search read only its window of index candidates while more matched (`meta.truncation: [{ field: "hits", limitedBy: "candidateWindow" }]`; a `symbol` search other than `regex` reads five times `MCP_MAX_SEARCH_HITS` matching symbols, within 500 to 5,000 (1,000 by default), in name order; the cut is reported on the last page of the window, the one without `nextCursor`), or a scan stopped at `MCP_SEARCH_SCAN_MAX_BYTES` (`limitedBy: "scanBudget"`). `partial` takes precedence; the search's own warning stays in `meta.warnings` and says how to narrow it.
- Paging: `meta.pagination: { hasMore, nextCursor? }`. While `hasMore` is true, `meta.nextActions` holds the same search with `cursor`, on `target: { kind: "artifact", artifactId }`. A cursor of another search is ignored with a `cursor-ignored` warning, and the hits start from the first page.
- Follow-up: a reply offers one next action at most. Without a next page, a `text` search with `queryMode: "auto"` and a `match` other than `regex` that found no hit for a query containing `.`, `_` or `$` offers the same search with `queryMode: "literal"`, unless the server runs with `MCP_ENABLE_INDEXED_SEARCH=false` (then, as with `regex`, `auto` already scans every file): the index splits text at those characters, so `Stack.getCount` misses `itemStack.getCount()` there, while a literal scan finds it. A search whose `packagePrefix` or `fileGlob` matches no indexed path gets no such offer, since a literal scan skips the same files.
- Scope that matches nothing: when `packagePrefix` or `fileGlob` matches no indexed file path, no file is searched, for every `intent`, `match` and `queryMode`: the reply is `not_found` (or `unavailable` in the cases under Statuses), and except for a Jar-in-Jar shell, whose own warning says why its index is empty, `meta.warnings` has a `resource_not_indexed` warning (severity `info`) that names the filter. Only Java source is indexed, so a resource glob such as `data/minecraft/recipe/*.json` never matches; read such a file by its exact path with `file-read`. `*` and `?` do not match `/`, so `*ServerChunkCache*` matches only a file at the top of the index, while `**/*ServerChunkCache*` matches it in any directory.
- Workspace: for a `workspace` target whose sources omit `net.minecraft`, a query that looks like a class name (letters, digits, `_`, `$` and dots, with a last segment that starts with an upper-case letter, `_` or `$`, or is `class_<n>`) and found no hit in `net.minecraft` or `com.mojang` carries a `source-coverage-partial` warning, with or without hits in other packages; `class-find` confirms a Minecraft class in the binary jar.
- A Jar-in-Jar shell indexes none of its bundled classes, so a search finds only the shell's own classes, and one without hits is `unavailable`; the warning points to `class-find`, `source-read` and `member-list`.
- Example: `{ "target": { "kind": "artifact", "artifactId": "<artifactId>" }, "query": "BlockPos" }`; a text search: `{ "target": { "kind": "version", "version": "1.21.10" }, "query": "registerBlocks", "intent": "text", "packagePrefix": "net.minecraft.world.level.block" }`

### `symbol-check`

Check whether 1–50 classes, fields or methods exist in a Minecraft version's mappings. Read-only.

- Inputs: `target` (kinds `version` with `version` only, and `workspace` with `projectPath` only; a workspace's Minecraft version is read from `minecraft_version`, `mc_version` or `minecraftVersion` in its `gradle.properties`), `mapping` (required; the namespace the names are written in), `symbols`, `nameMode` (`auto` (default): a dotless class name such as `dhl` or `Item` is looked up as given, in whichever namespace `mapping` names; `fqcn`: classes must be fully qualified, and a dotless one fails with `ERR_INVALID_INPUT` naming `symbols.<i>.className`), `signatureMode` (omitted: a method with a `descriptor` is looked up as `exact` and every other symbol as `name-only`; `name-only`: a method matches by owner and name, and any `descriptor` is ignored; `exact`: a method also matches by `descriptor`, which every method then needs, `ERR_INVALID_INPUT` naming `symbols.<i>.descriptor` otherwise), `maxCandidates` (1–200, default `5`).
- Result: `items: [{ symbol, status, match?, candidates?, candidateCount, ambiguityReasons?, unobfuscatedRuntime?, runtimeValidated? }]`, `counts`, `version`, `mapping`. `match` is the symbol found, in the same `{ kind, className, memberName?, descriptor? }` form as `symbol`. `candidates: [{ kind, className, memberName?, descriptor?, matchKind, confidence }]` is left out when it is empty or only repeats an exact `match`; a cut at `maxCandidates` is reported as `meta.truncation: [{ field: "items[<i>].candidates", limitedBy: "maxCandidates" }]`. `runtimeValidated: true` marks a symbol checked against the runtime jar of an unobfuscated version.
- Statuses: `ok`; `not_found`; `ambiguous` when several symbols match; `unavailable` when the version's mappings cannot answer; `invalid` and `error` for a failed lookup (see Work items).
- Version metadata that could not be fetched: when the version's metadata, which locates its mapping files, cannot be downloaded (the version manifest is unreachable, a request is refused, times out or returns an error status), the lookups that need the data are `unavailable` and `meta.warnings` has a `mapping-fetch-failed` warning with severity `warning` that names the version and the cause; the call can be retried once the download works. A version that has no mapping files gets no such warning. `symbol-map`, `class-mappings` and `symbol-trace` add the same warning; `symbol-trace` gives it for a scanned version whose metadata cannot be fetched, and fails with `ERR_REPO_FETCH_FAILED` when the version manifest itself cannot be read, since it needs the manifest to choose the versions it scans.
- Errors: a workspace without a Minecraft version in `gradle.properties` fails the call with `ERR_WORKSPACE_VERSION_UNRESOLVED`.
- Example: `{ "target": { "kind": "version", "version": "1.21.10" }, "mapping": "mojang", "symbols": [{ "kind": "class", "className": "net.minecraft.world.item.Item" }, { "kind": "method", "className": "net.minecraft.world.item.Item", "memberName": "getName" }] }`
- Replaces (8.x): `check-symbol-exists`; `batch-symbol-exists`; `analyze-symbol` `task: "exists"`.
- From 8.x `check-symbol-exists`:
  - `version` → `target: { kind: "version", version }`.
  - `kind`, `name`, `owner`, `descriptor` → one `symbols` item: a class's `name` is `className`; a field's or method's `owner` is `className` and its `name` is `memberName`. A packed `Class.method` name is not taken.
  - `sourceMapping` → `mapping` (required, as before). `nameMode`, `signatureMode`, `maxCandidates` → same names and defaults, except that without `signatureMode` a method with a `descriptor` is looked up as `exact`: 8.x ignored the descriptor unless `signatureMode: "exact"` was passed (a `maxCandidates` above 200 fails validation instead of being clamped).
  - `sourcePriority`, `gradleUserHome` → dropped: the symbol tools read mappings from the sources the server is configured with (`MCP_MAPPING_SOURCE_PRIORITY`, default `loom-first`, and the Loom caches under `GRADLE_USER_HOME`).
  - `detail`, `include` → dropped: the reply is the short form; `match` and `candidateCount` are always returned, `provenance` and `mappingContext` are not.
- From 8.x `batch-symbol-exists`:
  - `target: { kind: "version", value }` → `target: { kind: "version", version }`; `target: { kind: "workspace" }` with `projectPath` → `target: { kind: "workspace", projectPath }`; `projectPath` with a `version` target → dropped: it only steered the resolution of the source artifact. The version of a workspace comes from its `gradle.properties` instead of resolving the workspace's source artifact, so `scope`, `strict` (of the workspace target), `allowDecompile`, `preferProjectVersion` and `strictVersion` are dropped: no artifact is resolved.
  - `mapping` → `mapping`, now the namespace of the `symbols` names and required; 8.x looked the names up in the namespace of the resolved artifact.
  - `entries[].kind`, `name`, `owner`, `descriptor` → `symbols` as for `check-symbol-exists`; `entries[].nameMode`, `signatureMode`, `maxCandidates` → the call-level `nameMode`, `signatureMode`, `maxCandidates`, one value for every symbol. An entry without `nameMode` required a fully qualified class name outside the `obfuscated` namespace; the catalog default is `auto`, so pass `nameMode: "fqcn"` to keep that rule.
  - `concurrency`, `failFast` → dropped: every symbol is looked up and reported in its own item. `sourcePriority`, `gradleUserHome`, `detail`, `include` → dropped as for `check-symbol-exists`.
  - `results[]` and `summary` become `items[]` and `counts`.
- From 8.x `analyze-symbol` `task: "exists"`: `subject` → one `symbols` item (`subject.kind: "symbol"` is not inferred: give `class`, `field` or `method`); `version` → `target: { kind: "version", version }`; `projectPath` without `version` → `target: { kind: "workspace", projectPath }`; `sourceMapping` → `mapping` (required; 8.x assumed `obfuscated`); `nameMode`, `maxCandidates` → same names; `signatureMode` → same name; omitted, a method with a `descriptor` is looked up as `exact` and any other symbol as `name-only` (8.x `analyze-symbol` defaulted to `exact`); `gradleUserHome`, `detail`, `include` → dropped as for `check-symbol-exists`.

### `symbol-map`

Map 1–50 class, field or method names from one namespace to another for a Minecraft version. Read-only. Heavy: the call runs behind the server's shared heavy-tool gate (one call at a time, two waiting; a further heavy call fails with `ERR_LIMIT_EXCEEDED`), which `find-mapping` and `resolve-method-mapping-exact` also used; `batch-mappings`, `resolve-workspace-symbol` and `analyze-symbol` (`map`, `exact-map`, `workspace`) did not.

- Inputs: `target` (kinds `version` with `version` and optional `projectPath` for Loom cache discovery, and `workspace` with `projectPath` only), `mapping` (required), `toMapping`, `symbols`, `exact` (default `false`), `nameMode`, `signatureMode`, `maxCandidates` (as for `symbol-check`), `detail` (default `summary`).
- `toMapping` is required with a `version` target (`ERR_INVALID_INPUT` naming `toMapping`). With a `workspace` target and no `toMapping`, with or without `exact`, each symbol is mapped to the names the project compiles against: the namespace its `build.gradle(.kts)` declares (`officialMojangMappings()` → `mojang`, Yarn → `yarn`). That lookup matches methods strictly by owner, name and descriptor, as `exact: true` does, so every method needs a `descriptor` and every class a fully qualified name (`ERR_INVALID_INPUT` naming the item field); `nameMode` and `signatureMode` do not apply.
- `exact: true` (with `toMapping`) maps methods strictly by owner, name and full descriptor, and reports `unavailable` when a class in the descriptor cannot be translated; every symbol must be a `method` with a `descriptor` (`ERR_INVALID_INPUT` naming `symbols.<i>.kind` or `symbols.<i>.descriptor`). Without it, `signatureMode: "exact"` matches the descriptor but accepts a partly translated one.
- Result: `items: [{ symbol, status, match?, candidates?, candidateCount, ambiguityReasons?, unobfuscatedRuntime?, runtimeValidated?, mappingContext, provenance? }]`, `counts`, `version`, `mapping`, `toMapping` (the namespace mapped into, also when it came from the workspace), and for the workspace compile names `workspace: { resolved, mappingApplied?, evidence? }`.
- `detail`: `summary` leaves out a candidate list that is empty or only repeats an exact `match`; `standard` returns every candidate list; `full` adds each item's `mappingContext` and `provenance` (which mapping file answered) and the workspace's `evidence`. Every level keeps `symbol`, `status` and an item's `error`.
- Statuses: as for `symbol-check`. A cut at `maxCandidates` is reported in `meta.truncation` as for `symbol-check`.
- Example: `{ "target": { "kind": "version", "version": "1.21.10" }, "mapping": "obfuscated", "toMapping": "mojang", "symbols": [{ "kind": "class", "className": "dhl" }] }`; exact: `{ "target": { "kind": "version", "version": "1.21.10" }, "mapping": "intermediary", "toMapping": "yarn", "exact": true, "symbols": [{ "kind": "method", "className": "net.minecraft.class_1937", "memberName": "method_8320", "descriptor": "(Lnet/minecraft/class_2338;)Lnet/minecraft/class_2680;" }] }`; workspace: `{ "target": { "kind": "workspace", "projectPath": "/path/to/mod" }, "mapping": "mojang", "symbols": [{ "kind": "class", "className": "net.minecraft.world.item.Item" }] }`
- Replaces (8.x): `find-mapping`; `resolve-method-mapping-exact`; `resolve-workspace-symbol`; `batch-mappings`; `analyze-symbol` `task: "map"`, `"exact-map"`, `"workspace"`.
- From 8.x `find-mapping`:
  - `version` → `target: { kind: "version", version }`; `kind`, `name`, `owner`, `descriptor` → one `symbols` item as for `symbol-check`; `sourceMapping` → `mapping`; `targetMapping` → `toMapping`; `nameMode`, `signatureMode`, `maxCandidates`, `detail` → same names and defaults, except that without `signatureMode` a method with a `descriptor` is looked up as `exact` (8.x ignored the descriptor unless `signatureMode: "exact"` was passed).
  - `disambiguation: { ownerHint, descriptorHint }` → dropped: the hints filtered the candidates by their owner and descriptor in the destination namespace, which the `symbols` fields (written in `mapping`) do not express. Narrow a method with `signatureMode: "exact"` and its `descriptor`, or with `exact: true`, or read every candidate with a larger `maxCandidates`.
  - `sourcePriority`, `gradleUserHome`, `include` → dropped as for `check-symbol-exists`.
- From 8.x `resolve-method-mapping-exact`: the same call with `exact: true`; `owner`, `name`, `descriptor` → one `symbols` item `{ kind: "method", className: owner, memberName: name, descriptor }`; `version`, `sourceMapping`, `targetMapping`, `maxCandidates`, `detail` → as for `find-mapping`; `sourcePriority`, `gradleUserHome`, `include` → dropped.
- From 8.x `resolve-workspace-symbol`: `projectPath` → `target: { kind: "workspace", projectPath }` without `toMapping`; `version` → dropped: the version comes from the project's `gradle.properties` (for a project that declares it elsewhere, use a `version` target with the compile namespace as `toMapping`, and `exact: true` for methods, which is what the workspace lookup does); `kind`, `name`, `owner`, `descriptor` → `symbols`; `sourceMapping` → `mapping`; `maxCandidates`, `detail` → same names; `sourcePriority`, `gradleUserHome`, `include` → dropped. `workspaceDetection` becomes `result.workspace` and `result.toMapping`.
- From 8.x `batch-mappings`: `version` → `target: { kind: "version", version }`; `projectPath` → `target.projectPath`; `entries[].kind`, `name`, `owner`, `descriptor` → `symbols`; `entries[].sourceMapping`, `targetMapping` → the call-level `mapping`, `toMapping`, one pair for every symbol (send one call per namespace pair); `entries[].signatureMode`, `maxCandidates` → the call-level `signatureMode`, `maxCandidates` (omitted, a method with a `descriptor` is now looked up as `exact`; 8.x ignored the descriptor unless `signatureMode: "exact"` was passed); `entries[].disambiguation` → dropped as for `find-mapping`; `concurrency`, `failFast` → dropped: every symbol is mapped and reported in its own item; `sourcePriority`, `gradleUserHome`, `include` → dropped; `detail` → `detail`. `results[]` and `summary` become `items[]` and `counts`. Entries had no `nameMode` and required a fully qualified class name outside the `obfuscated` namespace; the catalog default is `auto`, so pass `nameMode: "fqcn"` to keep that rule.
- From 8.x `analyze-symbol` `task: "map"`, `"exact-map"`, `"workspace"`: `subject` → one `symbols` item (as for `task: "exists"`); `version` → `target: { kind: "version", version }`; `projectPath` → `target: { kind: "workspace", projectPath }` for `workspace` (and in place of an omitted `version`); `sourceMapping` → `mapping` (required; 8.x assumed `obfuscated`); `targetMapping` → `toMapping` (required with a `version` target; 8.x assumed `mojang`); `exact-map` → `exact: true`; `nameMode`, `signatureMode` (omitted: `exact` for a method with a `descriptor`, `name-only` otherwise; 8.x `analyze-symbol` defaulted to `exact`), `maxCandidates` → same names; `gradleUserHome`, `include` → dropped; `detail` → `detail`.

### `class-mappings`

List one class and its fields and methods with their names in all four namespaces (`obfuscated`, `mojang`, `intermediary`, `yarn`) for a Minecraft version. Read-only. Heavy, like `symbol-map`: `get-class-api-matrix` queued the same way, `analyze-symbol` `task: "api-overview"` did not.

- Inputs: `version`, `className` (in the `mapping` namespace), `mapping` (required), `kinds` (any of `class`, `field`, `method`; default all), `limit` (rows per page, 1–5000; default all rows), `cursor`.
- Result: `rows: [{ kind, descriptor?, obfuscated?, mojang?, intermediary?, yarn?, completeness }]` (each namespace entry is `{ symbol, owner, name, descriptor? }`; `completeness` is `true` when all four namespaces have a name), `rowCount` (rows in the whole listing), `className`, `classIdentity` (the class name per namespace), `version`, `mapping`, `ambiguousRowCount?`, `unobfuscatedRuntime?` (on 26.1+ the other namespaces are empty by design).
- Paging: `meta.pagination: { hasMore, nextCursor? }`; a page cut by `limit` is reported as `meta.truncation: [{ field: "rows", limitedBy: "limit" }]` with the `class-mappings` call for the next page in `meta.nextActions`. A cursor that belongs to another listing is ignored with a `cursor-ignored` warning. A class the mappings do not know returns no rows.
- Example: `{ "version": "1.21.10", "className": "net.minecraft.world.item.Item", "mapping": "mojang", "kinds": ["method"], "limit": 50 }`
- Replaces (8.x): `get-class-api-matrix`; `analyze-symbol` `task: "api-overview"`.
- From 8.x `get-class-api-matrix`: `version`, `className`, `cursor` → same names; `classNameMapping` → `mapping`; `includeKinds` (a comma-separated string) → `kinds` (an array); `maxRows` → `limit` (a value above 5000 fails validation instead of being clamped with a warning); `sourcePriority`, `gradleUserHome` → dropped as for `check-symbol-exists`. In the reply, `nextCursor`, `rowsTruncated` and `cursorIgnored` become `meta.pagination`, `meta.truncation` and a `cursor-ignored` warning, and `classNameMapping` is `mapping`.
- From 8.x `analyze-symbol` `task: "api-overview"`: `subject.name` → `className`; `version` → `version` (a `projectPath` in place of `version` is dropped: pass the version); `classNameMapping`, or `sourceMapping` in its place → `mapping` (required; 8.x assumed `obfuscated`); `includeKinds` → `kinds`; `maxRows` → `limit`; `gradleUserHome` → dropped; `detail` and `include: ["matrix"]` → dropped: the rows are always returned. 8.x returned rows only with `include: ["matrix"]` or a `detail` above `summary`, and at most 25 unless `maxRows` was set; `class-mappings` returns every row unless `limit` is set.

### `symbol-trace`

Scan Minecraft versions for one method and report in which of them it exists. Read-only. Heavy, like `symbol-map`: `trace-symbol-lifecycle` queued the same way, `analyze-symbol` `task: "lifecycle"` did not.

- Inputs: `symbol` (a method: `{ kind: "method", className, memberName, descriptor? }`; another `kind` fails with `ERR_INVALID_INPUT` naming `symbol.kind`), `mapping` (required), `fromVersion` (default the oldest version in the manifest), `toVersion` (default the newest listed version: the latest release, or the latest snapshot with `includeSnapshots: true`), `maxVersions` (1–400, default `120`; the newest versions are kept), `includeSnapshots` (default `false`), `withTimeline` (default `false`).
- Result: `status`, `lifecycle: { symbol, mapping, range: { fromVersion, toVersion, scannedCount }, presence: { firstSeen?, lastSeen?, missingBetween, existsNow }, timeline? }`. With `withTimeline: true`, `timeline: [{ version, exists, reason? }]` has one entry per scanned version; `reason` is `class-not-found`, `descriptor-mismatch` or `unresolved` (the version could not be checked; `meta.warnings` says why).
- Statuses: `ok` when some scanned version has the method; `not_found` when the versions that could be checked lack it; `unavailable` when no scanned version could be checked.
- Cuts: a range longer than `maxVersions` is cut to its newest versions and reported as `meta.truncation: [{ field: "lifecycle.range", limitedBy: "maxVersions" }]`, with a warning naming the effective `fromVersion`.
- Errors: `symbol.memberName` is the method's simple name (see Work items); a `memberName` that reads as a class name, such as `Inner`, fails with `ERR_INVALID_INPUT` naming `symbol.memberName`, and `meta.nextActions` offers the `symbol-check` call for that class.
- Example: `{ "symbol": { "kind": "method", "className": "net.minecraft.server.MinecraftServer", "memberName": "tickServer" }, "mapping": "mojang", "fromVersion": "1.21.1", "toVersion": "1.21.10" }`
- Replaces (8.x): `trace-symbol-lifecycle`; `analyze-symbol` `task: "lifecycle"`.
- From 8.x `trace-symbol-lifecycle`: `symbol` (`"fully.qualified.Class.method"`) → `symbol: { kind: "method", className, memberName }`; `descriptor` → `symbol.descriptor`; `mapping` → `mapping` (required; 8.x assumed `obfuscated`); `fromVersion`, `toVersion`, `maxVersions`, `includeSnapshots` → same names (a `maxVersions` above 400 fails validation instead of being clamped); `includeTimeline` → `withTimeline`; `sourcePriority`, `gradleUserHome` → dropped as for `check-symbol-exists`. In the reply, `query` becomes `lifecycle.symbol` and `lifecycle.mapping`.
- From 8.x `analyze-symbol` `task: "lifecycle"`: `subject.owner` and `subject.name` → `symbol.className` and `symbol.memberName`; `subject.descriptor` → `symbol.descriptor`; `version` (the range end) → `toVersion`; `fromVersion`, `toVersion`, `maxVersions`, `includeSnapshots` → same names; `includeTimeline` → `withTimeline`; `sourceMapping` → `mapping` (required); `gradleUserHome`, `detail`, `include` → dropped: the presence and range are always returned.

### `version-compare`

Compare two Minecraft versions: the classes added and removed between their client jars, the entries added and removed in their generated registries, and with `withLibraries` the libraries their version manifests list. Read-only. Heavy, like `symbol-map`: `compare-versions` queued the same way, `compare-minecraft` did not.

- Inputs: `fromVersion`, `toVersion`, `category` (`classes` | `registry` | `all`, default `all`), `packageFilter` (a package prefix such as `net.minecraft.world.item`; classes only), `registry` (one registry, such as `block` or `minecraft:block`; a name without a namespace is read as `minecraft:`), `limit` (class names per added or removed list, 1–5000, default `500`), `withLibraries` (default `false`), `detail` (default `summary`). `registry` with `category: "classes"` and `packageFilter` with `category: "registry"` fail with `ERR_INVALID_INPUT` naming the key; `registry` does not change `category`, so with `all` the classes are compared too.
- Result: `comparison: { fromVersion, toVersion, status, classes?, registry?, libraries? }`, each block present when its category was compared.
  - `classes: { addedCount, removedCount, unchanged, mappingApplied, packageFilter?: { value, matchedFrom, matchedTo }, added?, removed? }`. `mappingApplied` is the namespace of the compared names: `mojang` when the jars carry real names or the official mappings load for both versions, `obfuscated` when they do not (`meta.warnings` then says that a deobfuscated `packageFilter` cannot match).
  - `registry: { name?, summary: { registriesChanged, totalAdded, totalRemoved }, newRegistries, removedRegistries, changed, added?, removed? }`. `changed` maps each registry with added or removed entries to `{ added, removed }` counts; `added` and `removed` map it to the entry names. With `registry`, every field covers that registry only and `name` is its full name.
  - `libraries: { addedCount, removedCount, versionChangedCount, added?, removed? }`, keyed by `group:artifact` as described under [compare-minecraft migration-overview: `libraries`](#compare-minecraft-migration-overview-libraries).
- `detail`: `summary` returns the counts, `mappingApplied`, the `packageFilter` matches, the registry `summary`, `newRegistries`, `removedRegistries` and `changed`, and the library counts, with no name lists. A summary reply offers one follow-up in `meta.nextActions`: the same call at the lowest level that adds a non-empty list, `detail: "standard"` when a class or library list would hold names, otherwise `detail: "full"` when registry entries were added or removed. `standard` adds the class lists (each cut at `limit`) and the library lists; `full` also adds the registry entry lists. Every level keeps `comparison` and its `status`.
- Cuts: a class list cut at `limit` is reported as `meta.truncation: [{ field: "comparison.classes.added" | "comparison.classes.removed", limitedBy: "limit" }]` at `standard` and `full`, with the service's warning naming how many names were shown; narrow with `packageFilter`.
- Statuses: `ok`; `partial` when, with `category: "all"`, the registry comparison failed (the `registry` block is left out and a `registry-unavailable` warning says why), or when the library lists could not be read within 5 seconds (the `libraries` block is left out and a `libraries-unavailable` warning reads `Could not compare libraries between <from> and <to>: <reason>` or `Library comparison between <from> and <to> timed out after 5000ms.`); `not_found` when `registry` names a registry that exists in neither version (a `registry-not-found` warning names it, and `meta.nextActions` offers `registry-read` with `{ version: toVersion }`, which lists the registry names, in place of any `version-compare` follow-up). `not_found` takes precedence over `partial`: it answers the registry the call named, and the `libraries-unavailable` warning still reports a library failure. A registry that exists and did not change is `ok` with zero counts. With `category: "registry"`, a failed registry comparison fails the call, as in 8.x.
- Example: `{ "fromVersion": "1.21.1", "toVersion": "1.21.10", "packageFilter": "net.minecraft.world.item" }`; one registry with its entries: `{ "fromVersion": "1.21.1", "toVersion": "1.21.10", "category": "registry", "registry": "block", "detail": "full" }`
- Replaces (8.x): `compare-versions`; `compare-minecraft` `task: "versions"`, `"registry-diff"`, `"migration-overview"`.
- From 8.x `compare-versions`: `fromVersion`, `toVersion`, `category`, `packageFilter` → same names; `maxClassResults` → `limit` (a value above 5000 fails validation instead of being clamped with a warning). 8.x returned every list; `version-compare` answers with counts at its default `detail: "summary"`, so pass `detail: "standard"` for the class names and `"full"` for the registry entries. In the reply, `classes.namespace` becomes `classes.mappingApplied` and `classes.packageFilter.namespace` is left out (it equals `mappingApplied`).
- From 8.x `compare-minecraft` `task: "versions"`: `subject: { kind: "version-pair", fromVersion, toVersion, packageFilter? }` → the top-level `fromVersion`, `toVersion`, `packageFilter`; the `fromVersion` and `toVersion` of a `class` or `registry` subject → the same names; `task` → dropped: `category` picks what is compared; `maxClassResults` → `limit`; `detail` → `detail` (default `summary` as before; at `summary` 8.x returned only `summary.{ status, headline, subject, counts }`, where `version-compare` returns the counts of each block; at `standard` and `full` it returned every class and registry name list); `include` → dropped: `classes` (the class lists at `summary`) is `detail: "standard"`, `registry` (the registry block at `summary`) needs nothing because the registry counts and `newRegistries`/`removedRegistries` come at every level, and the other groups changed nothing in this task; `limit` → dropped: 8.x accepted it but no task used it; `maxEntriesPerRegistry`, `includeFullDiff` → dropped: this task did not use them. `summary.status` (`changed` / `unchanged`), `summary.headline` and `summary.counts` are left out: the counts are in `comparison`. The `compare-minecraft` follow-up call in `meta.truncated` becomes the `version-compare` call in `meta.nextActions`.
- From 8.x `compare-minecraft` `task: "registry-diff"`: → `category: "registry"`; `subject.registry` → `registry`, which now narrows the counts and lists to that registry (8.x returned the counts of every registry); its both-sides entry fetch (`include: ["registry"]` or `detail: "full"`, with `maxEntriesPerRegistry`) → two `registry-read` calls, one per version, with `registry`, `withData: true` and `limit` from `maxEntriesPerRegistry`; `version-compare` with `detail: "full"` returns the entries added and removed. `subject.fromVersion`, `subject.toVersion` (of any subject kind) → `fromVersion`, `toVersion`; `detail` → `detail` (the counts at `summary`, the entries added and removed at `full`); `maxClassResults`, `limit`, `includeFullDiff` → dropped: this task did not use them. The `partial` status of a failed entry fetch and its `get-registry-data` follow-up calls do not exist: `version-compare` fetches no entry bodies.
- From 8.x `compare-minecraft` `task: "migration-overview"`: → `category: "all"` with `withLibraries: true`; `subject` → `fromVersion`, `toVersion` (`packageFilter` was ignored by this task; `version-compare` applies it when given); `maxClassResults` → `limit`; `detail`, `include` → `detail` as for `task: "versions"`; `limit`, `maxEntriesPerRegistry`, `includeFullDiff` → dropped: this task did not use them. `migration.libraries` becomes `comparison.libraries` (lists at `standard` and `full`, counts at every level). `migration.impact` is dropped: it is derived from the class and registry counts. Its `class-diff` and `inspect-minecraft` follow-up calls are dropped: a summary reply offers one follow-up (see `detail`), so parallel follow-ups do not overflow the heavy-tool queue; pass a listed class to `class-diff` yourself. The 5-second deadline on the library fetch stays: past it, the answer comes without `libraries`, with `status: "partial"` and the `timed out after 5000ms` warning, so an unreachable network does not hold the heavy-tool queue for the whole fetch timeout.
- From 8.x `compare-minecraft`, for every task: `task: "auto"` and an omitted `task` (the task was picked from `subject.kind`) → dropped: choose `version-compare` (with `category`) or `class-diff`. `subject` fields a task ignored → dropped, because that task ignored them: a `class` subject's `className`, `mapping`, `sourcePriority` and `gradleUserHome` under `versions`, `registry-diff` and `migration-overview`; a `registry` subject's `registry` under `versions`; a `version-pair` subject's `packageFilter` under `registry-diff`. `include` groups not mapped above → dropped: they changed nothing in that task.

### `class-diff`

Diff one class between two Minecraft versions: the constructors, methods and fields added, removed and modified. Read-only. Heavy, like `symbol-map`: `diff-class-signatures` queued the same way, `compare-minecraft` `task: "class-diff"` did not. It reads the version manifest (to check both versions and their order), the client jars and, for a namespace other than `obfuscated`, the mappings.

- Inputs: `className` (fully qualified, in the `mapping` namespace; a name without a package fails with `ERR_INVALID_INPUT` naming `className` unless `mapping` is `obfuscated`, the only namespace with classes in the default package), `fromVersion`, `toVersion` (`fromVersion` must not be newer), `mapping` (required; the namespace of `className` and of the member names returned; a name looked up in the wrong namespace reads as missing in both versions), `detail` (default `full`).
- Result: `diff: { className, fromVersion, toVersion, mappingApplied, classChange, status, summary, constructors?, methods?, fields? }`. `mappingApplied` is the namespace of the returned names: `mapping`, except that `obfuscated` reads `mojang` when both versions are 26.1+ (as `query.mapping` of `diff-class-signatures` did). `classChange` is `added`, `removed`, `present_in_both` or `absent_in_both`. `summary` counts `{ added, removed, modified }` for `constructors`, `methods`, `fields` and `total`. Each member delta is `{ added, removed, modified }`; added and removed members carry `ownerFqn`, `name`, `javaSignature`, `jvmDescriptor`, `accessFlags`, `isSynthetic`, and a modified member carries `key` and `changed` (`accessFlags`, `isSynthetic`, `javaSignature`, `jvmDescriptor`).
- `detail`: `summary` returns `classChange` and `summary`; `standard` adds `constructors`, `methods` and `fields`, with modified members as `{ key, changed }`; `full` (the default, because the before and after values are what a migration needs and one class's diff stays small) adds `from` and `to` to each modified member. Every level keeps `diff` and its `status`.
- Statuses: `ok`, also for `classChange` `added` and `removed`; `not_found` when neither version has the class (`classChange: "absent_in_both"`, with a warning naming the class), including a class that neither version's mapping data names; `unavailable` when the mapping data of a version without the class could not be loaded, for example because the mapping files could not be downloaded. The class name was then looked up as given, so the class may exist in that version under its mapped name, and `classChange` still reads `added`, `removed` or `absent_in_both`; a `Could not map class …` or `Mapping lookup failed for class …` warning names the class. To tell these apart, when the class name could not be mapped, `class-diff` looks it up again in the mapping data of each version without the class: a name that data does not hold is a real absence, and only data that could not be loaded, or a lookup that failed, makes the diff `unavailable`. A 26.1+ version is not looked up for a `mojang` name: its jar already uses Mojang names, so the class's absence there stands.
- Unmapped members: members listed in a `Could not remap …` warning keep their jar (obfuscated) names in the deltas, although `mappingApplied` names the requested namespace.
- Errors: a version missing from the manifest fails with `ERR_VERSION_NOT_FOUND` and `meta.nextActions` offers `version-list`; a `fromVersion` newer than `toVersion` fails with `ERR_INVALID_INPUT`.
- Example: `{ "className": "net.minecraft.world.item.Item", "fromVersion": "1.21.1", "toVersion": "1.21.10", "mapping": "mojang" }`
- Replaces (8.x): `diff-class-signatures`; `compare-minecraft` `task: "class-diff"`.
- From 8.x `diff-class-signatures`: `className`, `fromVersion`, `toVersion` → same names; `mapping` → `mapping`, now required (8.x defaulted to `obfuscated`, so a Mojang name came back as `absent_in_both` with only a warning); `includeFullDiff` → `detail`: `true` (the default) is `detail: "full"` (the default), `false` is `"standard"`; `sourcePriority`, `gradleUserHome` → dropped: `class-diff` reads mappings from the sources the server is configured with (`MCP_MAPPING_SOURCE_PRIORITY`, default `loom-first`, and the Loom caches under `GRADLE_USER_HOME`). In the reply, `query` and `range` become `diff.className`, `diff.fromVersion`, `diff.toVersion` and `diff.mappingApplied`.
- From 8.x `compare-minecraft` `task: "class-diff"`: `subject.className`, `subject.fromVersion`, `subject.toVersion`, `subject.mapping` → the top-level names (`mapping` required); `subject.sourcePriority`, `subject.gradleUserHome` → dropped as for `diff-class-signatures`; `includeFullDiff` → `detail` as for `diff-class-signatures`; `detail` → `detail`, default `full` instead of `summary` (at `summary` 8.x returned only `summary.{ status, headline, subject, counts }`, while `class-diff` returns `diff.classChange` and `diff.summary`; the class diff came only at `standard` and `full`); `include` → dropped: `["diff"]` changed nothing (the block was `classDiff`), and the other groups changed nothing in this task; `task`, `limit`, `maxClassResults`, `maxEntriesPerRegistry` → dropped: they did not change a class diff. `summary.status` (`changed` / `unchanged`) and `summary.headline` are left out: `diff.summary.total` holds the counts.

### `registry-read`

Read a Minecraft version's generated registries (`minecraft:block`, `minecraft:item`, …): their names and entry counts, and with `withData` their entries. Read-only. Heavy, like `get-registry-data`. The first read of a version downloads its server jar and runs the game's data generator (needs `java`); the result is cached under `MCP_CACHE_DIR`.

- Inputs: `version`, `registry` (one registry, such as `block` or `minecraft:block`; default all), `withData` (default `false`), `limit` (entries per registry with `withData`, an integer of at least 1; default all).
- Result: `registries: [{ name, entryCount, default?, entries? }]` (one element when `registry` is given), `version`. `entries` keeps the game's `{ "<id>": { "protocol_id": <n> } }` objects; `entries` and `default` (the registry's default entry, when it has one) come only with `withData: true`.
- Next actions: with `registry` and without `withData`, `meta.nextActions` holds the same call with `withData: true`.
- Cuts: a registry whose entries `limit` cut is reported as `meta.truncation: [{ field: "registries[<i>].entries", limitedBy: "limit" }]`; `entryCount` stays the full count.
- Errors: an unknown `registry` fails with `ERR_SOURCE_NOT_FOUND`; call without `registry` for the names.
- Example: `{ "version": "1.21.10" }`; one registry's entries: `{ "version": "1.21.10", "registry": "block", "withData": true, "limit": 50 }`
- Replaces (8.x): `get-registry-data`.
- From 8.x `get-registry-data`: `version`, `registry` → same names; `includeData` → `withData`, whose default is now `false` (8.x defaulted to `true` and returned every registry's entries); `maxEntriesPerRegistry` → `limit`. ### `mod-inspect`

Read a mod jar's metadata from its `fabric.mod.json`, `quilt.mod.json`, `META-INF/neoforge.mods.toml`, `META-INF/mods.toml` or `mcmod.info`, and its entries. Read-only; nothing is decompiled.

- Inputs: `jarPath` (the mod jar; Windows and `\\wsl$` / `\\wsl.localhost` spellings are converted as for every jar path), `withClasses` (default `false`).
- Result: `mod: { loader, jarKind, classCount, modId?, modName?, modVersion?, description?, entrypoints?, mixinConfigs?, accessWidener?, accessTransformers?, dependencies?, nestedJars?, classes? }`. `loader` is `fabric`, `quilt`, `forge`, `neoforge` or `unknown` (a `META-INF/mods.toml` with `modLoader="lowcodefml"`, which Forge and NeoForge share, is `forge` unless a NeoForge loader value or `META-INF/neoforge.mods.toml` says `neoforge`); `jarKind` is `binary`, `source` or `mixed`; `dependencies` are `{ modId, versionRange?, kind }` with `kind` `required`, `optional`, `recommends` or `conflicts`; `nestedJars` lists the bundled Jar-in-Jar entries. With `withClasses: true`, `classes` lists the path of every `.class` entry of the jar with `/` as `.` and without `.class` (`com/example/Foo$Bar.class` → `com.example.Foo$Bar`), inner classes included. For an ordinary class this is its binary class name, which `source-read` and `member-list` accept with `target: { kind: "jar", jarPath }`. Some entries are not class names those tools accept: `module-info` and `package-info` entries (`com.example.package-info`) and multi-release copies under `META-INF/versions/<n>/` (`META-INF.versions.17.com.example.Foo`; read the class by its plain name). `classCount` counts the same entries.
- Errors: a path that is not an existing `.jar` file fails with `ERR_INVALID_INPUT`; a file that is not a zip archive fails with `ERR_SOURCE_NOT_FOUND`.
- Example: `{ "jarPath": "/mods/example-1.0.0.jar", "withClasses": true }`
- Replaces (8.x): `analyze-mod-jar`; `decompile-mod-jar` without `className` (its class listing); `analyze-mod` `task: "summary"`, `"decompile"`.
- From 8.x `analyze-mod-jar`: `jarPath` → `jarPath`; `includeClasses` → `withClasses`. In the reply, `classes` lists each entry path with `/` as `.` and without `.class` instead of the entry path (`com/example/Foo.class` becomes `com.example.Foo`); every other field is unchanged.
- From 8.x `decompile-mod-jar` without `className`: `jarPath` → `jarPath`; `includeFiles` → `withClasses` (`includeFiles: true`, its default, is `withClasses: true`); `maxFiles` → dropped: the class names come from the jar's entry list without decompiling, so the whole list is returned. The class names differ from the decompiled `files`: `mod-inspect` lists every `.class` entry, inner classes included, while `files` listed one name per decompiled top-level class. `fileCount` becomes `classCount` (counted the same way as `classes`); `outputDir` (the decompile cache directory), `returnedFileCount`, `filesTruncated` and `filesOmitted` are dropped. A class's source is `source-read` with `target: { kind: "jar", jarPath }` (see `source-read`).
- From 8.x `analyze-mod` `task: "summary"`: `subject: { kind: "jar", jarPath }` → `jarPath`; `task` → dropped: the tool is the task; `detail` → `withClasses`: at `"standard"` and `"full"` 8.x returned the `metadata` block with the class list, which is `withClasses: true`; at its default `"summary"` it hid the `metadata` block, which `mod-inspect` always returns; `include` → dropped: no group showed the `metadata` block at `detail: "summary"`, so `["files"]` there returned no class list either; `query`, `searchType`, `limit`, `includeFiles`, `maxFiles`, `maxLines`, `maxChars`, `targetMapping`, `outputJar`, `executionMode` → dropped: this task did not use them. `summary.counts.classes` is `mod.classCount`; `summary.counts.dependencies` is the length of `mod.dependencies`.
- From 8.x `analyze-mod` `task: "decompile"`: `subject.jarPath` → `jarPath`; `includeFiles`, `maxFiles` → as for `decompile-mod-jar`; `task`, `detail`, `include` → dropped as for `task: "summary"`; the other inputs → dropped: this task did not use them.

### `mod-search`

Search the Java source of a mod jar with a regular expression. Read-only. A sources jar (only `.java` entries) is searched directly; any other jar is decompiled first, once, into the decompile cache under `MCP_CACHE_DIR` (needs `java`; the decompiler is downloaded on first use unless `MCP_VINEFLOWER_JAR_PATH` names it).

- Inputs: `jarPath`, `query` (1–200 characters after trimming; a regular expression, or literal text when it is not a valid one; case-insensitive), `searchType` (default `all`), `limit` (1–200 hits, default `50`).
- `searchType`: `class` matches simple class names; `method` and `field` match declaration lines (a line that starts with `public`, `private` or `protected` and declares a method or a field); `content` matches the other lines; `all` matches all of these.
- Result: `hits: [{ type, name, file, line?, context? }]`. `type` is `class`, `method`, `field` or `content`; `name` is the class name for `class` and `content` hits and the member name for `method` and `field` hits; `file` is the source path inside the jar; `line` and `context` (the matching line with its neighbors) come with every hit but `class`. No hits is a success with `hits: []`.
- Cuts: when the search stopped at `limit`, `meta.truncation` holds `[{ field: "hits", limitedBy: "limit" }]` (there may be no further hit). There is no cursor: narrow `query` or `searchType`, or raise `limit`.
- Errors: a path that is not an existing `.jar` file fails with `ERR_INVALID_INPUT`.
- Example: `{ "jarPath": "/mods/example-1.0.0.jar", "query": "onInitialize", "searchType": "method" }`
- Replaces (8.x): `search-mod-source`; `analyze-mod` `task: "search"`.
- From 8.x `search-mod-source`: `jarPath`, `query`, `searchType` → same names; `limit` → `limit` (a value above 200 fails validation instead of being clamped with a warning). In the reply, `totalHits` (it equaled the number of returned hits) and the echoed `query` and `searchType` are dropped, `truncated` becomes `meta.truncation`, and the "Detected source jar; …" notice is left out.
- From 8.x `analyze-mod` `task: "search"`: `subject.jarPath` → `jarPath`; `query`, `searchType` → same names; `limit` → `limit` (8.x accepted any positive value and lowered one above 200 with a warning; a value above 200 now fails validation); `task` → dropped: the tool is the task; `detail`, `include` → dropped: the hits are always returned (8.x hid the `hits` block at its default `detail: "summary"`); `includeFiles`, `maxFiles`, `maxLines`, `maxChars`, `targetMapping`, `outputJar`, `executionMode` → dropped: this task did not use them.

### `mod-remap`

Remap a Fabric or Quilt mod jar from intermediary names to Yarn or Mojang names. Writes a file (`readOnlyHint: false`, `destructiveHint: true`), but only with `apply: true`; without it, the call is a preview that writes nothing.

- Inputs: `jarPath`, `toMapping` (`yarn` | `mojang`), `outputJar` (default `<modId>-<modVersion>-<toMapping>.jar` in the directory of `jarPath`, with `mod` and `0` for a missing id or version), `version` (the Minecraft version whose mappings are used; default the version in the mod's `minecraft` dependency, such as `1.21.1` from `~1.21.1`), `force` (default `false`: rebuild even when the remap cache holds the result, and look up the newest Yarn build again), `apply` (default `false`). `jarPath` and `outputJar` take Windows and `\\wsl$` / `\\wsl.localhost` spellings as every jar path does.
- Result: `remap: { mode, … }`, with the fields of the preview or the apply below.
- Preview (no `apply`): reads the jar's metadata, not its class names, and returns `remap: { mode: "preview", jarPath, outputJar, outputExists, toMapping, loader, modId?, modVersion?, version? }`, with `jarPath` and `outputJar` as the paths the remap would use. Nothing is written and nothing is downloaded. `meta.nextActions` holds the same call with `apply: true` (its reason says when it replaces an existing `outputJar`). When the mod names no Minecraft version and `version` is not given, `version` is absent, a `version-unresolved` warning says that applying needs one, and the next action is a `template: true` entry with `"version": "<minecraft-version>"`. The preview does not detect which names the jar uses, so a refusal that depends on them (a Mojang-named jar with `toMapping: "yarn"`) comes on apply.
- Apply (`apply: true`): writes `outputJar`, replacing an existing file, and returns `remap: { mode: "apply", outputJar, version, fromMapping, toMapping, resolvedTargetNamespace, durationMs, fromCache? }`. `fromMapping` is the namespace detected in the jar (`intermediary` or `mojang`). A remap runs tiny-remapper with `java` and downloads the mappings it needs; a jar already in `toMapping` names is copied (with a warning saying so). A result in the remap cache is copied from there and marked `fromCache: true`; pass `force: true` to rebuild it instead.
- Refusals, in preview and apply alike: an `outputJar` that is the input jar fails with `ERR_INVALID_INPUT` on `outputJar`, so the input is never overwritten. The file itself is compared (same device and inode), so every spelling of it counts: a symbolic or hard link, a `..` path, a different letter case on a case-insensitive file system, and a default name equal to the input's; a path that does not exist yet is never the input. An `outputJar` that is an existing directory fails the same way; a jar whose loader is not Fabric or Quilt fails with `ERR_REMAP_FAILED`; a `jarPath` that does not end in `.jar` fails with `ERR_INVALID_INPUT` on `jarPath`, and a missing one with `ERR_JAR_NOT_FOUND`. Apply without a known version fails with `ERR_INVALID_INPUT` on `version`. On apply, a Mojang-named jar cannot be remapped to `yarn`: `ERR_REMAP_FAILED`, with a hint to use `toMapping: "mojang"`.
- Example: `{ "jarPath": "/mods/example-1.0.0.jar", "toMapping": "mojang" }`; then the `meta.nextActions` call with `"apply": true`.
- Replaces (8.x): `remap-mod-jar`; `analyze-mod` `task: "remap"`.
- From 8.x `remap-mod-jar`: `inputJar` → `jarPath`; `outputJar` → `outputJar`; `mcVersion` → `version`; `targetMapping` → `toMapping`; `forceRemap` → `force`. `remap-mod-jar` wrote at once; `mod-remap` writes only with `apply: true`. An `outputJar` that is the input jar is rejected (`remap-mod-jar` could write over the input jar). In the reply, `mcVersion` becomes `version` and `targetMapping` becomes `toMapping`, and the "Result served from cache." warning becomes `fromCache: true`.
- From 8.x `analyze-mod` `task: "remap"`: `subject.jarPath` → `jarPath`; `targetMapping` → `toMapping`; `outputJar` → `outputJar`; `executionMode` → `apply` (`"preview"`, the default, is `apply: false`; `"apply"` is `apply: true`); `task` → dropped: the tool is the task; `detail`, `include` → dropped: the preview and the result are always returned; `query`, `searchType`, `limit`, `includeFiles`, `maxFiles`, `maxLines`, `maxChars` → dropped: this task did not use them. `version` and `force` are new to this path (the task read the version from the metadata and used the remap cache). `analyze-mod` refused to apply onto an existing `outputJar`; `mod-remap` replaces it, and the preview's `outputExists` shows beforehand that it would. The preview also refuses a loader it cannot remap, which `analyze-mod` found out only on apply. The `metadata` and `operation` blocks become `remap`.

### `project-validate`

Find a Loom workspace's mixin configs, access wideners and (on request) access transformers, validate each file against Minecraft bytecode, and report every file's outcome. Read-only. Long-running, like `validate-project`: the server's deadline (120 s by default, `MCP_VALIDATE_PROJECT_TIMEOUT_MS`, queue time included) applies, and each call runs alone while later requests wait: up to two wait, and a further one fails with `ERR_LIMIT_EXCEEDED` (see `meta.queue`).

- Inputs: `projectPath` (the workspace root; Windows and `\\wsl$` / `\\wsl.localhost` spellings are converted), `version` (default: read from the project's `gradle.properties`, `minecraft_version`, `mc_version` or `minecraftVersion`, with an info warning naming the version), `mapping` (the namespace of the mixins' names, and of the wideners whose header says `named`; default: read from the project's build scripts, such as `officialMojangMappings()` or a Yarn or intermediary `mappings` line, with a `mapping-from-project` info warning), `discover` (one or more of `mixins`, `access-wideners`, `access-transformers`; default `["mixins", "access-wideners"]`), `scope` (`vanilla`, `merged` or `loader`; omitted, mixins are checked against the vanilla jar and wideners and transformers against the project's loader jar), `detail` (default `summary`). An explicit `version` or `mapping` always wins over the project's. Access wideners are validated in the namespace their header declares: `official` as `obfuscated`, `intermediary` as `intermediary`, and `named`, the project's development names, in the project's mapping, given or read from the build (`yarn` when there is neither), so a widener of a project with `officialMojangMappings()` is read as Mojang names. A header without a namespace is validated as `intermediary` with a warning, and an explicit `mapping` overrides the header of every widener. A transformer's namespace is inferred from the project's loader (Forge `srg`, NeoForge `mojang`).
- Result: `project: { status, counts, items, tasks, workspace? }`. `items: [{ path, kind, status, errors?, issues?, summary?, provenance? }]` names every discovered file in discovery order (mixin configs, then wideners, then transformers), with `kind` `mixin-config`, `access-widener` or `access-transformer`. `errors` lists what failed at every level: each mixin class's error-severity issues as `<class>: <message>`, for an invalid widener or transformer, its definite entry failures as `line <n>: <issue>` (an issue that already starts with its line is kept as it is) and then the lines the service rejected, as `Line <n>: …` (a missing or unsupported header, a malformed line), which say why when no entry failed — the same `errors` as `access-validate` gives the file; or the reason a file could not be validated. A widener's or transformer's other warnings, such as a mapping override or a class that could not be mapped, are in `meta.warnings` only. `counts: { total, ok, partial, invalid, error, blocked }` counts the items by status. `tasks` is the workspace task report (`workspace.detected`, `gradle.readable`, `loom.cache.found`, `minecraft.artifact.resolved`, `mixins.validated`, `accessWideners.validated`, `accessTransformers.validated`), each with `status` (`ok`, `skipped`, `missing`, `error`) and any `error` or `warnings`.
- `detail`: `summary` returns each file's `path`, `kind`, `status` and `errors`; `standard` adds each file's `issues` (a mixin config's issues, each with its `className`, explained and with their lookups offered as next actions; a widener's or transformer's failed entries, uncertain ones marked as below, and its rejected lines as `{ issue }`) and `workspace: { projectPath, mixinConfigs, accessWideners, accessTransformers }`; `full` adds each file's `summary` and `provenance` (the version, jar and namespaces used) and the task evidence (durations, files found, the artifact checked). Every level keeps `project`, its `status` and each item's `status`.
- Statuses: an item is `ok`, `partial` (a mixin config with a class whose check was incomplete or whose only errors are uncertain, such as a name that could not be mapped, or with a source that could not be validated; a widener or transformer checked against another version's runtime jar, `approximate: true`, which also adds a `version-mismatch` warning naming the file and why, or whose only failed entries are uncertain), `invalid` (a definite error, or a widener or transformer whose header or a line was rejected), `error` (the file could not be validated, for example an access widener in the `classTweaker` format or a runtime jar that could not be resolved) or `blocked`. The call is `invalid` when any item is, else `partial` when any item is `partial` or `error`, else `ok`. A workspace with nothing to validate is `ok` with no items and a warning saying that nothing was validated. A widener or transformer entry that is not found after its class name could not be mapped (the class is misspelled or absent from that version, or the mapping data could not be loaded) carries `confidence: "uncertain"` and the service's warning as `confidenceReason`, as in `access-validate`; a widener or transformer item gets the same status, marked entries and `errors` as an `access-validate` call on that file with the same version, namespace, `scope` and `projectPath`.
- Blocked: a version that is neither given nor read from `gradle.properties` blocks the call when any file was found; a mapping that is neither given nor read from the build blocks it only when mixin configs were found. Then the call validates nothing and returns `status: "blocked"`, each found file as a `blocked` item, a warning naming the missing input, and one `template: true` next action: the same call with `"version": "<minecraft-version>"` and/or `"mapping": "<mapping>"`. Wideners and transformers alone need no mapping; the Minecraft artifact check (`tasks["minecraft.artifact.resolved"]`) is then `skipped` rather than run in an assumed namespace.
- Next actions: at `summary`, when any item is not `ok`, exactly one: the same call with `detail: "standard"`. At `standard` and `full`, the lookups that check each mixin issue (`symbol-check`, `source-read`).
- Example: `{ "projectPath": "/path/to/project" }`
- Replaces (8.x): `validate-project` `task: "project-summary"`. The `access-widener` and `access-transformer` tasks of `validate-project` are taken over by `access-validate`, documented with it; the `mixin` task by `mixin-validate`.
- From 8.x `validate-project` `task: "project-summary"`: `subject.projectPath` → `projectPath` (now converted from Windows and WSL spellings); `subject.discover` → `discover` (at least one kind); `version` → `version`; `mapping` → `mapping`; omitted, it is read from the build as 8.x did for the mixins, but a build that declares none now blocks the call instead of validating the mixins as `obfuscated` names; the given or read mapping also applies to wideners whose header says `named`, which 8.x read as Yarn names unless `mapping` was given; `scope` → `scope`; `detail` → `detail` (same default); `task`, `subject.kind` → dropped: the tool is the task; `preferProjectVersion` → dropped: an omitted `version` is always read from the project, and an explicit one always wins (8.x `preferProjectVersion: true` let the project's version override an explicit one; `false` blocked a call without `version`); `preferProjectMapping` → dropped: an explicit `mapping` wins, an omitted one is read from the build; `atNamespace` → dropped: the transformer namespace is inferred from the project's loader, as 8.x did without it; `configPaths` → dropped: to validate chosen configs, use `mixin-validate` with `configPaths` and `projectPath`; `sourceRoots` → dropped: the mixin sources are found under the common single-module and `common`/`fabric`/`neoforge`/`forge`/`quilt` source roots; `subject.gradleUserHome`, `sourcePriority` → dropped: the server's configured sources are used (`GRADLE_USER_HOME`, `MCP_MAPPING_SOURCE_PRIORITY`), as on the symbol tools; `include` → dropped: `detail` decides what is returned; `minSeverity`, `hideUncertain`, `warningMode`, `warningCategoryFilter`, `treatInfoAsWarning`, `includeIssues`, `reportMode`, `explain` → dropped: the reply's shape is `detail`, and filtering it is the caller's. In the reply, `summary.status` becomes `project.status`; `summary.counts` and `project.summary` (counted per mixin class and per widener) become `project.counts` (counted per file), and each file now has its own item; `summary.headline`, `summary.subject` and `summary.notes` are dropped; `summary.nextActions` (a `validate-project` retry) becomes a `project-validate` template in `meta.nextActions`; `workspace` and `tasks` are kept (`workspace` from `standard`). A mixin config that could not be validated, and an access widener or transformer whose validation threw, were counted `invalid`; they are now `error` items, which make the call `partial`. A widener or transformer checked against another version's jar counted as valid; it is now `partial`. A widener or transformer whose only failed entries could not be checked because their class name could not be mapped counted as invalid; it is now `partial`, and an invalid one's `errors` no longer repeat its other warnings.

### `mixin-validate`

Validate Mixin classes against a Minecraft version's bytecode: their targets, `@Shadow`, `@Accessor`, `@Invoker` and injector members. Read-only. Long-running: the server's deadline (120 s by default, `MCP_VALIDATE_PROJECT_TIMEOUT_MS`, queue time included) applies, and each call runs alone while later requests wait: up to two wait, and a further one fails with `ERR_LIMIT_EXCEEDED` (see `meta.queue`; `validate-mixin` had neither).

- Inputs: exactly one of `source` (Java source text; leading and trailing whitespace is trimmed, as `validate-mixin` did, so issue lines count from the first non-blank line), `paths` (one or more mixin `.java` files), `configPaths` (one or more mixin config JSON files, such as `modid.mixins.json`), `discover: true` (every `*.mixins.json` under `projectPath`, skipping `.git`, `.gradle`, `build`, `out` and `node_modules`); none, or more than one, fails with `ERR_INVALID_INPUT` naming the fields. `projectPath` (the Loom project: the jar for `merged` and `loader` scope, the base of a config's source roots, and where an omitted `version` and `mapping` are read from; required with `discover: true`), `version`, `mapping` (the namespace of the mixin's names), `scope` (`vanilla` by default, `merged` or `loader`; the last two need `projectPath`), `detail` (default `summary`). Without `projectPath`, `version` and `mapping` are required. With it, an omitted `version` is read from `gradle.properties` and an omitted `mapping` from the build scripts, each with an info warning (`version-from-project`, `mapping-from-project`); an explicit value always wins. A config's mixin sources are looked up under the project's single-module and `common`/`fabric`/`neoforge`/`forge`/`quilt` source roots; without `projectPath` the roots are taken relative to the config file's directory. Paths take Windows and `\\wsl$` / `\\wsl.localhost` spellings.
- Result: `validation: { status, counts, items, provenance? }`. `items` has one entry per validated source in request order (a config yields one per listed mixin class): `{ source: { kind, label, path?, configPath? }, status, className, targets, issues, summary, quickSummary, confidenceScore?, targetOutcomes?, … }`, or `{ source, status: "error", error: { code, detail, retryClass, issueOrigin, hints? } }` for a source that could not be validated (a file that cannot be read, a stage budget exhausted). `issues` are `{ severity, kind, annotation, target, message, line?, confidence?, category?, resolutionPath?, issueOrigin?, … }`. `counts: { total, ok, partial, invalid, error, validationErrors, validationWarnings }` counts the items by status; `validationErrors` and `validationWarnings` are the service's totals of error- and warning-severity issues over all items. A source that cannot be read fails as `Could not read the mixin file "<path>" (resolved to "<path>"): <reason>`. `provenance` (the version, jar, requested and applied namespace and scope) is present when every source shares it.
- `detail`: `summary` returns each source's issues and summary; `standard` adds each issue's `explanation`, the resolution trace in each source's `provenance`, and the lookups that check each issue as next actions; `full` adds the service's full per-source detail (`resolvedMembers`, `toolHealth`, `confidenceBreakdown`, structured or aggregated warnings) and each source's `warnings`, and `issueSummary`, `incompleteReasons`, `toolHealth` and `confidenceScore` on `validation`. Every level keeps `validation`, its `status` and each item's `status`.
- Statuses: an item is `ok`, `partial` (the check was incomplete, or its only errors are uncertain: the service could not map a name, so the target may still exist; each such issue keeps `confidence: "uncertain"`), `invalid` (a definite error) or `error`. The call is `invalid` when any item is, else `partial` when any is `partial` or `error`, else `ok`; or `blocked`.
- Blocked: when `projectPath` is given and an omitted `version` or `mapping` cannot be read from it, nothing is validated: `status: "blocked"`, no items, a `version-unresolved` or `mapping-unresolved` warning, and one `template: true` next action, the same call with `"version": "<minecraft-version>"` and/or `"mapping": "<mapping>"`. The namespace is never assumed.
- Next actions: the suggestions the service makes for an issue at `standard` and `full` (a `symbol-check` of a missing class or field, a `source-read` outline of a class whose method is missing or whose metadata could not be loaded) are `meta.nextActions` and are removed from the issues. At `summary`, when any item is `invalid` or `partial`, one next action: the same call with `detail: "standard"`. A `source` that contains `<…>` (Java generics) is repeated in that follow-up as sent: a value the request carried is not taken for a placeholder.
- Errors: an unreadable or malformed config fails with `ERR_INVALID_INPUT`; `discover: true` under a directory with no `*.mixins.json` fails with `ERR_INVALID_INPUT`, with a hint to pass `configPaths` or point `projectPath` at the workspace root; an inline `source` that fails to validate fails the call with the service's code.
- Example: `{ "configPaths": ["/path/to/project/src/main/resources/example.mixins.json"], "projectPath": "/path/to/project" }`
- Replaces (8.x): `validate-mixin`; `validate-project` `task: "mixin"`.
- From 8.x `validate-mixin`: `input: { mode: "inline", source }` → `source`; `input: { mode: "path", path }` → `paths: [path]` (a file that cannot be read is now an `error` item rather than a failed call); `input: { mode: "paths", paths }` → `paths`; `input: { mode: "config", configPaths }` → `configPaths`; `input: { mode: "project", path }` → `discover: true` with `projectPath: path` (8.x could search one directory and resolve the jar through another `projectPath`; the search root is now `projectPath`); `version`, `mapping`, `scope`, `projectPath` → same names (`version` and `mapping` are now required without `projectPath`; with it, an omitted one is read from the project, and a `mapping` the build does not declare blocks the call; for an omitted `mapping`, 8.x assumed `obfuscated` without `projectPath`, and also with it when the build declared none); `preferProjectVersion` → dropped: omit `version` with `projectPath` to read it from the project, an explicit one wins; `preferProjectMapping` → dropped: omit `mapping` with `projectPath` to read it from the build, an explicit one wins; `sourceRoots` → dropped: the default roots cover single-module and `common`/`fabric`/`neoforge`/`forge`/`quilt` layouts; list other sources with `paths`; `sourcePriority`, `gradleUserHome` → dropped: the server's configured sources are used, as on the symbol tools; `reportMode`, `explain` → `detail` (`summary` is `reportMode: "summary-first"`, the 8.x default; `standard` is `"compact"` with `explain: true`; `full` is `"full"` with `explain: true`); `minSeverity`, `hideUncertain`, `warningMode`, `warningCategoryFilter`, `treatInfoAsWarning`, `includeIssues` → dropped: the reply's shape is `detail`, and filtering it is the caller's. In the reply, `results[].result.valid` and `validationStatus` become `items[].status`; `results[].error`, `errorCode` and `errorDetails` become `items[].error`; `summary` becomes `validation.counts`, counted by item status (`valid`, which counted every class without a definite error, and `processingErrors` become `ok`, `partial`, `invalid` and `error`), with `totalValidationErrors` and `totalValidationWarnings` as `validationErrors` and `validationWarnings`; `mode` is dropped; the warnings move to `meta.warnings` (and onto each item at `full`), with the automatic retry's notice worded without the 8.x input; in-result `suggestedCall`s become `meta.nextActions`.
- From 8.x `validate-project` `task: "mixin"`: `subject.input` → the input forms as for `validate-mixin`; `version`, `mapping`, `scope` → same names as for `validate-mixin`; `task`, `subject.kind` → dropped: the tool is the task; `detail`, `include` → `detail` (the issues come at every level; 8.x returned them from `standard` or with `include: ["issues"]`); `atNamespace`, `configPaths` → dropped: this task did not use them; the other inputs → as for `validate-mixin`. `summary.status` becomes `validation.status`, `summary.counts` and `project.summary` become `validation.counts`, and the `issues` block (the per-source results) becomes `validation.items`.

### `access-validate`

Check one access widener (Fabric) or access transformer (Forge, NeoForge) against a Minecraft version's bytecode, entry by entry. Read-only.

- Inputs: `format` (`access-widener` or `access-transformer`); exactly one of `content` (the file's text; leading and trailing whitespace is trimmed, as `validate-access-widener` and `validate-access-transformer` did, so lines count from the first non-blank line) and `path` (the file to read; Windows and `\\wsl$` / `\\wsl.localhost` spellings are converted); none or both fail with `ERR_INVALID_INPUT` naming the fields. `version` (required). `mapping` (required), the namespace of the file's names: `obfuscated`, `mojang`, `intermediary` or `yarn` for a widener, `obfuscated`, `mojang` or `srg` for a transformer; any other pairing fails with `ERR_INVALID_INPUT` naming `mapping`. It is required because a widener header can mislead: `named` reads as Yarn and a header without a namespace as `intermediary`, both wrong for a Mojang-mapped project. `mapping` always wins over the header, with a warning when they differ. `projectPath` and `scope` (`vanilla`, `merged` or `loader`) pick the jar: `scope` defaults to `loader` with `projectPath` and to `vanilla` without it. `vanilla` checks the vanilla client jar of `version`, also when `projectPath` is given; `merged` and `loader` check a runtime jar found in the workspace and the Gradle home (`GRADLE_USER_HOME`): a Loom runtime jar for a widener, a Forge or NeoForge one for a transformer. An `srg` transformer needs a Forge runtime jar: with neither `projectPath` nor `scope`, or with `scope: "vanilla"`, it fails with `ERR_INVALID_INPUT` ("An SRG access transformer needs scope "loader" so a Forge runtime jar can be resolved.").
- Result: `validation: { status, format, errors?, headerVersion?, namespace?, entries, summary, provenance?, approximate?, approximationReasons? }`. `entries` lists every parsed entry in file order with its `line`, its parsed fields (a widener's `kind`, `transitive`, `targetKind`, `target`, `owner?`, `name?`, `descriptor?`; a transformer's `owner`, `target`, `targetKind`, `name?`, `descriptor?`, `accessAction`, `finalAction?`) and `valid`; a failed entry adds `issue` and `suggestions?` (similar member names, or the descriptors that exist). Checked against a runtime jar, each entry also reports `resolvedInRuntime` and the runtime access, descriptor and signature, and `provenance` names the jar, version, scope and namespaces used. `summary: { total, valid, invalid }` counts the entries as the service does, an uncertain entry as invalid. `headerVersion` and `namespace` are the widener header's. `errors`, on an invalid file only, says why: each definitely failed entry as `line <n>: <issue>` (an issue that already starts with its line is kept as it is), then the lines the service rejected, as `Line <n>: …` (a missing or unsupported header, a malformed line), which are the only reason when no entry failed. Every other warning, such as a mapping override or a class that could not be mapped, stays in `meta.warnings` only.
- Uncertain entries: when the service cannot map an entry's class into the jar's namespace, it warns `Could not map class "<class>" from <namespace> to <namespace>.` or `Mapping lookup failed for class "<class>".` and looks the class up by its unmapped name. That happens when the mapping data could not be loaded (for example, the mapping files cannot be downloaded), and also when the data loaded but does not name the class: the class name is misspelled, or the class does not exist in that version. An entry that then is not found keeps `valid: false` and is marked `confidence: "uncertain"`, with that warning as `confidenceReason`: the class or member may still exist, so check the class name. Only the entries of the class the warning names are uncertain; a miss in a class that was mapped is a definite failure. A rule violation (`mutable` on a method, `extendable` on a field, `transitive-` under a v1 header) is never uncertain.
- Statuses: `invalid` when an entry definitely fails or the file itself is rejected (its header, a malformed line); else `partial` when its only failures are uncertain, or when it was checked against another version's runtime jar (`approximate: true`, with `approximationReasons`, and a `version-mismatch` warning with severity `warning` that carries the reasons); else `ok`.
- Errors: a `path` that cannot be read fails with `ERR_INVALID_INPUT` naming `path`; a widener in the `classTweaker` format fails with `ERR_INVALID_INPUT`; a runtime jar of another loader than the workspace's fails with `ERR_CONTEXT_UNRESOLVED`. When no runtime jar is found, the call fails with `ERR_CONTEXT_UNRESOLVED`, with a hint to run the Gradle tasks that generate the runtime jars before checking again; no next action is offered, since the same call fails the same way until they have run.
- Example: `{ "format": "access-widener", "path": "/path/to/project/src/main/resources/example.accesswidener", "version": "1.21.10", "mapping": "intermediary" }`
- Replaces (8.x): `validate-access-widener`; `validate-access-transformer`; `validate-project` `task: "access-widener"`, `"access-transformer"`.
- From 8.x `validate-access-widener`: `content` → `content` (or `path` to read the file); `version`, `projectPath`, `scope` → same names; `mapping` → `mapping`, now required (omitted, 8.x took the header's namespace, and `intermediary` without one); `preferProjectVersion` → dropped: `version` is required, and reading the version from a project is `project-validate`'s work; `sourcePriority`, `gradleUserHome` → dropped: the server's configured sources are used (`MCP_MAPPING_SOURCE_PRIORITY`, `GRADLE_USER_HOME`), as on the symbol tools. In the reply, `valid` becomes `validation.status` and the warnings move to `meta.warnings`; the other fields are unchanged. An invalid file gains `errors`; a failed entry whose class name could not be mapped gains `confidence: "uncertain"` and alone makes the file `partial` instead of invalid; an approximate result, which counted as valid, is `partial`.
- From 8.x `validate-access-transformer`: `content`, `version`, `projectPath`, `scope` → as for `validate-access-widener`; `atNamespace` → `mapping` (`srg`, `mojang` or `obfuscated`), now required: 8.x inferred it from the workspace's loader with `projectPath` (Forge `srg`, NeoForge `mojang`) and failed without one; `preferProjectVersion`, `sourcePriority`, `gradleUserHome` → dropped as for `validate-access-widener`. The reply changes as for `validate-access-widener`.
- From 8.x `validate-project` `task: "access-widener"` and `"access-transformer"`: `task` and `subject.kind` → `format`; `subject.input: { mode: "inline", content }` → `content`; `subject.input: { mode: "path", path }` → `path` (now converted from Windows and WSL spellings); `version`, `scope` → same names; `mapping` (widener task) and `atNamespace` (transformer task) → `mapping`, required (each task ignored the other one); `preferProjectVersion`, `sourcePriority` → dropped as for `validate-access-widener`; `detail`, `include` → dropped: every entry is returned (8.x returned the failed ones from `standard` or with `include: ["issues"]`); `preferProjectMapping`, `sourceRoots`, `configPaths`, `minSeverity`, `hideUncertain`, `explain`, `warningMode`, `warningCategoryFilter`, `treatInfoAsWarning`, `includeIssues`, `reportMode` → dropped: these tasks did not use them. `projectPath` is new to this path. These tasks ran under `validate-project`'s long-running deadline and alone; `access-validate` has neither. In the reply, `summary.status` becomes `validation.status`; `summary.counts` and `project.summary`, which counted the file, become `validation.summary`, which counts its entries; the `issues` block is the `validation.entries` with `valid: false`; `summary.headline` and `summary.subject` are dropped.

### `mixin-verify-target`

Check that the method or field a mixin targets exists in a jar's bytecode, and which of `@Shadow`, `@Accessor` and `@Invoker` fits it. Read-only.

- Inputs: `target` (kinds `version` with optional `projectPath` and `scope`, `jar`, `coordinate`, `workspace` and `dependency`; not `artifact`: the members are read from the binary jar of the artifact the tool resolves), `className` (fully qualified), `kind` (`method` or `field`), `memberName` (the member's simple name: one with `.`, `(`, `)`, `/` or `;` fails with `ERR_INVALID_INPUT`, while `<init>` and `<clinit>` are accepted), `descriptor` (optional JVM descriptor; without it every member with the name matches), `mixinMemberName` (optional, the name of your mixin member: for a private target, `get`/`set`/`is` names suggest `@Accessor` and `invoke`/`call` names `@Invoker`), `mapping` (required: the namespace of `className`, `memberName` and `descriptor`; it is also applied when the target is resolved, as `artifact-resolve` applies it), `autoRemap` (default `true`).
- `autoRemap`: when the resolved artifact's namespace (`result.artifact.mappingApplied`) differs from `mapping`, the class and member names are translated into it with the Minecraft version's mapping data, and a warning reports the translation. A method's descriptor is translated with it and picks one overload; a field is translated by name, and a descriptor that cannot be translated is dropped with a warning, the member then being matched by name. A class or member name that cannot be translated (including a method named without a descriptor that has several overloads in the mapping data) fails the call with `ERR_NAMESPACE_MISMATCH`, never a `not_found` verdict, and so does any namespace difference with `autoRemap: false`. When translation is needed and the artifact reports no version (any target but `version`), the call fails with `ERR_INVALID_INPUT`.
- Per target kind: a `version` or `workspace` target is a Minecraft jar, resolved with `mapping` applied: the server remaps the jar into it, and when it cannot, resolution fails with `ERR_MAPPING_NOT_APPLIED`; when the resolved artifact's namespace still differs from `mapping`, the names are translated as above. A `jar`, `coordinate` or `dependency` target backed by a sources jar takes `mapping` as the jar's own namespace without translating anything, so pass the names as the jar has them, with the namespace `artifact-resolve` reports for that target (`obfuscated` for a jar without a Minecraft version); a mod jar's own classes are checked that way. A `jar` target without a sources jar is decompiled for `obfuscated` (Java and the decompiler are needed) and fails with `ERR_MAPPING_NOT_APPLIED` for any other `mapping`; a `jar` target with a sources jar fails the same way for `intermediary` and `yarn`, since its Minecraft version is unknown, and a `coordinate` target, whose version is the library's own, fails with `ERR_MAPPING_UNAVAILABLE` for them.
- Result: `verdict: { status, className, kind, memberName, mapping, matches, candidates, advice? }` and `artifact` (see Shared conventions, version honesty included). `className`, `memberName` and `mapping` are the names looked up and their namespace, the artifact's: the translated names when `autoRemap` translated them. `matches: [{ name, descriptor, accessFlags, javaSignature? }]` are the members found; `candidates: [{ name, descriptor, reason }]` explain a miss: members with the name and another descriptor, or members with a similar name. `advice: { suggestedAnnotation, reasoning, exampleSnippet, candidates? }` comes with exactly one match: `@Shadow`, `@Accessor`, `@Invoker`, `@Inject-only` (a visible method needs no invoker), or `null` with both options in `candidates` for a private method without `mixinMemberName`.
- Statuses: `ok` (one match), `ambiguous` (several matches: overloads matched by name), `not_found` (none). An `ambiguous` reply has one `template: true` next action, the same call with `"descriptor": "<descriptor>"` to replace with one of `verdict.matches[].descriptor`; after a translation it names the translated `className` and `memberName` and the artifact's `mapping`, since the descriptors are in that namespace.
- Errors: a class the jar lacks fails with `ERR_CLASS_NOT_FOUND`, with a `class-find` next action for its simple name in the resolved artifact; an artifact without a binary jar fails with `ERR_CONTEXT_UNRESOLVED`; a target that cannot be resolved fails as it does for `artifact-resolve`.
- Example: `{ "target": { "kind": "version", "version": "1.21.10" }, "className": "net.minecraft.world.entity.Entity", "kind": "method", "memberName": "tick", "mapping": "mojang" }`
- Replaces (8.x): `verify-mixin-target`.
- From 8.x `verify-mixin-target`: `owner` → `className`; `member.kind` → `kind`; `member.name` → `memberName` (its simple name only); `member.descriptor` → `descriptor` (a blank one now fails instead of being ignored); `mixinMemberName` → same name; `mapping` → `mapping`, now required (omitted, 8.x looked the names up in the artifact's own namespace: pass that namespace, which `artifact-resolve` reports as `mappingApplied`); `autoRemap` → `autoRemap`, now `true` by default (8.x defaulted to `false` and failed with `ERR_NAMESPACE_MISMATCH` whenever `mapping` differed from the artifact's namespace); `target: { kind: "version" | "jar" | "coordinate", value }` → `{ kind: "version", version }`, `{ kind: "jar", jarPath }`, `{ kind: "coordinate", coordinate }`; `target: { kind: "workspace", scope?, strict? }` with `projectPath` → `{ kind: "workspace", projectPath, scope? }`, with `strict` dropped as for `artifact-resolve`; `target: { kind: "dependency", group, name, version?, versionFromProject? }` → `{ kind: "dependency", group, name, dependencyVersion }`, or with `projectPath` for `versionFromProject: true`; `projectPath` → `target.projectPath` (version, workspace and dependency targets); `scope` → `target.scope` (version and workspace targets); `strictVersion` → dropped: an approximated version is reported in `result.artifact` with a `version-mismatch` warning instead of failing; `preferProjectVersion` → dropped: a `workspace` target reads the version from the project; `sourcePriority`, `gradleUserHome` → dropped: the server's configured sources are used, as on the symbol tools. In the reply, `exists` becomes `verdict.status` (`ok` or `ambiguous` for `true`), `resolvedOwner` becomes `verdict.className` and `verdict.mapping`, `accessorAdvice` becomes `verdict.advice`, `provenance.artifactId` and `provenance.mappingNamespace` become `result.artifact.artifactId` and `mappingApplied`, the workspace and dependency resolution details of `provenance` are dropped (`artifact-resolve` with `detail: "full"` returns them), and the warnings move to `meta.warnings`.

### `nbt-decode`

Decode Java Edition NBT bytes into a typed JSON document (see [Typed NBT document shape](#typed-nbt-document-shape)). Read-only; works offline.

- Inputs: `nbtBase64` (the NBT bytes as base64; whitespace is ignored), `compression` (`none`, `gzip` or `auto`, default `auto`: the bytes are gunzipped when they start with the gzip header).
- Result: `typedJson` (`{ rootName, root }`), `compressionDetected` (`none` or `gzip`), `inputBytes` (the decoded byte count before any inflation).
- Errors: invalid base64 fails with `ERR_INVALID_INPUT`; a stream that is not well-formed NBT, or `compression: "gzip"` on bytes that are not gzip, fails with `ERR_NBT_PARSE_FAILED`; input over `MCP_MAX_NBT_INPUT_BYTES`, inflated bytes over `MCP_MAX_NBT_INFLATED_BYTES` and a document over `MCP_MAX_NBT_RESPONSE_BYTES` fail with `ERR_LIMIT_EXCEEDED`.
- Example: `{ "nbtBase64": "CgABUgMABmFuc3dlcgAAACoA" }`
- Replaces (8.x): `nbt-to-json`.
- From 8.x `nbt-to-json`: `nbtBase64`, `compression` → same names and defaults. In the reply, `meta.compressionDetected` and `meta.inputBytes` move into `result`.

### `nbt-encode`

Encode a typed NBT JSON document into Java Edition NBT bytes as base64. Read-only; works offline.

- Inputs: `typedJson` (required; the document, as `nbt-decode` returns it), `compression` (`none` or `gzip`, default `none`). `typedJson` is a data document: the NBT format rules validate it, so a member the format does not define is ignored rather than rejected as an unknown key.
- Result: `nbtBase64`, `outputBytes` (the byte count after compression), `compressionApplied`.
- Errors: a document that breaks the format fails with `ERR_NBT_INVALID_TYPED_JSON`; `error.fieldErrors[0].path` is the JSON pointer of the offending node, and `meta.nextActions` holds a `template: true` `nbt-decode` call (`"nbtBase64": "<base64-encoded-nbt-payload>"`), since decoding a real payload yields a well-formed document to edit. A document that validates but cannot be written fails with `ERR_NBT_ENCODE_FAILED`; output over `MCP_MAX_NBT_RESPONSE_BYTES` fails with `ERR_LIMIT_EXCEEDED`.
- Example: `{ "typedJson": { "rootName": "R", "root": { "type": "compound", "value": { "answer": { "type": "int", "value": 42 } } } }, "compression": "gzip" }`
- Replaces (8.x): `json-to-nbt`.
- From 8.x `json-to-nbt`: `typedJson`, `compression` → same names and defaults; `typedJson` is now required by the schema (8.x accepted a call without it and failed with `ERR_NBT_INVALID_TYPED_JSON`; it now fails with `ERR_INVALID_INPUT` naming `typedJson`). In the reply, `meta.outputBytes` and `meta.compressionApplied` move into `result`, and the `exampleCalls` decode suggestion becomes the `nbt-decode` template in `meta.nextActions`.

### `nbt-patch`

Apply RFC 6902 JSON Patch operations to a typed NBT JSON document and return the new document. Read-only; works offline.

- Inputs: `typedJson` (required; the document), `patch` (1 or more operations `{ op, path, value? }`, applied in order). `op` is `add`, `remove`, `replace` or `test`; `move` and `copy` are not supported. `path` is a JSON Pointer into the document (`/root/value/<name>`, with `~1` for `/` and `~0` for `~`; `-` appends to a list's `value` array); `""` addresses the whole document, so `replace` with `path: ""` swaps it. `value` (required by `add`, `replace` and `test`) is the JSON put at `path`: a typed node `{ type, value }` at a node's path, a bare payload at a node's `value` path. Both inputs are data documents: an operation member the RFC does not use, such as `from` on `add`, is ignored, as RFC 6902 says.
- Result: `typedJson`, `appliedOps` (operations applied, `test` included), `testOps`, `changed` (`false` when only `test` operations ran).
- Errors: every operation must leave valid typed NBT; one that does not, a path that does not exist, and a failed `test` fail the whole call with `ERR_JSON_PATCH_CONFLICT`, and no document is returned. A malformed operation (a path without a leading `/`, a missing `value`) fails with `ERR_JSON_PATCH_INVALID`; a malformed input document fails as for `nbt-encode`, with the same `nbt-decode` template.
- Example: `{ "typedJson": { "rootName": "R", "root": { "type": "compound", "value": { "answer": { "type": "int", "value": 42 } } } }, "patch": [{ "op": "test", "path": "/root/value/answer", "value": { "type": "int", "value": 42 } }, { "op": "replace", "path": "/root/value/answer/value", "value": 7 }] }`
- Replaces (8.x): `nbt-apply-json-patch`.
- From 8.x `nbt-apply-json-patch`: `typedJson` → `typedJson`, now required as for `nbt-encode`; `patch` → `patch` with the same `{ op, path, value }` operations, now at least one (8.x accepted an empty patch and returned the document unchanged), and `path: ""` is accepted (8.x rejected an empty path with `ERR_INVALID_INPUT`); `path` is used as given, as RFC 6901 defines it (8.x trimmed surrounding whitespace, so `" /root/value/x "` addressed `/root/value/x`; now it fails with `ERR_JSON_PATCH_INVALID`). In the reply, `meta.appliedOps`, `meta.testOps` and `meta.changed` move into `result`.

### `cache-manage`

Report, list, verify and delete the server's cache entries. A writer (`readOnlyHint: false`, `destructiveHint: true`), but only `action: "delete"` with `apply: true` deletes anything.

- Inputs: `action` (required: `summary`, `list`, `verify` or `delete`), `cacheKinds` (one or more of `artifact-index`, `downloads`, `mapping`, `registry`, `decompiled-source`, `mod-remap`, `binary-remap`, `nested-jar`, `workspace`; default every kind), `selector` (entries matching every field given: `artifactId`, `version` (an entry's version, or a whole version token in its path: `1.21` matches `1.21.4`, `1.2` does not match `1.21`), `jarPath`, `entryId`, `status` (`healthy`, `partial`, `stale`, `orphaned`, `corrupt` or `in_use`), `olderThan` (an ISO-8601 duration such as `P30D` or `PT12H`: entries last updated longer ago than that), `mapping` (`obfuscated`, `mojang`, `intermediary` or `yarn`, as the cache records the entry's namespace), `scope` (`vanilla`, `merged` or `loader`), `projectPath` (the entry's paths under it); `jarPath` and `projectPath` take Windows and `\\wsl$` / `\\wsl.localhost` spellings, and one that names the file system root, such as `/`, fails with `ERR_INVALID_INPUT` naming it, in every action, since it would select every entry), `limit` (`list` only: entries per page, default `50`, no maximum), `cursor` (`list` only), `apply` (`delete` only: `true` deletes; default `false` previews).
- Refusals, each `ERR_INVALID_INPUT` naming the field: `apply` with any action but `delete` (also `apply: false`); `limit` or `cursor` with any action but `list`; `delete` without a `selector` that has at least one field, in preview and apply alike, so a delete never sweeps a whole cache kind by accident. An `olderThan` that is not a positive ISO-8601 duration and an invalid `cursor` fail with `ERR_INVALID_INPUT` too.
- Result: `cache: { action, status, … }`, with the fields each action below returns.
- `summary` returns `cache: { action, status, entryCount, totalBytes, kinds }`; `kinds` has one `{ cacheKind, entryCount, totalBytes, status }` per requested kind, `status` being the kind's health: the first of `in_use`, `corrupt`, `orphaned`, `stale` and `partial` that one of its entries has, else `healthy`; a kind with no matching entries reports `partial`, except `workspace`, which is always `healthy`.
- `list` returns `cache: { action, status, entries }`, each entry `{ cacheKind, entryId, path, sizeBytes, status, meta }` sorted by kind and id; `meta` carries what the cache records about the entry, such as `artifactId`, `version`, `mapping`, `scope`, `updatedAt`, and for an `artifact-index` entry its `binaryJarPath` and `sourceJarPath` (each absent when the artifact has none). `meta.pagination` is `{ hasMore, nextCursor? }`; with more entries, `meta.nextActions` holds the call for the next page.
- `verify` checks every selected entry, including whether each cached registry report still parses, and returns `cache: { action, status, checkedEntries, unhealthyEntries }`; a warning in `meta.warnings` names the health states found. List the unhealthy entries with `action: "list"` and `selector.status`.
- `delete` returns `cache: { action, status, applied, deletedEntries, deletedBytes }`. Without `apply`, it deletes nothing and counts the entries and bytes it would delete; when it found any, `meta.nextActions` holds the same call with `apply: true`. With `apply: true`, an `artifact-index` entry's row is removed from the cache database, a `workspace` entry is forgotten, and other entries' files are removed (a `binary-remap` directory with its contents); the counts are what was actually deleted.
- Statuses: `partial` when a listed, summarized or verified entry is unhealthy (any state but `healthy`), or when an apply could not delete a cached download (a warning names it, and the counts leave it out); otherwise `ok`. Any other entry an apply cannot remove, such as a file in a read-only directory, fails the whole call with `ERR_INTERNAL`, after the entries ahead of it in the listing order were removed. A listing or delete that matches nothing is `ok` with zero counts and no next action.
- The cache database: a call that reads the `artifact-index` kind (every action, a preview included, and every call without `cacheKinds`) opens the cache database as every tool that reads the index does. That open runs a pending full integrity check and backs up and recreates a corrupt database (one that does not open as a database, or fails that check). A preview still deletes no cache entry. A call limited to other kinds does not open it, so it works when the database cannot be opened.
- Example: `{ "action": "delete", "cacheKinds": ["downloads"], "selector": { "version": "1.21.1" } }`; then the `meta.nextActions` call with `"apply": true`.
- Replaces (8.x): `manage-cache`.
- From 8.x `manage-cache`: `action` → `action`, with `inspect` → `list` (inspect returned the first `limit` entries and ignored `cursor`: the first `list` page) and `prune` → `delete` (prune ran the same deletion); `cacheKinds` → `cacheKinds` (an empty list now fails instead of meaning every kind); `selector` → `selector` with the same nine fields (`artifactId`, `version`, `jarPath`, `entryId`, `status`, `olderThan`, `mapping`, `scope`, `projectPath`), `mapping` now `obfuscated`, `mojang`, `intermediary` or `yarn`, `scope` `vanilla`, `merged` or `loader`, and an unknown field rejected; `limit`, `cursor` → same names, `list` only; `executionMode` → `apply` (`"apply"` is `apply: true`; `delete` only, where 8.x ignored it for the other actions); `detail`, `include` → dropped: every action returns its whole answer and its warnings at every call (at its default `detail: "summary"`, 8.x hid the `list` and `inspect` entries and the `summary` stats). A `delete` preview now needs a selector too (8.x previewed the whole cache without one). In the reply, `summary.status` becomes `cache.status` (8.x called a summary with an empty kind `partial`, and a delete `changed` or `unchanged`); `summary.counts` and the `stats`, `cacheEntries` and `operation` blocks become the fields of `cache`; `summary.nextActions` (the `manage-cache` apply call) becomes the `apply: true` call in `meta.nextActions`, offered only when the preview found entries; `meta.pagination.nextCursor` becomes `meta.pagination` with `hasMore`.

### `server-metrics`

Return the runtime counters of this server process since it started. Read-only.

- Inputs: none; any key fails with `ERR_INVALID_INPUT`.
- Result: `metrics`, the snapshot `get-runtime-metrics` returns: per-area timings (`resolve_duration_ms`, `search_duration_ms`, `decompile_duration_ms`, …), search, index and cache counters, `tool_call_counts` and `tool_call_duration_ms` per tool, and the mapping resolution cache statistics. Each call is counted under the name it was made with, so a catalog tool and the 8.x tool it replaces are counted apart; the counters keep the 8.x names as data. A call is counted once its snapshot is taken, so a reply does not count the call that returned it.
- Example: `{}`
- Replaces (8.x): `get-runtime-metrics`.
- From 8.x `get-runtime-metrics`: no inputs (8.x ignored any key it was given; `server-metrics` rejects one). The snapshot is unchanged, under `result.metrics` instead of `result`.

### Essential Conventions

- Among the 8.x tools, the top-level workflow tools `inspect-minecraft`, `analyze-symbol`, `compare-minecraft`, `analyze-mod`, `validate-project`, and `manage-cache` cover the common workflows and return summary-first results with follow-up hints.
- `resolve-artifact` uses `target: { kind, value }`. `kind` is one of `"version"`, `"jar"`, `"coordinate"`, `"workspace"`, or `"dependency"` (see "Workspace and dependency target shapes" below).
- `get-class-source` and `get-class-members` use `target: { kind, value }` — the same `kind`-based shape as `resolve-artifact` (`"version"`, `"jar"`, `"coordinate"`, `"workspace"`, `"dependency"`), plus `target: { kind: "artifact", artifactId }` to reuse an already-resolved artifact.
- `find-class`, `search-class-source`, `get-artifact-file`, `list-artifact-files`, and `index-artifact` accept either an `artifactId` or the shared object `target` shape. All five also accept a top-level `projectPath`, which supplies the workspace context a target cannot supply from its own fields — `target.kind="workspace"`, and `target.kind="dependency"` with no `version` and `versionFromProject` omitted or `true`. A dependency target that sets `versionFromProject: false` and supplies no `version` is rejected with `ERR_INVALID_INPUT` before `projectPath` is read, so that shape must carry its own `version`.
- `validate-mixin` and `validate-project task="mixin"` use `input.mode="inline" | "path" | "paths" | "config" | "project"`.
- Positive integer tool arguments accept numeric strings such as `"10"` for documented top-level parameters.
- A parameter with a fixed safe default takes that default when it is omitted. The 8.x tools are listed with the input schema `{ "type": "object" }`, so their defaults are documented in this reference rather than advertised; catalog tools advertise their defaults in their input schemas.
- Retryable `suggestedCall` payloads omit parameters when the supplied value already matches the tool default, keeping recovery calls smaller without changing behavior.
- `ERR_CLASS_NOT_FOUND` errors from the class tools carry a top-level `didYouMean` array (parallel to `suggestedCall`) with ranked near-miss candidates from the artifact's symbol index: each entry is `{ className, matchReason }` where `matchReason` is `"exact-simple-name"` (same simple name in another package — the moved-class case, ranked first), `"case-insensitive"`, or `"edit-distance:N"`. Candidates come from the symbol index of the artifact the caller REQUESTED first, followed by any the artifact the lookup ended on contributes, deduplicated by FQN. A candidate found outside the requested artifact carries an extra `artifactId` naming where it was found; an entry WITHOUT that field is always from the artifact the caller asked about. The union matters because the requested artifact is, in the partial-source fallback scenario, the one with no `net.minecraft` symbols — which is why the fallback fired — so collecting from it alone returns `[]` in exactly the case the fallback exists to serve. Candidates are hints, never assertions that the class exists at the suggested location; the array is empty when neither index has anything usable. All same-simple-name FQNs are enumerated rather than collapsed. When an internal redirect resolved a different artifact while trying to answer the call — the binary fallback, or the nested-jar redirect that follows a shell jar's bundled inner jar — the error carries `details.fallbackArtifactId` naming it, alongside `details.binaryFallbackAttempted` for the binary case. `details.artifactId`, `details.mapping` and `details.qualityFlags` all describe the REQUESTED artifact, so identity, namespace and quality never disagree about which artifact is being reported. `fallbackArtifactId` and `binaryFallbackAttempted` are internal `AppError.details` fields for diagnosis and are NOT published on the wire; the envelope reports the requested artifact as `error.context.artifactId`.
- For `get-class-members`, cached signatures for a JAR at the same path are reused while its raw `mtimeMs` and size are unchanged. A different value for either causes the signature to be read again.
- For qualified indexed-source queries, `find-class` resolves the full enclosing-type chain in the source file, accepts `.` or `$` between nested types, and returns the requested spelling. It does not use same-named types from other indexed files as substitutes or depend on the global candidate limit; the requested type must exist.
- `find-class` searches the nested `.class` inventories of Jar-in-Jar shell artifacts such as the Fabric API umbrella JAR. It accepts simple or qualified names, returns dotted names for inner classes, deduplicates a class bundled more than once, and honors `limit`. The returned source path is inferred from the outer class. For top-level matches, `get-class-source` and `get-class-members` resolve the actual containing nested JAR before reading content; dotted inner-class matches are also readable through `get-class-source`. An empty result means no match in the class inventories that could be read: a nested JAR that cannot be read or exceeds the nested-entry size cap is skipped without a warning, and when the artifact's source coverage excludes `net.minecraft` and the query is a Minecraft-style class name, `warnings` says so and `suggestedCall` points to `get-class-source`.
- Source-oriented tools expose `artifactContents` so callers can tell whether the backing artifact is a `source-jar` or a `decompiled-binary`. `get-class-source`, `get-class-members`, `search-class-source`, and `get-artifact-file` also expose `returnedNamespace`.
- `get-class-source` with `mode: "metadata"` (the default) returns a generated outline of the class's symbols in `sourceText`, not a slice of its source lines, so the response has no `returnedRange` key (also through `batch-class-source` entries and `inspect-minecraft task="class-source"`). `totalLines` is the line count of the whole source file the outline was built from, and `truncated` / `charsTruncated` are `true` only when `maxChars` cut the outline. Use `mode: "snippet"` or `"full"` when you need line numbers: those modes return `returnedRange`.
- When `mapping` is omitted, `get-class-source`, `get-class-members`, and `batch-class-members` all inherit the mapping the target artifact was resolved with, and report it as `returnedNamespace` (an inherited `obfuscated` on a 26.1+ runtime is reported as `mojang`; see [Namespace Definitions](#namespace-definitions)). A target that carries no resolved mapping of its own falls back to `obfuscated`. An explicit `mapping` is never overridden.
- Cache-backed source, mapping, validation, batch, and workflow tools accept `gradleUserHome?: string` when they need Loom cache data. Use it for builds that used an isolated `GRADLE_USER_HOME`; the server searches `<gradleUserHome>/loom-cache` and `<gradleUserHome>/caches/fabric-loom` instead of the MCP process's Gradle User Home; project-local roots under `projectPath` still apply. The value selects a Gradle User Home, not arbitrary Loom cache roots.
- `resolve-artifact` adds the `binary-jar-no-classes` quality flag when the binary jar it accepted opens cleanly but holds no `.class` entry — a `yarn`/`intermediary` `v2` mapping jar, a resource-only mod jar, or a jar of nothing but directory entries. The flag describes such an artifact and never refuses it, so an empty decompile can be told apart from a decompiler fault. It is set for `target.kind="coordinate"`, `"jar"` and `"version"`. A class-free jar that is not a Jar-in-Jar shell still fails during indexing with `ERR_DECOMPILER_FAILED`, so the flag does not reach the response in that case.
- `get-class-members` returns `decompiledFallback` (with `constructors`, `fields`, `methods`, each entry is `{ name, line, kind }`) and `decompiledMemberCounts` whenever bytecode enumeration yields zero but the decompiled source for the class is already indexed. The bytecode-derived `members` / `counts` are preserved as-is; the fallback is additive and carries no descriptor or access modifier. `qualityFlags` gains `"members-from-decompiled-source"` in that case. Use `get-class-source` for descriptors and full context.
- `get-class-members` also returns an additive `status: "ok" | "members_unavailable" | "partial"` field so callers can distinguish "really 0 members" from "extraction unavailable":

  | `status` | When | Extra fields |
  | --- | --- | --- |
  | `"ok"` | `counts.total > 0`, OR `counts.total === 0` AND binary extraction succeeded AND `decompiledFallback` did not fire (genuinely empty class). | none |
  | `"partial"` | `decompiledFallback` is populated (bytecode returned zero but the indexed decompiled source supplied member names; `qualityFlags` includes `"members-from-decompiled-source"`). | `decompiledFallback`, `decompiledMemberCounts` |
  | `"members_unavailable"` | Binary signature extraction threw a non-`ERR_CLASS_NOT_FOUND` error AND no decompiled fallback was available. | `unavailableReason: string`, `suggestedCall: { tool: "get-class-source", params: { target: { kind: "artifact", artifactId }, className, mode: "snippet", mapping } }` (the params validate against `get-class-source`'s input schema). |

  The shape is purely additive: `members` / `counts` / `decompiledFallback` / `decompiledMemberCounts` / `qualityFlags` are unchanged for callers that ignore `status`. `ERR_CLASS_NOT_FOUND` still propagates as a thrown error rather than as `members_unavailable`. Set `MEMBERS_STATUS_LEGACY=1` at process start to omit `status` / `unavailableReason` / `suggestedCall` entirely (legacy shape).
- `get-class-members` returns a `context` block describing the jar the bytecode was read from — `{ minecraftVersion, mappingType, mappingNamespace, jarSignature, generatedAt }`. A `batch-class-members` per-entry result carries the same block only at a detail level that retains it, `detail: "standard"` or `"full"`; the batch tool defaults to `detail: "summary"`, which strips the whole block from every entry exactly as it does on a direct `get-class-members` call (see the projection bullet below). `analyze-mod` `task="members"` omits it by design, because an arbitrary mod jar's path names the mod's own version. `minecraftVersion` is `"unknown"` for an artifact classified as a dependency. For any other artifact it is read from the jar's path: a jar inside a dependency store — Gradle's `modules-2` cache, or the local Maven repository at `~/.m2` or wherever `MCP_LOCAL_M2` points it — reports a version only when the part of the path below the store's own root names the Minecraft runtime: either the `net/minecraft` group directory followed by a runtime artifactId, or — under any other group — a jar FILE NAME that starts with `minecraft-`, which is the position both store layouts build from the artifactId. No other part of the path may name the runtime, so neither a group directory that starts with `minecraft-` (`com.minecraft-tools:annotations`) nor a file name that merely contains the token (`my-minecraft-client-helper-9.9.jar`) qualifies. Minecraft's own jar staged inside either store still reports its version while another jar there reports `"unknown"` instead of the cache-layout constant `2.1` or that jar's own release number; a jar outside any dependency store is read heuristically and reports the first version-shaped token anywhere in its path, whether or not the jar is Minecraft's. When the path yields nothing, the version the resolver established fills it in — except for a dependency artifact, whose resolver-side version is its own coordinate version, so `"unknown"` stands and no Minecraft version is substituted for it. `mappingType` is the literal `"unknown"` on every response; nothing populates it. `mappingNamespace` and the sibling `returnedNamespace` are both set from the request's effective mapping, so the two always agree with each other; neither promises that every returned name is in that namespace, because an individual member whose remap failed keeps its source-namespace name. `generatedAt` is the ISO-8601 instant the response was built.
- `context.jarSignature` is a sha256 over the jar's resolved path, modification time and size on a successful binary extraction, and the empty string when binary member extraction failed — the failure the `status` table above reports as `"members_unavailable"`, or as `"partial"` when the decompiled fallback supplied names instead. It is NOT a hash of the jar's bytes, so it is neither a content identity nor a cache key: two byte-identical jars at different paths sign differently, a jar merely touched signs differently from itself, and two different sets of bytes written to one path at the same size and modification time sign identically. A changed signature therefore does not prove the jar's bytes changed, and an unchanged one does not prove they did not; use it for one thing only: spotting that the jar behind two responses is no longer the same file in the same state. (The field was called `jarHash` until the rename recorded in `CHANGELOG.md`; the value and its derivation are unchanged.)
- `search-class-source` accepts `queryNamespace`. For `intent="symbol"`, an explicitly namespaced fully-qualified class name is searched by its simple name and package, including when the namespace already matches the artifact. Mojang names on a proven unobfuscated Minecraft runtime (26.1+) also use this identity path when the stored label is `obfuscated`; no mapping data is required. Genuinely different namespaces are translated through `find-mapping` before search. An explicit `scope.packagePrefix` takes precedence over the package derived from either the original or translated class name. `translatedQuery` describes a namespace/name rewrite, not an unchanged identity lookup; identity does not imply a mapping graph was consulted. Omitting `queryNamespace` keeps the existing query behavior. `intent="text"` / `intent="path"` do not translate — text search is a literal match against the artifact namespace; namespace mismatches surface warnings instead. `sourcePriority` is only consulted during translation.
- The nine lookup tools and four `batch-*` tools named in the per-tool defaults below share the entry-tool **`detail`** (`summary` | `standard` | `full`) + **`include[]`** response contract (the per-tool `compact` boolean is gone). `summary` is the terse shape (drops diagnostics/empties, slims candidates), `standard` keeps fields but drops heavy diagnostics, `full` keeps everything. Per-tool defaults are chosen so the default response is unchanged: `resolve-artifact`, `find-mapping`, `resolve-method-mapping-exact`, `resolve-workspace-symbol`, `check-symbol-exists`, and the four `batch-*` tools default **`summary`**; `get-class-source`, `get-class-members`, `search-class-source`, and `list-artifact-files` default **`standard`**. (Migration: `compact: true` → `detail: "summary"`; `compact: false` → `detail: "full"`.)
- At `detail: "summary"`, empty arrays / null / empty objects are stripped. For `resolve-artifact` it also omits `provenance`, `artifactContents`, `sampleEntries`, `adjacentSourceCandidates`, `binaryJarPath`, `coordinate`, `repoUrl`, and `resolvedSourceJarPath` — `include: ["provenance"|"artifact"|"samples"|"candidates"|"paths"]` re-adds the matching field(s). For mapping tools, `summary` (1) omits the redundant `candidates` array on a single full-confidence exact-match resolution and (2) slims the tail to `{kind, symbol, owner, name, descriptor, confidence, matchKind}` with `candidateDetailsTruncated: true` when an unresolved result has more than three candidates; `include: ["candidates"]` keeps the full candidate list. `candidatesTruncated` keeps its independent meaning ("more candidates exist upstream than returned").
- `get-class-source` and `get-class-members` omit the diagnostic fields `provenance`, `artifactContents`, and `qualityFlags` at `detail: "summary"` and `detail: "standard"` (the lean common path). Pass `include: ["provenance"]` (or the legacy alias `includeProvenance: true`) or use `detail: "full"` to include all three. `detail: "summary"` additionally strips empty fields, and for `get-class-members` also strips `context`; `decompiledFallback` and `decompiledMemberCounts` are preserved. `search-class-source` and `list-artifact-files` omit `artifactContents` at `detail: "summary"` (re-add via `include: ["artifact"]`) — the primary `hits` / `items` payload is always preserved.
- `get-class-members` returns a slim member shape: `accessFlags` is dropped (modifiers are in `javaSignature`), `ownerFqn` is hoisted to a single block-level `members.ownerFqn` when all members share one owner (per-member only when `includeInherited` surfaces multiple owners), and **field** `jvmDescriptor` is omitted by default. Method/constructor `jvmDescriptor` is always present for overload disambiguation. Pass `include: ["descriptors"]` (or the legacy alias `includeDescriptors: true`) to also emit field descriptors.
- Windows and WSL path forms are normalized for `jarPath`, `projectPath`, and environment-variable path overrides.
- Heavy analysis tools are serialized in-process to protect stdio stability. Queue overflow returns `ERR_LIMIT_EXCEEDED`.
- All tools and JSON resources use the standard `{ result?, error?, meta }` envelope. `class-source` and `artifact-file` resources return raw text on success and structured JSON on failure.

### Inspection response controls

`include[]` support depends on the tool and task: it can retain optional result blocks or affect what is fetched. `meta.includeApplied` echoes the normalized, deduplicated request; it does not guarantee that every requested group produced a block. `timings` is accepted wherever `include` lists it, but no tool currently returns a timings block. For example, `inspect-minecraft task="class-overview"` does not return a member list or a detailed provenance block, even with `detail: "full"` or those include groups. For signatures, select `task: "class-members", detail: "standard", include: ["descriptors"]`; at summary detail, also include `"members"` to retain the member block.

For `inspect-minecraft task="search"`, `detail: "summary", include: ["samples"]` retains `result.search` with the first zero to five hits in the existing rank order, including `hits: []` on a miss. Summary without samples omits this block. `result.summary.counts.hits` counts the fetched hits. At summary, `meta.pagination.returnedCount` counts the samples, the first zero to five fetched hits, whether or not `include: ["samples"]` returns them; at `standard` and `full` it counts the whole fetched page. Seven fetched hits at summary therefore report `counts.hits: 7`, `returnedCount: 5`, and `hasMore: false` when no further page exists. `result.search.nextCursor` and `meta.pagination.nextCursor` keep the original page continuation: they advance after the fetched page and cannot recover its sixth and seventh hits, which are not among the samples. Repeat the same subject, limit and input cursor with `detail: "standard"` or `"full"` to see that whole fetched page, with or without samples.

For `inspect-minecraft task="list-files"`, `meta.pagination` reports `returnedCount`, `hasMore` and, when the listing returned a cursor, `nextCursor` at every detail. The listing returns a cursor for every full page, so when the last page holds exactly `limit` paths, `hasMore` is still true and the next call returns no paths. At summary, the task samples the first zero to ten listed paths, and `result.files` returns them only with `include: ["files"]`; `returnedCount` counts those samples whether or not they are returned. `hasMore` and `nextCursor` continue after the fetched page, not after the samples. Use `detail: "standard"` or `"full"` to see the whole fetched page, where `returnedCount` counts it.

Response detail and source mode are separate controls. `inspect-minecraft task="class-source"` requests source metadata by default; `include: ["source"]` or `detail: "full"` requests a snippet, not the whole file. To read later lines deliberately, call `get-class-source` with the returned artifact ID, the original requested class name and mapping, and explicit ranges, for example:

```json
{
  "tool": "get-class-source",
  "arguments": {
    "target": { "kind": "artifact", "artifactId": "<resolved-artifact-id>" },
    "className": "net.minecraft.world.item.Item",
    "mapping": "mojang",
    "mode": "snippet",
    "startLine": 201,
    "endLine": 400
  }
}
```

Use the mapping from your original lookup rather than substituting the returned class name's namespace. Carry forward applicable `projectPath`, `gradleUserHome` and `sourcePriority` context when making later low-level reads. If the original mapping was omitted, source/member lookup can inherit the resolved artifact's stored mapping. Use `get-class-source mode="full"` when you explicitly want the whole file.

For `analyze-symbol task="workspace"`, read `result.workspace.mappingApplied` for the applied workspace mapping (`detail: "standard"` or `include: ["workspace"]` retains it). `result.summary.subject.sourceMapping` echoes the requested source mapping.

### inspect-minecraft workspace focus

Use `subject.kind="workspace"` when `inspect-minecraft` should resolve Minecraft artifact context from a project. Its `focus` is a structured object, not a string:

| --- | --- | --- |
| `focus: { kind: "class", className: "..." }` | `class-overview` | `class-overview`, `class-source`, `class-members` |

`task="auto"` is structured dispatch based on `subject.kind` and `focus.kind`; it is not a natural-language planner and does not interpret prose. ### Workspace and dependency target shapes

`resolve-artifact`, `get-class-source`, and `get-class-members` accept two synthesizing `target.kind` values in addition to the canonical `"version"` / `"jar"` / `"coordinate"` shapes. The synthesizer rewrites the call into one of those canonical shapes before downstream resolution, so behaviour from the resolver onward is unchanged.

| target shape | When to use | Required input | Result |
|---|---|---|---|
| `{ kind: "workspace", scope?, strict? }` | When the caller already passes a `projectPath` and wants the tool to detect Minecraft version, compile mapping, and loader from `gradle.properties` and `build.gradle(.kts)`. | `projectPath` | Synthesised to `{ kind: "version", value: <detected> }`. Scope precedence is `target.scope` → top-level `scope` → loader-derived default (`"merged"` when a loader is detected, `"vanilla"` otherwise). When the version is not detected, raises `ERR_WORKSPACE_VERSION_UNRESOLVED` regardless of `strict`. Detected facts surface on `provenance.workspaceResolution`. |
| `{ kind: "dependency", group, name, version?, versionFromProject? }` | When the caller wants to resolve a Maven-coordinate dependency (e.g. `dev.architectury:architectury`) without computing the exact version themselves. | `projectPath` (unless `version` is given) | Synthesised to `{ kind: "coordinate", value: "<group>:<name>:<version>" }`. The dependency JAR is treated as non-vanilla: binary remap is suppressed, so a non-obfuscated mapping request is honored only if a source-backed jar can supply it. If a source-backed jar is available, the resolver returns `mappingApplied` equal to the requested mapping with `qualityFlags` including `"source-backed"`, and no warning is added. If none is, that same non-obfuscated request comes back with `mappingApplied: "obfuscated"` and `qualityFlags` including `"dependency-mapping-unverified"`, plus a warning that the caller must validate symbol availability. An explicit `mapping: "obfuscated"` request never takes that branch: it passes through as `mappingApplied: "obfuscated"` with `qualityFlags` including `"source-backed"` (or `"decompiled"`), and never carries `"dependency-mapping-unverified"`. Resolution metadata appears on `provenance.dependencyResolution`. |

#### Inspecting a Fabric / loader dependency like vanilla

To read members or source of a Fabric API (or any loader/Maven dependency) class
the same way you read vanilla, pass a `dependency` target straight to
`get-class-members` / `get-class-source` — no separate lookup tool is needed:

```jsonc
// members of a Fabric API class, version taken from the workspace
{
  "tool": "get-class-members",
  "className": "net.fabricmc.fabric.api.event.player.UseEntityCallback",
  "target": { "kind": "dependency", "group": "net.fabricmc.fabric-api", "name": "fabric-api", "versionFromProject": true },
  "projectPath": "/path/to/workspace"
}
```

Use an explicit `"version"` instead of `versionFromProject` when you already
know it. Because dependency JARs are not binary-remapped, a non-obfuscated
mapping request is honored only when a source-backed jar can supply it: there
`mappingApplied` equals the requested mapping and `qualityFlags` includes
`"source-backed"`. When no source-backed jar can supply it, that same
non-obfuscated request comes back in the dependency's own namespace with
`mappingApplied: "obfuscated"` and `qualityFlags` including
`"dependency-mapping-unverified"`, and the names are the JAR's compiled names.
A request that asks for `"obfuscated"` outright is a separate branch: it passes
through as `mappingApplied: "obfuscated"` with `"source-backed"` or
`"decompiled"`, never with `"dependency-mapping-unverified"`.
For repeated lookups against the same dependency, call `resolve-artifact` once
and reuse the returned `artifactId` via `target: { kind: "artifact", artifactId }`.

Workspace detection is memoised in a process-resident `WorkspaceContextCache` (16-entry LRU, 5-minute TTL). A cache hit also re-stats the project files the detection read: unconditionally, the project root's `gradle.properties`, `build.gradle`, and `build.gradle.kts` (present or not, stat taken before detection runs so even an edit racing the read is caught); plus any subproject `build.gradle`/`build.gradle.kts` or mod descriptor (`fabric.mod.json`, `quilt.mod.json`, `META-INF/mods.toml`, `META-INF/neoforge.mods.toml`) that actually contributed a compile-mapping or loader declaration (stat taken after detection returns, since which files those are is not known beforehand - an edit landing in the narrow window between detection reading such a file and this later stat is not guaranteed to be caught immediately, though the next read() re-stats it again). If a covered file was edited, created, or deleted since the entry was written, the hit is discarded and the workspace is re-detected, even within the TTL. Two things are NOT covered by any of this: a subproject build script or descriptor that was scanned but declared nothing (editing one to newly declare a mapping/loader is only picked up once the 5-minute TTL expires and the workspace is re-detected from scratch); and `settings.gradle(.kts)`/`libs.versions.toml`, which detection does not read at all, at any point - editing either changes nothing detection reports, regardless of caching or TTL. The cache is observable through `manage-cache` with `cacheKinds: ["workspace"]`, and individual entries can still be invalidated manually via `selector.projectPath`.

`target.kind="dependency"` resolution probes up to six de-duplicated `gradle.properties` keys in order — `name_version`, `snake_case(name)_version`, `camelCaseVersion`, `lastSegment(group)_name_version`, `snake_case(lastSegment(group)_name)_version`, and `camelCase(lastSegment(group)_name)Version`. Hyphens become underscores in the snake_case forms (`fabric-api` probes `fabric_api_version`); for hyphen-less names the snake_case forms deduplicate into the raw keys, leaving four. The probe falls back to the modules-2 cache layout `~/.gradle/caches/modules-2/files-2.1/<group>/<name>/`. `group` and `name` are held to the coordinate route's identifier rule (`[A-Za-z0-9._+-]`, no leading `.`, no `..`) **before** either probe runs, so no directory is listed on behalf of a coordinate that would be refused later — a blocklist of `/`, `\`, `..` and NUL was not enough, since `group="D:"` with `name="."` carries none of them and is drive-relative on Windows. Version tokens that contain path separators, `..`, NUL, control characters, or any character outside `[A-Za-z0-9._+-]` and the space are rejected; in `gradle.properties` the rejection is recorded under `attempts[]` as `gradle.properties:<key>:rejected-unsafe-version` and the next key is tried. An explicit `target.version` is trimmed before it is checked, matching the coordinate route. Snapshot and dev directories are excluded by default. The modules-2 fallback resolves directly when exactly one valid entry remains. When several entries remain and the dependency is a submodule of an umbrella package (artifact name differs from the group's last segment, e.g. `net.fabricmc.fabric-api:fabric-screen-handler-api-v1`), the declared umbrella version property (`fabric_api_version` / `fabricApiVersion`) locates the cached umbrella POM and the submodule adopts the version that POM names — the resolving response records `provenance.submoduleVersionSource: "umbrella-pom"` with the POM path in `provenance.source` (workspace-context-cache hits within the TTL return the cached version with `provenance.source: "workspace-context-cache"` instead). Umbrella properties are never adopted verbatim as a submodule's version. Every remaining ambiguity raises `ERR_DEPENDENCY_VERSION_UNRESOLVED` with `candidatesSeen` so a global cache cannot supply a version the workspace did not declare.

`target.kind="coordinate"` values are parsed as `group:artifact:version[:classifier]`, and **all four** segments are held to that same token rule: 1–200 characters from `[A-Za-z0-9._+-]`, no leading `.`, and no `..`. `version` and `classifier` additionally admit the space character, because Fabric publishes Yarn against Minecraft's own pre-release ids and those contain spaces — `net.fabricmc:yarn:1.14 Pre-Release 1+build.10:v2` is a real coordinate. `groupId` and `artifactId` stay space-free: Maven identifiers never carry one. A space is not a path separator and cannot leave a directory, so the segment still becomes exactly one path component. The 200-character bound is a sanity limit on a single segment, **not** a control on the length of the resulting file name — `artifactId`, `version` and `classifier` are concatenated into one name, so the filesystem's own `NAME_MAX` is what refuses an overlong one. Every segment becomes a directory or file-name component in the `~/.m2` layout, the Gradle cache layout, and the remote repository URL, so this is enforced once at the parse chokepoint rather than at each of those sinks. Each segment is trimmed before it is checked — `g : a : 1.0` resolves as `g:a:1.0` — as is whitespace around the whole value, which also means a leading or trailing space cannot survive into a `version`. A rejected segment raises `ERR_COORDINATE_PARSE_FAILED` with `details.component` naming it (`groupId`, `artifactId`, `version`, or `classifier`) — an empty mandatory segment included — and `details.coordinate` echoing the coordinate string as the parser received it. On a `target.kind="coordinate"` request that is `target.value` **after** the tool has trimmed its outer whitespace, so padding around the whole value is not echoed back; padding around an individual segment is. Because a `dependency` target is synthesised into a coordinate, both routes enforce the identical rule, and the dependency route applies it to `group` and `name` before it touches the filesystem.

### Common Pitfalls

- Flat-`artifactId` tools (`find-class`, `get-artifact-file`, `list-artifact-files`, `search-class-source`, `index-artifact`) also accept the shared `target` shape (`{ kind: "version" | "jar" | "coordinate" | "artifact" | "dependency", ... }`) instead of `artifactId` — exactly one of the two must be supplied. The target is resolved (and ingested if needed) before the lookup, so a fresh `resolve-artifact` round-trip is unnecessary. `{ kind: "artifact", artifactId }` passes through directly. Targets that need workspace context beyond their own fields — `kind: "workspace"`, or `kind: "dependency"` without an explicit `version` — need a `projectPath`: all five tools accept a top-level `projectPath` parameter for this. Alternatively, resolve with `resolve-artifact` first and pass the returned `artifactId`.
- `analyze-symbol` infers an omitted `version` from `projectPath` (gradle.properties `minecraft_version`/`mc_version`); the response then carries `versionInference { version, source }` and a warning. An explicit `version` always wins. `inspect-minecraft` direct subjects without `subject.artifact` auto-resolve only when exactly one workspace is known to the process (provenance warning attached); several candidates are refused with `workspaceCandidates`. That unique workspace is then resolved through `target.kind="workspace"` like any other workspace subject, so it picks up the project's compile mapping and loader scope; the separately detected Minecraft version is retained only as the "is this workspace usable at all" guard.

- Loom split-source workspaces publish a version as a `minecraft-common` / `minecraft-clientOnly` sources-jar pair with no merged jar. Version-target resolution indexes both halves (the companion jar appears in `provenance.companionSourceJars`), so client-only classes are queryable under the merged scope. If a class still cannot be found, the error's `exampleCalls` carries a `scope: "vanilla"` retry — the decompiled client jar also contains client-only classes.
- `mapping="mojang"` requires source-backed artifacts on legacy obfuscated versions. For unobfuscated releases such as `26.1+`, the runtime/decompile path is accepted directly for version targets, Minecraft runtime coordinates such as `net.minecraft:client:26.1`, and jar targets proven to be a 26.1+ Minecraft runtime jar (see [Lookup Rules](#lookup-rules)). When source jars are not available but the version's Mojang tiny mappings, the tiny-remapper jar, and `MappingService.checkMappingHealth` are all healthy, `resolve-artifact` with `target.kind="version"` will transparently tiny-remap the binary jar (`obfuscated -> mojang`) and decompile the result, and the response carries `qualityFlags` `"binary-remapped"` and `"decompiled"` plus `provenance.transformChain` `"binary-remap:obf->mojang"` and `"decompile:vineflower"`. Coordinate and jar targets are not eligible for this fallback; a legacy coordinate or a jar that is not proven to be a 26.1+ runtime jar still surfaces `ERR_MAPPING_NOT_APPLIED`. Source-backed and obfuscated artifacts keep their existing `artifactId` hashes — only the new mojang-remapped variant lives in a separate cache slot.
- For `mapping="mojang"` on 26.1+ version targets, Minecraft runtime coordinates such as `net.minecraft:client:26.1`, and jar targets proven by their contents to be such Minecraft runtimes, explicit `allowDecompile: false` rejects a binary-only result with `ERR_SOURCE_NOT_FOUND` before source ingestion or decompilation. Available source jars remain usable. This option does not prevent downloads or source discovery needed to resolve the target. Legacy Mojang binary-remap eligibility and its mapping errors keep the behavior described above.
- Mojang binary-remap cache entries live under `<cacheDir>/remapped`. `manage-cache` lists valid files plus corrupt directories and leftover temp entries under `cacheKinds: ["binary-remap"]`; corrupt entries carry `status: "corrupt"` and `meta.artifactId`, so callers can preview or apply cleanup with `selector.artifactId`.
- Jar-in-Jar shell jars (near-zero own classes with bundled `META-INF/jars/*.jar`, e.g. the Fabric API umbrella jar) no longer dead-end in `ERR_DECOMPILER_FAILED`. `resolve-artifact` detects the shell, skips decompilation, and returns the artifact with `qualityFlags: ["shell-jar"]` and the bundled inventory in `provenance.nestedJars`; `analyze-mod-jar` reports the same inventory as `nestedJars`. `get-class-source` / `get-class-members` lookups against a shell automatically redirect to the single nested jar containing the class and mark the response with `provenance.nestedJar` (`entryName` + `shellArtifactId`); after a redirect, `get-class-source` returns the nested jar's `artifactId`, which covers only that jar, while `get-class-members` keeps the shell's; a class found in several nested jars raises `ERR_NESTED_JAR_AMBIGUOUS` with `nestedJarCandidates` and per-candidate `suggestedCall` examples instead of picking one. Class-not-found errors on a shell carry the `nestedJars` inventory, on every access path that publishes one — the tool result envelope, `batch-*` entries, and `mc://` resource reads — with `nestedJarsTruncated: true` beside it when caps shortened the published list. That flag is omitted entirely when the inventory is complete, so read its absence as "complete", never as "unknown". `search-class-source` does not follow the redirect: a shell indexes none of its bundled classes, so its searches return no hits and a warning that points to `find-class`. The redirect is deliberately single-level: a nested jar that is itself a shell surfaces its own inventory when resolved directly as its own artifact. Extracted nested jars are content-addressed under `<cacheDir>/nested-jars`, observable through `manage-cache` with `cacheKinds: ["nested-jar"]`.
- `list-artifact-files` indexes Java source paths only — `assets/` and `data/` prefixes list nothing. Text files under those prefixes ARE retrievable by exact path with `get-artifact-file`: when the index has no row, the tool reads the entry directly from the backing jar (`deliveryMode: "jar-read-through"` marks such responses). This works for any artifact with a backing jar — vanilla client jars and mod jars alike; for Jar-in-Jar shells it reads the shell's own entries only (resolve a nested jar as its own artifact to reach its resources). Read-through delivery is text-only with a 512 KiB per-file cap (`truncated: true` beyond it); binary entries (e.g. `.png`, `.ogg`) answer with size metadata plus `contentOmittedReason` instead of content. Traversal-shaped paths (`..`, absolute) are rejected with `ERR_INVALID_INPUT`, and a miss returns `ERR_FILE_NOT_FOUND` with `nearbyPaths` naming same-named entries elsewhere in the jar (directory layouts move between versions, e.g. `assets/minecraft/models/item/*` → `assets/minecraft/items/*`).
- `search-class-source` defaults to `queryMode="auto"`. Use `queryMode="literal"` for explicit substring scans. Indexed `intent="text"` search (`queryMode="auto"` or `"token"`, any `match` except `"regex"`) selects candidate files by whole index tokens: the index splits source text at every character that is not a letter or digit, such as whitespace, `.`, `_`, `$` and `-`, does not split camelCase, and ignores case; with `match="prefix"` the last query word may match the start of a token. Each candidate is then checked for the query as a substring, ignoring case for `"contains"` and `"prefix"` and matching case exactly for `"exact"`. A `"contains"` query for `Entity` therefore does not find a file whose only occurrence is inside `LivingEntity`, and a file that also has a standalone `Entity` can report its first match inside `LivingEntity`. `queryMode="literal"` checks every file for the substring, so `Entity` also finds `LivingEntity` and `entityCount`. Decompiled text, such as Minecraft source, can differ from hand-written code: parameters may be `final`, annotations such as `@Nullable` can sit between modifiers and the type, and long declarations wrap. Search for a method by its name (or with `intent="symbol"`) rather than by a full declaration such as `public void teleportTo(double`. `match="regex"` enforces `query.length <= 200` and caps results at `100`.
- `search-class-source` returns compact hits only. Content hits (`matchedIn: "content"`) also carry `line`, the 1-based line of the first match in the file, and `context`, that line with one line before and after it joined by `\n`, the same fields `search-mod-source` returns; symbol hits carry their line in `symbol.line`, and path hits carry neither. Content hits also carry `enclosingSymbol: { symbolKind, symbolName, startLine, endLine }`, the innermost declaration whose line range contains `line`. `startLine` is the declaration's own line, the line symbol search reports for it, so annotation lines above it are outside the range; `endLine` is the line of the brace that closes its body, or of the `;` that ends a field or a method without a body. A constructor appears as `symbolKind: "method"` named after its class. Lambdas, anonymous classes, enum constants, initializer blocks and compact record constructors are not declarations here, so a match inside one names the member or type that holds it. `enclosingSymbol` is absent when no declaration contains the line, such as a match in the package line, an import or the file's header comment. Pass `startLine` and `endLine` to `get-class-source` with `mode: "snippet"` to read that declaration. Symbol and path hits never carry `enclosingSymbol`. `inspect-minecraft` `task: "search"` returns the same hits. Use `get-artifact-file` or `get-class-source` to inspect returned files.
- Indexed `intent="text"` and `intent="path"` searches (any `match` except `"regex"`; for text, any `queryMode` except `"literal"`) read one bounded candidate window from the index in index-relevance order and verify only those candidates: 500 for `match="exact"`/`"prefix"`, and five times the maximum hit count (500 to 5,000; 1,000 by default) for `"contains"`. `scope.packagePrefix`, or the literal directory prefix before the first `*`/`?` of `scope.fileGlob`, narrows that window inside the index, so in-scope matches are found even when many out-of-scope files also match. A glob without a literal prefix, such as `**/*Entity.java`, is applied only to the candidates already in the window, so its hits stay limited to that window. When the index matched more candidates than the window holds, the window's last page, the one without `nextCursor`, carries a `warnings` entry that says the search examined only its candidate window and results may be incomplete, whether or not that page is full. An indexed `intent="symbol"` search (any `match` except `"regex"`) reads a window of matching symbols in name order, of the same size as for `"contains"`, and reports a cut the same way; `match="regex"` scans every symbol. To search past the window, use `queryMode="literal"` with `intent="text"` (a full substring scan, still bounded by the scan byte budget; a `warnings` entry reports when that budget is reached), or `match="regex"` for paths. When `packagePrefix` or `fileGlob` (top-level on `search-class-source`; on the search subject or workspace focus of `inspect-minecraft` `task: "search"`) matches no indexed file path, the search reads no file and returns no source hits, for every `intent`, `match` and `queryMode`, with a `warnings` entry that says so; a workspace `inspect-minecraft` search can still add its binary-backed class match, which ignores these filters. Indexed paths are Java source only, so a resource glob such as `data/minecraft/recipe/*.json` never matches (read such a file by exact path with `get-artifact-file`). `*` and `?` do not match `/`, so `*ServerChunkCache*` matches only a file at the top of the index, while `**/*ServerChunkCache*` matches it in any directory.
- On legacy (1.x) versions, `find-class` and `get-class-source` on `mapping="obfuscated"` expect Mojang obfuscated names. Deobfuscated queries warn and usually need `mapping="mojang"` or a `find-mapping` step first. On `26.1+` the `obfuscated` names already are Mojang names, so no mapping step applies; a miss points at near-miss class names instead (see [Lookup Rules](#lookup-rules)).
- `get-class-members` exposes `annotationDefault` on annotation-type members (the `default` value of an `@interface` member) whenever the classfile carries it, and accepts `includeAnnotations: true` to additionally list runtime-visible member annotations such as `@java.lang.Deprecated` per member. The leaner `names`/`signatures` projections drop annotation fields. `analyze-mod` `task="members"` includes both without a flag.
- On unobfuscated versions, `find-mapping`, `resolve-method-mapping-exact`, and `check-symbol-exists` report two structured `mappingContext` flags instead of per-response warning sentences (`get-class-api-matrix` reports a top-level `unobfuscatedRuntime: true` — its non-mojang columns are empty by design there): `unobfuscatedRuntime: true` replaces "Version X is unobfuscated; mapping graph is empty because the runtime already uses deobfuscated names.", and `runtimeValidated: true` replaces "Version X is unobfuscated; validated symbol existence against runtime bytecode." Do not pattern-match the old sentences.
- `check-symbol-exists` defaults to strict FQCN class lookup. Use `nameMode="auto"` for short class names.
- On unobfuscated versions, the runtime-bytecode check behind `check-symbol-exists` answers a method query named `<init>` from the class's own constructors, so an existing constructor descriptor resolves instead of returning `not_found`.
- For unobfuscated releases such as `26.1+`, `check-symbol-exists` and `analyze-symbol task="exists"` validate `mojang` lookups against runtime bytecode when no mapping graph exists, and return `mapping_unavailable` when the runtime JAR itself is unreachable.
- On unobfuscated versions, every `not_found` and `mapping_unavailable` verdict from the mapping graph — classes and fields included, not just methods — is re-validated against runtime bytecode before being returned, so a graph that lacks a record for a real symbol (e.g. `EntityType.ITEM`) no longer produces false negatives. Genuinely-missing symbols still return `not_found` after the runtime check. Bytecode-derived response contexts report `mappingNamespace: "mojang"` on unobfuscated versions instead of a hardcoded `"obfuscated"`.
- `check-symbol-exists` can use `signatureMode="name-only"` for overload discovery, but exact `descriptor` matching is still the most reliable path.
- Inherited-member expansion (`get-class-members` with `includeInherited: true`, and the `check-symbol-exists` runtime-bytecode fallback that reuses it) suppresses super-class and interface resolution warnings for platform packages that are never inside a Minecraft jar (`java.*`, `javax.*`, `jdk.*`, `sun.*`, `com.mojang.serialization.*`). A warning about any other unresolved super type — including `com.mojang.blaze3d.*` — is a real signal.
- `analyze-symbol task="api-overview"` inherits `sourceMapping` as the default `classNameMapping`; it falls back to `obfuscated` only when neither value is provided.
- `find-mapping` accepts short class ids such as `dhl` only when `sourceMapping="obfuscated"`. Other class lookup paths still validate class names as fully-qualified.
- `find-mapping` still rejects the public namespace name `official`, but upstream Tiny files that use `official` internally are now bridged to the supported `obfuscated` graph automatically.
- `get-class-api-matrix` now uses the explicit `classNameMapping` as its base namespace even when an obfuscated identity is also available.
- `inspect-minecraft task="class-overview" | "search" | "class-source" | "class-members"` needs artifact context for plain `subject.kind="search" | "class" | "file"` inputs. Use `subject.kind="workspace"` when you want the tool to resolve the artifact for you. Invalid combinations return `ERR_INVALID_INPUT` with a retryable `suggestedCall`; when artifact context is the only missing piece, the suggested retry preserves the requested task.
- Workspace `inspect-minecraft` flows now treat `partial-source-no-net-minecraft` as a recoverable condition: `task="class-overview"` and class-like workspace `task="search"` can confirm vanilla classes through binary-backed symbol lookup, while workspace `task="list-files"` marks the response as partial and includes follow-up guidance.
- `analyze-mod` and `validate-project` keep their structured `subject` contracts; stale string-subject or domain-include payloads now fail with `ERR_INVALID_INPUT` plus a retryable `suggestedCall` instead of a dead-end schema error.
- `scope="loader"` now means runtime artifact discovery. Fabric/Quilt flows may still fall back to merged Loom artifacts, while Forge/NeoForge validation can resolve transformed loader runtime jars.
- `remap-mod-jar` requires Java and supports Fabric/Quilt inputs. Mojang-mapped inputs can only be copied through `targetMapping="mojang"`.
- `search-mod-source` enforces `query.length <= 200` and `limit <= 200`.
- `get-registry-data` can return names and counts only with `includeData=false`, or clip detailed payloads with `maxEntriesPerRegistry`.
- `validate-mixin` defaults `reportMode="summary-first"`: it hoists shared provenance/warnings/incomplete reasons and drops per-result `resolvedMembers`/`toolHealth`/`structuredWarnings`. Pass `reportMode="full"` (or `explain=true`) to get per-result `resolvedMembers`/`toolHealth`/`resolutionTrace` back. For the leanest output combine `includeIssues=false`, `reportMode="compact"`, and `warningMode="aggregated"`.
- `validate-mixin` top-level failures expose `failedStage` as a first-class field on the serialized `error` envelope (alongside `code`, `hints`, `suggestedCall`) — one of `"input-validation" | "resolve" | "mapping-health" | "parse" | "target-lookup"`. Branch on that before inspecting `message` to recover automatically (e.g. retry `resolve` failures with `scope="vanilla"`, retry `target-lookup` failures with a different `mapping`). Nested errors that already carry a `failedStage` are preserved so upstream tags (e.g. from `resolve-artifact`) surface unchanged.
- `validate-mixin` per-result `quickSummary` appends `Scope fell back from "<requested>" to "<applied>" (<reason>).` when `provenance.scopeFallback` is set and `Mapping health degraded: <degradations>.` when `toolHealth.overallHealthy === false`. Clean validations keep the original one-line summary; the extra notes only attach when the pipeline actually fell back or detected a degraded mapping.
- `mapping-health` stays lightweight for `obfuscated` and `mojang` requests. It avoids full Tiny mapping graph loads unless the caller requests `intermediary` or `yarn`, where Tiny namespace availability is part of the health check.
- `validate-mixin` runs each stage (`resolve` / `mapping-health` / `parse` / `target-lookup`) against an independent soft-deadline. When the `target-lookup` stage exhausts its budget mid-loop, completed targets stay in `targetOutcomes` with `status: "ok"` (and `slowTarget: true` plus `elapsedMs` when the per-target soft cap was exceeded) while remaining targets land as `status: "deferred-budget"`. The summary then carries `targetsDeferredBudget` and `degradedReason: "stage-budget"`, and `validationStatus` is promoted to `"partial"`. If the budget is exhausted before the first iteration, `targetOutcomes` stays empty, `targetsDeferredBudget` is omitted, and `degradedReason: "stage-budget-pre-target"`.
- Empty Mixin configs are treated as warning-only discovery results with `summary.total=0` instead of invalid input; malformed JSON still returns `ERR_INVALID_INPUT`.

### verify-mixin-target

Single-call probe for "does this owner / member exist, and which `@Shadow` / `@Accessor` / `@Invoker` should the mixin use?" Use it before authoring a mixin to avoid round-tripping through `find-class`, `get-class-members`, and `validate-mixin`.

Input shape:

- `owner` — fully-qualified class name (e.g. `net.minecraft.world.entity.LivingEntity`).
- `member` — discriminated by `kind`. `{"kind":"method","name":"tick","descriptor":"()V"}` or `{"kind":"field","name":"airSupply"}`. `descriptor` is optional; when omitted, the tool returns every overload (methods) or any matching name (fields).
- `mixinMemberName` (optional) — the caller-authored mixin field/method name. Drives the `accessorAdvice` rule table when the target is private (`getXxx` / `setXxx` → `@Accessor`, `invokeXxx` / `callXxx` → `@Invoker`).
- `target` — same shape as `resolve-artifact.target`: `{"kind":"version","value":"1.21.10"}`, `{"kind":"workspace"}` (uses `projectPath`), `{"kind":"dependency","group":"...","name":"..."}`, `{"kind":"coordinate","value":"..."}`, or `{"kind":"jar","value":"..."}`.
- `mapping`, `sourcePriority`, `projectPath`, `scope`, `preferProjectVersion`, `strictVersion` — same semantics as `resolve-artifact`.

Output shape:

- `exists: boolean` — true when at least one member matches by name (and descriptor when supplied).
- `resolvedOwner: { className, mapping }` — echoes the resolved namespace.
- `matches: Array<{ name, descriptor, accessFlags[], javaSignature? }>` — every member matching the request.
- `candidates: Array<{ name, descriptor, reason }>` — populated when `exists=false`. Two reasons are emitted: `"name match, descriptor … differs from requested …"` (descriptor mismatch) or `"name … is similar to requested …"` (Levenshtein-near misses, sourced from the same `suggestSimilar` helper used by the Mixin validator).
- `accessorAdvice` — annotation-recommendation block. Emitted only when `matches.length === 1` (a single unique match): descriptor-mismatch / nearest-neighbor / candidate-only responses carry no advice (rule table cannot be applied against an unmatched member), and ambiguous overload responses (descriptor omitted, multiple `matches[]`) also carry no advice (a single rule cannot describe several different targets). Re-call with an explicit `descriptor` to disambiguate the overload.
- `provenance: { artifactId, mappingNamespace, workspaceResolution?, dependencyResolution? }` — the workspace / dependency resolution shape from `resolve-artifact` is preserved when `target.kind` was `workspace` or `dependency`.

`accessorAdvice` rule matrix (top-down; first match wins):

| # | `member.kind` | target visibility | `mixinMemberName` regex | `suggestedAnnotation` |
|---|---|---|---|---|
| 1 | `field` | `public` / `protected` | (any) | `"@Shadow"` (no `@Accessor` needed for outside access, but the mixin still needs `@Shadow` to reference the field) |
| 2 | `method` | `public` / `protected` | (any) | `"@Inject-only"` (target already visible to mixin; no `@Invoker` needed) |
| 3 | `field` | `private` / `package-private` | `^get[A-Z]\w*$` / `^set[A-Z]\w*$` / `^is[A-Z]\w*$` | `"@Accessor"` (target field name inferred via prefix removal) |
| 4 | `field` | `private` / `package-private` | (anything else, including absent) | `"@Shadow"` (or `"@Shadow @Final"` when target is `final`) |
| 5 | `method` | `private` / `package-private` | `^invoke[A-Z]\w*$` / `^call[A-Z]\w*$` | `"@Invoker"` |
| 6 | `method` | `private` / `package-private` | any other non-empty value | `"@Shadow"` |
| 7 | `method` | `private` / `package-private` | (absent) | `null` + `candidates: [@Shadow, @Invoker]` |

`"@Inject-only"` is a pseudo-tag, NOT a real Mixin annotation, and only applies to visible (`public`/`protected`) **methods**. It signals "no `@Invoker` is needed because the target method is already accessible to the mixin"; use `@Inject` to hook it, or `@Shadow` to call it directly from mixin code. A visible **field** gets a concrete `"@Shadow"` recommendation instead — no `@Accessor` is needed to read/write it from outside, but mixin code still needs `@Shadow` to reference it. `accessorAdvice.exampleSnippet` is a deterministic Java fragment built from the recommendation; the tool does NOT compile-check the snippet — run a Gradle build before committing.

Errors:

- Owner not found returns `ERR_CLASS_NOT_FOUND` with `details.suggestedCall.tool === "find-class"` and `details.suggestedCall.params.artifactId` pre-filled to the resolved artifact, so the caller can immediately re-probe with the correct simple-name query.
- Workspace targets without a detectable Minecraft version still raise `ERR_WORKSPACE_VERSION_UNRESOLVED` (inherited from `resolve-artifact`).
- Namespace mismatch: when an explicit `mapping` argument differs from the resolved artifact's `mappingApplied` and `autoRemap` is not set, the tool raises `ERR_NAMESPACE_MISMATCH` instead of a silent `ERR_CLASS_NOT_FOUND` / `exists:false`. `details` carries `owner`, `requestedMapping`, `mappingApplied`, `artifactId` and a `nextAction`. With `autoRemap: true` the tool instead translates `owner`, `member.name` and `descriptor` from `mapping` into the artifact's namespace through `find-mapping` and adds a `warnings` entry naming the translation. Translation needs a Minecraft version (a `version` target, or a target that resolves one) and raises `ERR_INVALID_INPUT` without one; an owner or member it cannot translate raises `ERR_NAMESPACE_MISMATCH`. When only the descriptor cannot be translated, the member is matched by name and a warning says so.

### compare-minecraft migration-overview: `libraries`

`compare-minecraft` with `task="migration-overview"` includes a `migration.libraries` block (the `migration` block is returned at `detail: "standard"` or `"full"`) diffing the two versions' per-version JSON `libraries` array — the dependencies Minecraft itself ships with (LWJGL, Netty, etc.), which a class or registry diff cannot see. This is how a library swap such as LWJGL's GLFW binding being replaced by SDL surfaces, instead of silently changing behavior underneath a migration.

Entries are keyed by `group:artifact` (the Maven coordinate with the version, any trailing `@extension`, and any platform `natives-*` classifier stripped), so a routine version bump or the same library's per-platform native jars never read as churn. Comparison is order-independent: it does not matter what order the two sides' `libraries` arrays list their entries in, and a single side may legitimately carry more than one version for the same `group:artifact` key (Mojang manifests can list different versions on different platform rules) — every version seen on a side is tracked, not just the first.

- `migration.libraries.added` / `removed` — sorted arrays of `group:artifact:<versions>` strings for libraries present on only one side, where `<versions>` is the sorted, comma-joined list of distinct versions seen for that key on that side. A key with one version renders as before (e.g. `"org.libsdl:sdl3:3.2.0"`); a key with several platform-specific versions renders as e.g. `"g:a:1,2"`.
- `migration.libraries.addedCount` / `removedCount` — counts of the above.
- `migration.libraries.versionChangedCount` — count of `group:artifact` keys present on both sides whose version sets differ. No list is included.
- `summary.counts.librariesAdded` / `librariesRemoved` — the same added/removed counts, promoted into the top-level summary, so they are visible at `detail: "summary"` too.

The block is entirely additive: `summary.status` and `migration.impact` remain computed only from class and registry signals, unaffected by library changes. When per-version library details cannot be fetched (offline, or a fetch failure), the `libraries` block is omitted and a warning is added to the response instead of failing the whole `migration-overview` call. Fetching both sides' library lists is itself bounded by a short internal deadline (5 seconds, not configurable via any tool parameter or environment variable) so that an unreachable network — e.g. right after a restart, when class/registry data is already served from cached jars — cannot stall `migration-overview` for the full underlying fetch timeout; a deadline expiry is reported the same way as any other library-fetch failure: the block is omitted and a "timed out" warning is added. The library fetch already in flight is left to finish in the background and may still warm the cache for a later call.

### Batch lookup contract

`batch-class-source`, `batch-class-members`, `batch-symbol-exists`, and `batch-mappings` share one envelope. Each call sends a fixed shortlist (1..50 entries) and receives a per-entry result plus an aggregate summary. The batch runs `entries.length` underlying calls but resolves the shared artifact ONCE (where applicable), so the round-trip cost is `1 resolve + N per-entry` rather than `N × (resolve + per-entry)`.

Common input fields:

- `entries: Array<...>` — 1..50 per-entry payloads. Tool-specific shape (see each subsection).
- `concurrency: number` (1..8, default 4) — passed to the worker pool. Above 8 is rejected with `ERR_INVALID_INPUT` (`fieldErrors[0].path === "concurrency"`).
- `failFast: boolean` (default `false`) — when `true`, the first per-entry error sets an abort flag. Workers that have not yet picked up an entry short-circuit with `error.code === "ERR_BATCH_ABORTED"`. **In-flight workers continue to completion** — they are not cancelled (no AbortSignal wiring). Already-completed `ok` entries are still returned in `results`.
- `detail: "summary" | "standard" | "full"` (default `summary`) + `include[]` — applies the same per-tool projection the corresponding single tool applies at that detail level to each entry's `result`. `detail: "summary"` matches the old `compact: true` per-entry shape; `detail: "full"` matches the old `compact: false` (byte-identical to the single tool's full output).
- Per-tool shared inputs (`target`, `mapping`, `projectPath`, `version`, etc.) follow the same shape as the matching single tool. On `batch-class-source` and `batch-class-members`, `target` additionally accepts `{ "kind": "artifact", "artifactId": "..." }` to reuse an already-resolved artifact instead of resolving one — the same reuse shape `get-class-source` / `get-class-members` accept, and the exact shape their own per-entry `suggestedCall` proposes for a retry (see the table below). When `target.kind` is `"artifact"`, the shared `resolveArtifact` call is skipped entirely: `summary.sharedArtifactProvenance` is omitted (no provenance is invented for a reused artifact), and an unknown `artifactId` surfaces per-entry with the same `ERR_SOURCE_NOT_FOUND` a single-tool call would raise, rather than aborting the batch.

Resource behavior: `concurrency` limits per-entry dispatch for one batch call. Within one MCP server process, entries or calls that need the same artifact index or decompiled fallback share the in-flight rebuild by `artifactId`. Separate MCP server processes sharing the same cache are not coordinated by this process-local guard.

Common output:

```json
{
  "results": [
    {
      "index": 0,
      "status": "ok",
      "result": { ... single-tool-result-shape ... },
      "warnings": ["..."],
      "durationMs": 12.34
    },
    {
      "index": 1,
      "status": "error",
      "error": {
        "code": "ERR_CLASS_NOT_FOUND",
        "detail": "...",
        "suggestedCall": { "tool": "get-class-source", "params": { ... } }
      },
      "warnings": [],
      "durationMs": 5.6
    }
  ],
  "summary": {
    "total": 2,
    "ok": 1,
    "error": 1,
    "sharedArtifactId": "...",
    "sharedArtifactProvenance": { ... }
  }
}
```

Per-entry retry semantics: each `error.suggestedCall` proposes the **matching single tool**, never the batch tool itself. The retry mapping is fixed:

| Batch tool | Single tool retry |
|---|---|
| `batch-class-source` | `get-class-source` (with `target: { kind: "artifact", artifactId: <shared> }`) |
| `batch-class-members` | `get-class-members` (with `target: { kind: "artifact", artifactId: <shared> }`) |
| `batch-symbol-exists` | `check-symbol-exists` (with `version` derived from the resolved artifact) |
| `batch-mappings` | `find-mapping` (with `version` carried from the top-level batch input) |

Every per-entry `suggestedCall` is validated through the same `tool-schema-registry` gate as single-tool errors (see `## Errors → suggestedCall schema validation gate`).

If the **shared resolution itself** fails (e.g. `target.kind="version"` with an unknown version), the batch returns a top-level error envelope (no `results[]`). `failFast` does not apply because no entries ran.

#### batch-class-source

Read source for many classes against one shared resolved artifact. Per-entry: `{ className, mode?, startLine?, endLine?, maxLines?, maxChars?, outputFile? }`. Shared: `target`, `mapping`, `projectPath`, `scope`, `preferProjectVersion`, `strictVersion`, `allowDecompile`. Result shape per entry mirrors `get-class-source`. Duplicate `className` entries each run independently — no de-duplication.

#### batch-class-members

List members for many classes against one shared resolved artifact. Per-entry: `{ className, access?, includeSynthetic?, includeInherited?, memberPattern?, maxMembers? }`. Shared inputs match `batch-class-source`. Result shape per entry mirrors `get-class-members`, including the `status` field (`"ok"` / `"partial"` / `"members_unavailable"`).

#### batch-symbol-exists

Probe symbol existence for many entries against one shared Minecraft-version artifact. Per-entry: `{ kind: "class" | "field" | "method", name, owner?, descriptor?, nameMode?, signatureMode?, maxCandidates? }`. Shared: `target`, `mapping`, `projectPath`, `scope`, `preferProjectVersion`, `strictVersion`, `allowDecompile`. **`target.kind` is restricted to `"workspace"` or `"version"`** — `dependency` / `jar` / `coordinate` resolve to artifacts whose `provenance.version` is the library's own version (e.g. an Architectury or mod-loader version), NOT a Minecraft version, so querying the Minecraft mapping graph with that string would be a category error. The schema rejects the disallowed kinds with `ERR_INVALID_INPUT`. The shared Minecraft version is derived from `sharedArtifact.version` (version target) or `provenance.workspaceResolution.detected.minecraftVersion` (workspace target). When neither populates, the batch raises `ERR_WORKSPACE_VERSION_UNRESOLVED` at the resolution stage.

#### batch-mappings

Translate symbols across mapping namespaces with one shared Minecraft version. Per-entry: `{ kind, name, owner?, descriptor?, sourceMapping, targetMapping, signatureMode?, disambiguation?, maxCandidates? }`. Shared: top-level `version` (required) plus `sourcePriority` / `projectPath`. Per-entry `version` is rejected with an `unrecognized_keys` zod issue; the batch shape is intentionally single-version. There is no shared artifact resolution — each entry hits the mapping graph directly — so `summary.sharedArtifactId` is omitted.

### Migration Notes

- `inspect-minecraft` covers the version, artifact, class, file, and search workflows of `list-versions`, `resolve-artifact`, `get-class-source`, `get-class-members`, `search-class-source`, `get-artifact-file`, and `list-artifact-files`.
- `analyze-symbol` covers the symbol mapping, existence, lifecycle, workspace, and API overview workflows of `find-mapping`, `resolve-method-mapping-exact`, `check-symbol-exists`, `trace-symbol-lifecycle`, `resolve-workspace-symbol`, and `get-class-api-matrix`.
- `analyze-symbol task="lifecycle"` accepts `fromVersion`/`toVersion`/`maxVersions`/`includeTimeline`/`includeSnapshots` (lifecycle-only; rejected on other tasks). The legacy `version` field is a back-compat alias for `toVersion` (range end). The default scan window is the service default of 120 versions (max 400); pass `maxVersions: 5` for the old narrow window. Use `trace-symbol-lifecycle` directly only for parity with the expert tool.
- `analyze-symbol` `subject.kind` accepts `"symbol"` to auto-detect the concrete kind from the selector (owner+descriptor ⇒ method, owner only ⇒ field, otherwise ⇒ class); the inferred kind is surfaced as a warning. For `task="api-overview"` the inferred kind is always class.
- `compare-minecraft` covers the version-pair, class diff, registry diff, and migration-summary flows of `compare-versions`, `diff-class-signatures`, and `get-registry-data`.
- `analyze-mod` covers the metadata-first mod inspection and safe remap preview/apply flows of `analyze-mod-jar`, `decompile-mod-jar`, `get-mod-class-source`, `search-mod-source`, and `remap-mod-jar`. In `META-INF/mods.toml`, `modLoader="lowcodefml"` is shared by Forge and NeoForge and is classified as Forge; NeoForge requires a NeoForge loader signal or `META-INF/neoforge.mods.toml`.
- `analyze-mod` `task="members"` (subject `{ kind: "class", jarPath, className }`) reads a mod class's constructors/fields/methods (all access levels, including private and protected) straight from bytecode — no decompiler runs on this path, unlike `task="class-source"` which costs a full decompile. Responses mark `extractionMethod: "bytecode-only"`; a class missing from the jar returns `ERR_CLASS_NOT_FOUND`.
- `validate-project` covers workspace summaries and the direct Mixin, Access Widener, and Access Transformer validation of `validate-mixin`, `validate-access-widener`, and `validate-access-transformer`.
- `validate-project task="project-summary"` discovers mixins and access wideners by default. Add `discover: ["access-transformers"]` when you also want Access Transformer files included in the workspace summary.
- `validate-project task="project-summary"` infers an omitted `version` from `gradle.properties` (`minecraft_version`, `mc_version`, or `minecraftVersion`) and adds the warning `version was inferred from the workspace: <version> (source: projectPath:gradle.properties (<projectPath>)).`; the run then behaves exactly like one with `preferProjectVersion: true`. An explicit `version` is used as given unless `preferProjectVersion: true` is also set, which replaces it with the detected project version. The resolved version is passed to every discovered Mixin, Access Widener, and Access Transformer check.
- `preferProjectVersion: false` turns inference off. Without a `version`, the summary then returns `status: "blocked"` with the headline `project-summary requires version or preferProjectVersion=true.` and a `summary.nextActions` retry that sets `preferProjectVersion: true`.
- When inference finds no version and discovery found files, the summary returns `status: "blocked"` with the headline `Could not resolve Minecraft version for discovered workspace validators.` Its `summary.nextActions` entry carries `version: "<minecraft-version>"`; replace the placeholder with the project's Minecraft version before retrying.
- When discovery finds no files, the summary keeps `status: "ok"` but reports `Nothing to validate: no <kinds> were found.` as the headline, where `<kinds>` names only the file kinds `subject.discover` searched, and adds a `warnings` entry beginning `Nothing was validated:`. An `"ok"` status alone therefore does not mean any file passed validation.
- `validate-project task="project-summary"` returns an additive `tasks` field alongside the existing aggregate `result.summary` / `result.project` blocks. The headline `result.summary.status` is unchanged; the new field reports per-probe status so a `status: "blocked"` headline still preserves which probes succeeded.

Real mapping failures still produce warnings. Loader-runtime identity behavior, runtime-selection guards, per-entry access evidence, and the stored namespace labels in `provenance` retain their existing meaning.
- `manage-cache` covers cache inventory and safe cleanup. Use `executionMode="preview"` before `executionMode="apply"`.
- Replace `resolve-artifact` `targetKind` and `targetValue` with `target: { kind, value }`.
- Replace `get-class-source` and `get-class-members` top-level `artifactId`, `targetKind`, and `targetValue` with `target: { kind, value }` (same shape as `resolve-artifact`) or `target: { kind: "artifact", artifactId }`. ## Typed NBT document shape

`json-to-nbt` and `nbt-apply-json-patch` take a `typedJson` argument whose 8.x input schema accepts any value, so the required shape is documented here. A `typedJson` that does not match is rejected with `ERR_NBT_INVALID_TYPED_JSON`. The catalog tools `nbt-encode` and `nbt-patch` take the same document as `typedJson`, and `nbt-decode` returns one.

A document is:

```jsonc
{
  "rootName": "Level",            // string; the NBT root compound's name (may be "")
  "root": { "type": "compound", "value": { /* nodes */ } }
}
```

Every node is `{ "type": <nbt-type>, "value": <payload> }`, where `<nbt-type>` is one of `byte`, `short`, `int`, `long`, `float`, `double`, `byteArray`, `string`, `list`, `compound`, `intArray`, `longArray`. Payloads by type:

| `type` | `value` | Notes |
| --- | --- | --- |
| `byte` / `short` / `int` | number | Integer, in the JVM range for that width (`byte` is signed, −128..127). |
| `long` | **string** | Decimal digits, `-9223372036854775808`..`9223372036854775807`. Never a JSON number. |
| `float` / `double` | number, or the strings `"NaN"` / `"Infinity"` / `"-Infinity"` | A raw non-finite JSON number is rejected; use the string sentinels. |
| `string` | string | |
| `byteArray` / `intArray` | number[] | Each element must fit the element width. |
| `longArray` | string[] | Same decimal-string rule as `long`. |
| `list` | node[] | Also carries `"elementType"`: any node type, and every element's `type` must equal it. `"end"` is allowed only for an empty list. |
| `compound` | object of name → node | Keys are the NBT tag names. |

Rejections name the offending node twice: `error.fieldErrors[0].path` is the RFC6901 JSON pointer into the document (for example `/root/value/health/value`, `typedJson` when the whole document is wrong), and `error.hints` states the expected and received types plus this shape. `error.exampleCalls[0]` points at `nbt-to-json`, which produces a document this format accepts from any real NBT payload — the reliable way to obtain a valid `typedJson` to edit. Catalog replies offer the same call as a `template: true` `nbt-decode` call in `meta.nextActions`.

## Errors

`ProblemDetails.code` may carry the codes below in addition to the existing tool-specific values.

- `ERR_WORKER_RESTART` — Synthetic envelope produced when the worker exits during `tools/call`, replacement startup or initialization replay fails, or live process-tree cleanup leaves the supervisor unable to start a worker. The response is a `CallToolResult` with `isError: true` and `structuredContent.error.code === "ERR_WORKER_RESTART"`. `structuredContent.meta.synthetic === true` and `meta.restart` records `tool` / `durationMs` / `lastStage` / `lastStageElapsedMs` / `lastStageMeta` / `exit` / `retryRecommendation` so the caller can decide whether to retry, narrow the input, clear caches, or report a bug. Non-`tools/call` requests receive the legacy raw JSON-RPC `-32603` envelope.
- `ERR_TOOL_TIMEOUT` — Synthetic `CallToolResult` produced only for the long-running tools, `validate-project`, `project-validate` and `mixin-validate`, when the supervisor-owned end-to-end deadline expires. The default is 120,000 ms and includes supervisor queue time. `meta.timeout.phase` is `"queue"` when the call expired before dispatch and `"running"` after dispatch. A queue timeout does not restart the worker; a running timeout isolates the worker process tree, initiates replacement, and sets `meta.timeout.workerRestartInitiated: true`. Cancellation suppresses the timeout result while retaining the deadline for worker cleanup. For a catalog tool, `error.detail` and `meta.timeout.tool` name it, and the retry (the same call) is in `meta.nextActions` instead of `error.suggestedCall`; it is left out when redaction changed the arguments. The same holds for an `ERR_WORKER_RESTART` reply to a catalog call, whose `meta.restart.tool` names it and whose hints name no 8.x input.
- `ERR_MIXIN_PARSE_FAILED` — Reserved code for `validate-mixin` parse-stage failures in single / inline mode. Today the runtime parser is permissive (no hard parse failure path), but emitting this code keeps the contract stable for future strict-parse modes.
- `ERR_STAGE_BUDGET_PRE_PARSE` — Raised when a pre-parse stage (`resolve`, `mapping-health`, or `parse` itself) exhausts its independent soft-deadline before validation can proceed. The error carries `failedStage: <stage name>`, `meta.stageBudgetExhausted: true`, and the `budgetMs` / `elapsedMs` for the offending stage. Recovery: shrink `mixinConfigPath` (e.g. validate one config file at a time) or set `MIXIN_STAGE_BUDGETS_OFF=1` to disable budgets for diagnostic reruns.
- `ERR_WORKSPACE_VERSION_UNRESOLVED` — Raised by `resolve-artifact`, `get-class-source`, `get-class-members`, and `inspect-minecraft` (workspace subject, every artifact-context task) when `target.kind="workspace"` cannot detect a Minecraft version from `gradle.properties`. Both `strict: true` and `strict: false` raise; `details.strict` records which value was supplied. The error carries `details.projectPath` and `exampleCalls` with `target: { kind: "version", value: "<your-mc-version>" }` so the caller can fall back to an explicit version target.
- `ERR_DEPENDENCY_VERSION_UNRESOLVED` — Raised by `resolve-artifact`, `get-class-source`, and `get-class-members` (not `inspect-minecraft`, whose target schema has no `"dependency"` kind) when `target.kind="dependency"` cannot infer a version from `gradle.properties` or `~/.gradle/caches/modules-2/files-2.1/<group>/<name>/`. Multiple non-snapshot entries in modules-2 also raise this error: the synthesizer refuses to pick without project-specific evidence, sets `details.ambiguous=true`, and lists the cached versions in `details.candidatesSeen`. The error carries `details.attempts` (the gradle.properties keys that were probed) plus `exampleCalls` with `target: { kind: "dependency", group, name, version: "<your-version>" }`.

### Error classification: `retryClass` and `issueOrigin`

Every `ProblemDetails` built from a caught error carries both fields, on every access path that publishes one — the tool result envelope, `batch-*` entries, and `mc://` resource reads. They are INDEPENDENT axes and must be read separately: `retryClass` answers "what recovery posture should I take?", `issueOrigin` answers "whose failure is this?". Two publishers carry both fields without a caught error behind them, so neither can ever show a per-site override: the batch-aborted sentinel, synthesized by `buildBatchAbortedProblem` from `ERR_BATCH_ABORTED` alone, and the synthetic supervisor replies for `ERR_TOOL_TIMEOUT` and supervisor queue overflow, which write the pair as fixed literals. The synthetic `ERR_WORKER_RESTART` reply carries neither field; read its recovery posture from `meta.restart.retryRecommendation`.

- `retryClass` — `"input"` (the request is wrong; fix it, then retry), `"permanent"` (the identical call cannot succeed; do not retry), `"transient"` (a temporary failure; one retry is reasonable — also the value for any code not explicitly classified), `"server"` (an internal defect; treat like `permanent` for retry posture), `"environment"` (a server capability is missing — Java, decompiler, remapper — retrying will not help until it is installed). Derived from the error `code` alone. There is no per-call override and none is planned: narrowing what an existing code publishes would itself be a wire contract change.
- `issueOrigin` — `"code_issue"` (the request is wrong or names something that does not exist; fix the request), `"tool_issue"` (the tool could not produce a result for otherwise valid input), `"environment"` (the same missing-capability meaning as above). It has a per-throw-site override, so the same `code` can publish different values on different requests. Read it from each response; never assume a fixed value per code.

Because only `issueOrigin` is overridable, the two axes can disagree, and one pairing does so by design. `ERR_CONTEXT_UNRESOLVED` raised on an artifact that carries no binary jar publishes `retryClass: "input"` together with `issueOrigin: "tool_issue"` whenever the tool, not the caller, chose that artifact. `issueOrigin` is the one to act on there: replaying the same artifact cannot produce a different answer, whatever `retryClass` suggests. Which requests count as tool-chosen:

- `get-class-members` — every `target.kind` except `"jar"`, `{ "kind": "artifact", "artifactId": ... }` included. An `artifactId` is an opaque handle: its holder cannot tell from it whether the artifact has a binary jar, and cannot re-resolve it either, since `resolve-artifact` does not accept an `artifactId`. Only `target: { "kind": "jar", ... }`, where the caller named the exact jar, reports `issueOrigin: "code_issue"`.
- `batch-class-members` — same rule, applied once to the shared target and repeated on every failed entry, including its own `{ "kind": "artifact", "artifactId": ... }` variant: only `"jar"` reports `code_issue`.
- `inspect-minecraft` `task="class-members"` — same rule once more: only a subject whose artifact reference is `target: { "kind": "jar", ... }` reports `code_issue`. A subject naming a resolved artifact (`{ "type": "resolved-id", "artifactId": ... }`) reports `tool_issue`, matching the equivalent `get-class-members` target: it is the same opaque handle from an earlier resolve, and wrapping it in a subject does not give the caller any way to vet the artifact's binary jar.
- `verify-mixin-target` — the same rule on its own `target`: the tool reads the target's members from bytecode, so every `target.kind` except `"jar"` reports `tool_issue`. Its target schema has no `"artifact"` kind at all (unlike `batch-class-members`), so only `"jar"` reports `code_issue`.

To check whether an artifact carries a binary jar before retrying, call `cache-manage` with `action: "list"`, `cacheKinds: ["artifact-index"]` and `selector: { "artifactId": ... }`, the call a catalog reply's hint names. It returns the entry with its `meta` at every call, and `meta.binaryJarPath` is that artifact's stored path — read from the same row the members lookup reads, and absent when the row has none. With the 8.x tools, the hint names `manage-cache` with `action: "inspect"`, `selector: { "artifactId": ... }` and `include: ["cacheEntries"]`, whose `cacheEntries` block reports the same field. The `include` is not optional there: `manage-cache` defaults to `detail: "summary"`, which drops `cacheEntries` entirely, so without it the reply never shows the field (`detail: "standard"` or `"full"` opts the block back in as well).

### `suggestedCall` schema validation gate

Every `ProblemDetails.suggestedCall` payload an agent receives is validated against the registered `zod` schema for the named tool BEFORE it leaves the process. Invalid payloads (e.g. a `target.value` that holds a JSON-stringified inner target — the bug in v3 chains where round-tripping the suggestion produced `ERR_INVALID_INPUT`) are dropped from the published envelope.

The gate drops a primary suggestion for TWO reasons, and both are reported the same way. Either the payload failed schema validation, or — the common case — the guidance handed the gate a TEMPLATE whose values are still `<...>` placeholders, which is by design and never reached the schema at all. Whenever a primary suggestion is dropped and no `suggestedCall` survives, `error.hints` gains the literal sentence `"suggested call payload failed schema validation; using fallback examples"`. Read that sentence as "no directly-replayable suggestion is being published", not as evidence that a schema check failed: it is emitted for the placeholder-template case too. It also does NOT mean the envelope is empty of guidance — it coexists with `exampleCalls[]`, and in practice every recorded tool-contract envelope that carries the sentence also carries `exampleCalls`. Branch on the presence of `suggestedCall` / `exampleCalls`, never on this text.

The wording is deliberately retained verbatim even though it is inaccurate for the placeholder case: it is frozen inside the pre-migration envelope evidence under `tests/fixtures/premigration/` (six tool-contract envelope samples and four ProblemDetails goldens), which was captured against an untouched pre-migration build and cannot be re-recorded. Rewording the sentence — or splitting the single drop marker into two — breaks those goldens with no way to regenerate them. Fix the reader, not the string.

The optional `error.exampleCalls?: Array<{ tool: string; params: Record<string, unknown>; reason: string }>` field carries one or more alternative payloads when the primary is dropped. Each entry is **schema-valid**: it names a real tool and passes that tool's registered schema, so the argument names and types are right. It is NOT necessarily replayable as-is. Examples are explicitly permitted to be TEMPLATES — the same `<...>` placeholders that cause a primary `suggestedCall` to be dropped are allowed to survive here, because an example's job is to show the shape when no fillable suggestion exists. Recorded envelopes carry such templates today (the `analyze-mod` sample publishes `subject.jarPath: "<mod-jar-path>"`, and the typed-NBT recovery example publishes `nbtBase64: "<base64-encoded-nbt-payload>"`, which the NBT pipeline would reject as invalid base64 if sent verbatim). Scan the params for `<...>` values and fill them before sending; only `suggestedCall` is guaranteed placeholder-free.

`suggestedCall.params` is published **byte-identical** to the caller-supplied object — the gate validates emit-vs-drop only and never injects schema defaults into the published payload. Internal consumers that want the schema-normalized form read `validateToolParams(name, params).data` directly from `tool-schema-registry`.

## Meta fields

- `meta.deprecated` (replies of the deprecated 8.x tools only, success and error alike, including the supervisor's synthetic timeout, worker-restart and queue-overflow replies to them) — `{ replacedBy: string[], removeIn: "10.0.0" }`, in the JSON text and in `structuredContent`. `replacedBy` names the catalog tools that replace the tool; when `inspect-minecraft`, `analyze-symbol`, `compare-minecraft`, `analyze-mod` or `validate-project` is called with one of its `task` values, it names only the catalog tool for that task. `removeIn` is the earliest release that removes the 8.x tools. Catalog replies never carry it, and neither does a reply to an 8.x tool name under `MCP_DEPRECATED_TOOLS=off`, which treats that name as an unknown tool. Each 8.x tool's `tools/list` entry carries the same block, with every replacement, as `_meta.deprecated`.
- `meta.restart` (synthetic worker-restart responses only) — emitted exclusively when the supervisor returns an `ERR_WORKER_RESTART` envelope. Shape: `{ tool, durationMs, lastStage, lastStageElapsedMs, lastStageMeta, exit: { code, signal }, retryRecommendation }`. `retryRecommendation` is one of `"narrow-query" | "clear-cache" | "report-bug" | "same-request"`, decided by the supervisor from `lastStage`, `exit.signal`, and the recent restart cadence (3 restarts within 60 s of the same tool → `"report-bug"`).
- `meta.timeout` (`ERR_TOOL_TIMEOUT` only) — exact shape: `{ tool: "validate-project" | "project-validate" | "mixin-validate", phase: "queue" | "running", durationMs, deadlineMs, lastStage, lastStageElapsedMs, lastStageMeta, redactedToolArgs, redactedToolArgsModified, retryRecommendation, workerRestartInitiated }`. Stage and argument diagnostics use the supervisor's bounded redaction rules. `workerRestartInitiated` reports initiation only; it does not claim that replacement startup or initialization replay completed.
- `meta.queue` (supervisor queue overflow only) — `{ reason: "supervisor-request-queue", maxQueued: 2, queuedCount: 2 }`. The FIFO retains at most two total worker-bound requests; a queued long-running barrier (`validate-project`, `project-validate`, `mixin-validate`) consumes one slot, while a running barrier is outside the FIFO. Overflowing `tools/call` receives a synthetic `ERR_LIMIT_EXCEEDED` result. An overflowing non-tool request receives raw JSON-RPC `-32000` with message `"MCP supervisor request queue is full."`; notifications do not consume slots.
- Replacement startup/replay uses a 10–30 second internal watchdog and bounded retry backoff. Successful replay releases queued work. Spawn, pre-ready, replay, or watchdog failure terminalizes queued requests with the existing worker-restart response shapes. At the two-slot live-generation cap, new worker-bound requests, including `initialize`, fail immediately instead of entering the FIFO; notifications that cannot be delivered are emitted as structured supervisor warnings and dropped. Tree-cleanup helper attempts are bounded to five seconds so recovery and shutdown cannot wait forever on `taskkill` or an equivalent platform operation. On POSIX, `ESRCH` while signaling the saved process group means the group is already gone and is treated as completed cleanup. When a worker exits on its own (a crash or an external kill), the supervisor also signals that worker's process group on POSIX, so descendants such as a Java process are not left running; this does not delay the replacement. On Windows, descendants of a worker that exited on its own are not reaped, because `taskkill /T` cannot walk a tree whose root has already exited.
- `meta.stageBudgetExhausted` (`ERR_STAGE_BUDGET_PRE_PARSE` errors only) — set to `true` to flag that the failure is budget-driven rather than a genuine resolve / mapping-health / parse error. Pair with `failedStage` and `error.detail` (`"Stage <name> exhausted budget before parse completed."`) for diagnostics. The companion fields `meta.budgetMs` (the stage budget that was exceeded) and `meta.elapsedMs` (the actual stage elapsed time) are emitted alongside it on the same envelope so callers can decide between retry, input-shrink (`mixinConfigPath`), or `MIXIN_STAGE_BUDGETS_OFF=1` rollback without parsing message text.
- `validate-mixin` batch-mode entries (`results[i]`, when invoked with `input.mode = "paths" | "config" | "project"`) preserve typed error metadata when an entry fails: optional `errorCode` (e.g. `"ERR_STAGE_BUDGET_PRE_PARSE"`) and `errorDetails` (the `failedStage` / `stageBudgetExhausted` / `budgetMs` / `elapsedMs` shape from the underlying AppError) sit alongside the legacy `error` string. The shape is additive — callers that only read `error` continue to see the same human-readable message.

| `artifact-metadata` | `mc://artifact/{artifactId}` | Metadata for a previously resolved artifact. Its `artifactSignature` field carries the artifact's identity signature: a bare 64-character sha256 hex digest of the identified jar's bytes, or that digest followed by `:decompile`. A client that pattern-matched the older `<mtimeMs>:<size>` shape no longer matches. |

`versions-list`, `runtime-metrics`, `find-mapping`, `find-member-mapping`, `class-source-json`, `class-members`, and `artifact-metadata` return structured JSON envelopes on success (`{ result, meta }`) and failure (`{ error, meta }`).

`class-source` and `artifact-file` keep raw text responses on success, but still return structured JSON errors on failure.

## Response Envelope

All tools return exactly one of:

- Success: `{ result: { ... }, meta: { requestId, tool, durationMs, warnings? } }`
- Failure: `{ error: { type, title, detail, status, code, instance, fieldErrors?, hints? }, meta: { requestId, tool, durationMs, warnings? } }`

`meta.warnings` is present only when there is a warning: on the catalog tools a list of `{ code, severity, message }`, on the 8.x tools a list of strings. The replies the server puts in place of a tool's reply (a long-running call that timed out, a worker restart, a full request queue) are failures whose `meta` has `synthetic: true`, `syntheticSource: "supervisor"` and `timeout`, `restart` or `queue` instead of `requestId`, `tool` and `durationMs` (see [Errors](#errors) and [Meta fields](#meta-fields)).

Tools may publish execution counters on `meta` alongside the fields above. The NBT tools use this: `nbt-apply-json-patch` surfaces `appliedOps`, `testOps`, and `changed`; `json-to-nbt` surfaces `outputBytes` and `compressionApplied`; `nbt-to-json` surfaces `inputBytes` and `compressionDetected`. The catalog NBT tools (`nbt-decode`, `nbt-encode`, `nbt-patch`) return these counters in `result` instead.

JSON resources follow the same `result/error/meta` pattern. Text resources return plain text on success.

The same JSON envelope is mirrored in MCP `structuredContent` for SDK-aware clients, and failures also set `isError=true`.

The application-level `meta` field above is distinct from protocol-level `_meta`. Modern-era protocol fields (`resultType`, `ttlMs`, `cacheScope`, and the `io.modelcontextprotocol/serverInfo` identity echo in result `_meta`) sit at the MCP protocol result level, outside the application envelope, and appear only for modern-era clients (see `## MCP Protocol Support`).

## MCP Protocol Support

The stdio server implements MCP protocol revision `2026-07-28` and keeps the legacy initialize-based protocol fully supported in the same process. One process serves exactly one era; the first valid era signal selects it.

### Era selection

- A process starts with no era selected.
- `initialize` selects the LEGACY era. Any `io.modelcontextprotocol/*` era-claim keys inside `initialize` `params._meta` are ignored for classification and stripped before the frame reaches the worker (other `_meta` keys pass through), so a hybrid client that attaches a modern claim to `initialize` still completes the legacy handshake.
- A request whose `params._meta` carries BOTH `io.modelcontextprotocol/protocolVersion` (string) and `io.modelcontextprotocol/clientCapabilities` (object) selects the MODERN era. Selection is shallow: the era signal is a shape check only. The version VALUE is validated by the SUPERVISOR on EVERY modern request, so an unsupported version string still locks modern and then answers `-32022` — on that request and on every later one, regardless of which method pinned the connection.
- The lock is one-way and survives internal worker restarts. There is no era-switch method; switching eras requires a fresh process (see the recovery sequence below).
- `server/discover` is era-neutral: it never selects an era. Per-state outcomes are in the rejection table.
- An ordinary request received before any era signal is rejected with `-32602` `data.kind: "missing_meta"`. A notification received before any era signal is consumed without a response and without forwarding.

### Legacy era (initialize handshake)

Supported protocol versions: `2025-11-25`, `2025-06-18`, `2025-03-26`, `2024-11-05`, `2024-10-07`. Each is echoed verbatim by `initialize`. Any other requested version negotiates down to `2025-11-25`.

The supervisor caches the completed `initialize` / `notifications/initialized` pair and replays it into a replacement worker before queued requests are released; replay failure is a startup failure (see `ERR_WORKER_RESTART` in `## Errors`).

The legacy wire contract is byte-compatible with the pre-migration (SDK v1) server, with these recorded exceptions:

- `tools/call` with `arguments` omitted reaches the application validator as `{}`. Three outcome arms: (a) input-free tools succeed (`get-runtime-metrics`); (b) required-field schemas answer per-field `ERR_INVALID_INPUT` (`analyze-mod`); (c) a `{}`-accepting schema whose handler requires input answers that tool's own handler-level ProblemDetails — `json-to-nbt` answers `ERR_NBT_INVALID_TYPED_JSON` (status 400, `isError: true`) instead of the pre-migration validation-layer `ERR_INVALID_INPUT`.
- Legacy `tools/list` entries omit the v1-only `execution: {"taskSupport":"forbidden"}` field (SDK v2 does not emit it). In both eras the 8.x tools are listed as deprecated aliases with minimal entries and the input schema `{ "type": "object" }`, and their replies add `meta.deprecated` (see [Tool catalog](#tool-catalog)); the inputs they accept are the 8.x inputs described in this reference. The frozen pre-migration listing entries in `tests/fixtures/premigration/tool-contracts/` are a historical record of what the SDK v1 server advertised.
- An unknown tool is answered immediately at the supervisor, before queueing: the reply bytes are identical to v1, but the reply consumes no queue slot and no worker round-trip, so reply ordering and queue-overflow outcomes can differ from v1 under concurrent load.
- The unmatched-resource-URI error keeps the raw JSON-RPC `-32602` code, but its message changed from the pre-migration `MCP error -32602: Resource <uri> not found` to `Resource not found: <uri>`, and the error carries a `data.uri` field (SDK v2 wording).
- The `initialize` result advertises `resources: { listChanged: false }` and `tools: { listChanged: false }`, where the pre-migration server advertised `true` for both. The suppression is deliberate and is NOT era-gated — both eras read one `getCapabilities()`, so gating it would leave one process advertising two different contracts; the reasoning is under the modern-era capability paragraph below.
- The `initialize` result adds `instructions`, after `serverInfo`: the primer for AI agents described under [Tool catalog](#tool-catalog), the same text `server/discover` carries. Every other byte of the `initialize` result is unchanged.

### Modern era (2026-07-28, stateless)

Modern clients never send `initialize`. Every request carries `params._meta`:

| `_meta` key | Requirement | Value |
| --- | --- | --- |
| `io.modelcontextprotocol/protocolVersion` | required | `"2026-07-28"` |
| `io.modelcontextprotocol/clientCapabilities` | required | object (for example `{}`) |
| `io.modelcontextprotocol/clientInfo` | optional | `{ name, version }` |

Recommended bootstrap probe (era-neutral — it never locks an era; per-state outcomes are under the rejection table):

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "server/discover",
  "params": {
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {}
    }
  }
}
```

The discover result carries `supportedVersions: ["2026-07-28"]` (the modern per-request set — the legacy matrix is advertised through `initialize` negotiation, not through discover), `capabilities`, `instructions` (the primer for AI agents described under [Tool catalog](#tool-catalog), the same text the legacy `initialize` result carries), the server identity in `result._meta["io.modelcontextprotocol/serverInfo"]`, `resultType`, and the cache fields. `capabilities` advertises `resources: { listChanged: false }` and `tools: { listChanged: false }`, in that key order, and the legacy `initialize` result advertises the same payload — the two eras never disagree. The `false` is a deliberate suppression, not an SDK default: the SDK advertises `listChanged: true` for any registered tool or resource surface unless the server overrides it, and this server never emits `notifications/tools/list_changed` or `notifications/resources/list_changed` — the tool and resource surface is fixed at process start by environment flags — and there is no way to subscribe to those notifications either (see `subscriptions/listen` below). Treat both lists as static for the lifetime of the process; re-read them only across a restart.

Probe fallback rule for clients: fall back to the legacy `initialize` handshake on ANY unrecognized probe error or on a probe timeout — never key the fallback to one specific error code. Back-to-back pipelining is safe: a modern-claim `server/discover` immediately followed by `initialize` in one stdin chunk is admitted atomically in stdin order — the discover is answered with a DiscoverResult, the initialize negotiates, and the process ends legacy-locked. One narrow exception: when the worker is down (restarting) as that pair arrives, the replayed `initialize` pins the replacement worker first and the queued discover is answered `-32601`; the any-error fallback rule covers this case.

Every modern result — tool calls, resource reads, list methods, `server/discover`, and supervisor-synthesized results — carries `resultType: "complete"` and echoes the same server identity as discover in `result._meta["io.modelcontextprotocol/serverInfo"]`. `input_required` is never emitted. Raw JSON-RPC error responses never carry result-only fields.

Absent modern surfaces: `prompts/list` is not advertised and answers `-32601`. `ping`, `logging/setLevel`, `tasks/list`, and `tasks/get` answer `-32601` in the modern era; legacy `ping` keeps its automatic `{}` pong. `subscriptions/listen` is intentionally absent in BOTH eras: no subscription capability is advertised — which is why `listChanged` is advertised as `false` above rather than `true` — the worker runs with `maxSubscriptions: 0`, the rejection is `-32601`, and it is non-retryable: there is no live update stream to wait for, and nothing would be pushed onto one. The server never sends `notifications/message`; logging goes to stderr.

### Cache metadata (modern era only)

Both `ttlMs` and `cacheScope` are returned by exactly these cacheable methods: `tools/list`, `resources/list`, `resources/read`, `resources/templates/list`, `server/discover`, and `prompts/list` were it exposed (it is not). This is the protocol's five-method cacheable list plus `server/discover` (SDK/schema default row). Values:

| Surface | `cacheScope` | `ttlMs` |
| --- | --- | ---: |
| `tools/list` | `private` | `0` |
| `server/discover` | `private` | `0` |
| `resources/list`, `resources/templates/list` | `private` | `3600000` |
| `mc://versions/list` read | `private` | `300000` |
| `mc://metrics` read | `private` | `0` |
| class source, artifact, mapping, member, and artifact-metadata reads | `private` | `60000` |
| any successful read whose content is a ProblemDetails failure envelope | `private` | `0` |

The ProblemDetails row takes precedence over the resource-class rows; otherwise an exact-URI row beats a class row. Legacy responses carry no cache fields, no `resultType`, and no protocol `_meta` identity echo.

### Version negotiation

| Client sends | Outcome |
| --- | --- |
| `initialize` with `2025-11-25`, `2025-06-18`, `2025-03-26`, `2024-11-05`, or `2024-10-07` | verbatim echo; legacy era |
| `initialize` with any other version string | negotiates down to `2025-11-25`; legacy era |
| modern `_meta` with `protocolVersion: "2026-07-28"` | served; modern era |
| modern `_meta` with any other version string | LOCKS modern, then answers `-32022` with `data: { supported: ["2026-07-28"], requested }` — retry with a version from `data.supported`; do NOT fall back to `initialize` (the process is already modern-locked and would answer `-32601` `era_conflict`) |

### Rejection and error table

`-32602` reaches clients in distinct shapes. Branch on `error.data.kind` when present; the remaining shapes are distinguished by message family (most are data-less; the resource-miss row carries `data.uri`):

| Producer | State / trigger | Method scope | Code | Discriminator |
| --- | --- | --- | --- | --- |
| supervisor | no era selected; request without a valid era signal | any non-`server/discover` request | `-32602` | `data.kind: "missing_meta"` with `data.missing[]` (plus `data.invalid[]` for wrong-typed keys); the message names both recovery paths |
| supervisor | modern-locked; claim-less request | any request, including `server/discover` | `-32602` | `data.kind: "missing_meta"`; the message names the required keys |
| worker (SDK) | modern-locked; shallow-valid claim with a deep-invalid `_meta` value | forwarded requests | `-32602` | data-less; message starts `Invalid _meta envelope for protocol revision 2026-07-28:` (pinned example: `Invalid _meta envelope for protocol revision 2026-07-28: Invalid input: expected object, received number`) |
| worker (SDK) | forwarded params-schema violation | both eras | `-32602` | data-less; a `tools/call` schema failure starts `Invalid tools/call request:`; the request never reaches the application validator |
| worker (SDK) | non-object `arguments`, MODERN era | `tools/call` | `-32602` | data-less; message starts `Invalid tools/call request:` |
| supervisor | present, non-object `arguments`, LEGACY era | `tools/call` | `-32603` | raw JSON-RPC error; message is the legacy JSON-encoded validation issue array (`invalid_type`, expected `object`, path `["params", "arguments"]`); intercepted before the worker |
| worker (SDK) | unmatched resource URI | `resources/read`, both eras | `-32602` | message `Resource not found: <uri>` with `data.uri` (the pre-migration server answered `MCP error -32602: Resource <uri> not found` without `data` — code unchanged, message family changed) |
| worker (SDK) | unknown tool, MODERN era | `tools/call` | `-32602` | raw JSON-RPC error (sanctioned modern contract; the modern era never had a v1 contract here) |
| supervisor | unknown tool, LEGACY era | `tools/call` | none | SUCCESSFUL `CallToolResult` with `isError: true`, text `MCP error -32602: Tool <name> not found`, and NO `structuredContent` key — the missing `structuredContent` is the discriminator against a genuine tool failure |
| supervisor | `initialize` that is not a valid MCP initialize request | `initialize` | `-32602` | `data.kind: "invalid_initialize"` with `data.required[]` and `data.eraSelected: false` — the era is NOT locked, so the client may retry a well-formed `initialize` or select the modern era instead |
| supervisor | modern-locked; `initialize` arrives | `initialize` | `-32601` | `data.kind: "era_conflict"`, `selectedEra: "modern"`, `requestedEra: "legacy"`, `supported[]` = all six versions |
| supervisor | legacy-locked; modern-claim request arrives | any modern-claim request | `-32600` | `data.kind: "era_conflict"`, `selectedEra: "legacy"`, `requestedEra: "modern"` |
| supervisor / worker | `subscriptions/listen` | both eras | `-32601` | plain `Method not found` (no data). Non-legacy states reject at supervisor admission; a modern-signal listen still era-locks first, and a claim-less listen in non-legacy states fails the envelope check with `-32602` before the method rejection |
| supervisor | modern request with an unsupported `protocolVersion` value | every modern request | `-32022` | `data.supported: ["2026-07-28"]`, `data.requested` |
| supervisor | queue overflow, non-`tools/call` request | requests | `-32000` | message `MCP supervisor request queue is full.` (`tools/call` overflow receives the `ERR_LIMIT_EXCEEDED` `isError` result instead — see `## Meta fields`) |

`server/discover` per state: a valid modern-claim discover never selects or changes the era. It receives a DiscoverResult in the unselected and modern-locked states; in the legacy-locked state it is forwarded to the legacy-pinned worker, which answers `-32601` (the probe's any-error fallback rule covers this). A claim-less discover: unselected → `-32602` `missing_meta`; modern-locked → `-32602` `missing_meta`; legacy-locked → forwarded → `-32601`.

Era-conflict messages embed a launcher-neutral recovery sequence: close this transport, terminate and respawn the configured server command as a fresh stdio process, discard or re-issue any pending request ids, then perform the wanted era's opening (`initialize` + `notifications/initialized`, or a request carrying the required `io.modelcontextprotocol/*` `_meta` envelope).

Notification variants: a modern-era notification without a valid claim (for example a claim-less `notifications/cancelled`) is never forwarded to the worker; it is dropped with a logged `supervisor.notification_dropped` warning and, like every notification, receives no response. Supervisor-side bookkeeping still applies: a claim-less cancellation still cancels ANY tracked in-flight request (not only `validate-project`), releasing its pending slot, its deadline timer, and the `validate-project` barrier if it held one, and the eventual worker response is suppressed per MCP cancellation semantics via the ordinary response-finality tombstone. An `initialize` in flight is the one exception — its handshake lifecycle owns that entry.

### Synthetic terminal responses and retry semantics

Supervisor-synthesized replies (queue overflow, worker restart, long-running tool timeout, startup failure — shapes in `## Errors` and `## Meta fields`) are FINAL for that request instance: a late worker answer for the same id is discarded, so a client sees exactly one response per id. A raw JSON-RPC `-32603` whose message begins "MCP supervisor failed to" belongs to the same class: the supervisor emits one when an internal fault stops it from admitting a request, dispatching a queued one, or handing a worker response back to the client, and it is terminal and discards the worker's own later answer in exactly the same way. One case where the supervisor deliberately sends nothing: when its own cleanup after such a fault cannot prove the request was removed, it reports and stands down rather than risk a second reply for one id. Only the long-running tools (`validate-project`, `project-validate`, `mixin-validate`) carry a deadline of their own, so any other request left in that state waits for the worker to exit. Retrying with the SAME id after a synthetic terminal reply is legal — the retry re-forwards and clears the finality bookkeeping. Era rejections synthesize no such finality (they answer without forwarding), and dropped notifications receive no response at all. Modern-era synthetic results are decorated like ordinary modern results (`resultType: "complete"` plus the identity `_meta` echo); legacy synthetic results keep the pre-migration shapes. In both eras a synthetic result for a call to a deprecated 8.x tool adds `meta.deprecated` (see [Meta fields](#meta-fields)).

### Framing

Standard framing is newline-delimited JSON-RPC (the MCP stdio standard). `Content-Length` header framing is a LOCAL, NONSTANDARD compatibility extension — it is not part of MCP. The reader auto-detects both and may switch mid-stream; every response, including synthetic replies and replies released after a worker restart, uses the framing of the request it answers. `MCP_MAX_FRAME_BYTES` bounds accepted frames (see `## Environment Variables`), and a header block is capped at 8 KiB.

A `Content-Length` header block ends at its FIRST EMPTY LINE. A header line ends at an LF, and a CR immediately before that LF belongs to the terminator, so all four combinations a peer can write — `\r\n\r\n`, `\n\n`, `\n\r\n` and `\r\n\n` — delimit the block, and no `\r\n\r\n` sequence inside the JSON body can be mistaken for one. An EXTRA empty line after that terminator is body, not header: the peer's declared `Content-Length` does not count it, so the body window opens two or three bytes early and normally runs off the end of the JSON. That is a body-parse failure, which is framing-fatal — the session ends and the frames behind it are lost. Such a frame is malformed, but the outcome is worth knowing: it is not recovered from. It is not certain to fail, either. The window is shifted rather than mis-sized, so a declared length that happens to count trailing whitespace can absorb the shift exactly and the frame is delivered normally; the reader never detects the extra blank line, only where the bytes fall.

### Adopted-policy note

The 2026-07-28 revision does not mandate specific mixed-era conflict rules or unselected-state behavior for one stdio process. The era-conflict codes, `missing_meta` rejections, one-way lock, and discover neutrality documented here are this server's adopted policy, pinned by the committed wire suites (`tests/stdio/stdio-supervisor-era-state.test.ts`, `tests/stdio/stdio-supervisor-era-wire.test.ts`, `tests/stdio/stdio-supervisor-era-lifecycle.test.ts`). If a future protocol revision defines normative rules for these cases, those rules supersede this policy.

Tooling note: `pnpm test:manual:stdio-smoke` runs against the production supervisor by default; its direct-worker bridge fallback mode bypasses the supervisor and therefore observes the worker-level raw `-32602` for unknown tools instead of the restored legacy `isError` envelope.

## Mapping Policy

### Namespace Definitions

| Namespace | Description |
| --- | --- |
| `obfuscated` | The runtime jar's names as shipped. On legacy versions these are Mojang obfuscated names such as `a`, `b`, `c`; on unobfuscated releases (`26.1+`) the runtime ships Mojang names, so `obfuscated` and `mojang` name the same classes |
| `mojang` | Mojang deobfuscated names from `client_mappings.txt` such as `net.minecraft.server.Main` |
| `intermediary` | Fabric stable intermediary names such as `net.minecraft.class_1234` and `method_5678` |
| `yarn` | Fabric community human-readable names such as `net.minecraft.server.MinecraftServer` and `tick` |

The legacy public namespace name `official` was removed. Requests that still send `official` now fail validation and should be updated to `obfuscated`.

On an unobfuscated runtime (`26.1+`), the runtime's names as shipped are Mojang names, so a namespace field that would report `obfuscated` reports `mojang` instead. A request that omits `mapping` or passes `mapping="obfuscated"` therefore reports `"mojang"`, exactly as `mapping="mojang"` does, and both read the same names. Other reported values are unchanged: an `intermediary` or `yarn` request reports `mojang` only where the resolver falls back to the runtime names, which happens when an artifact or class tool resolves a 26.1+ target; the lifecycle tools keep reporting an explicit `intermediary` or `yarn` as requested. An explicit `intermediary` or `yarn` sent with an already-resolved `artifactId` skips that resolution, and the fields differ by tool: `get-class-source` reports `mojang` in both `mappingApplied` and `returnedNamespace`; `get-class-members` reports `mojang` in `mappingApplied` but keeps the requested `intermediary` or `yarn` in `returnedNamespace` and `context.mappingNamespace`; each `batch-class-members` entry forwards the explicit `mapping` and so reports what `get-class-members` does. The rule covers:

- `mappingApplied` from `resolve-artifact`, `inspect-minecraft task="artifact"`, `get-class-source`, `get-class-members`, `search-class-source`, `get-artifact-file`, `list-artifact-files`, `index-artifact`, and the batch tools, including `target.kind="workspace"` on a 26.1+ project that declares no `mappings` line.
- `returnedNamespace` from the tools above that return it, including `inspect-minecraft task="class-overview"`, and `context.mappingNamespace` from `get-class-members`.
- `query.mapping` from `diff-class-signatures` when both versions are `26.1+`, `result.comparison.mapping` from `compare-minecraft task="class-diff"` when both versions are `26.1+` (the `comparison` block is returned at `detail: "standard"` or `"full"`, not at the default `summary`), and `query.mapping` from `trace-symbol-lifecycle` when every scanned version is `26.1+`. A comparison or scan that reaches a pre-26.1 version reports the requested mapping, as before.
- `mapping` in the `tasks["minecraft.artifact.resolved"]` entry of `validate-project`.
- `resolvedOwner.mapping` and `provenance.mappingNamespace` from `verify-mixin-target`, and `provenance.mappingApplied` from `validate-mixin`.
- `mappingApplied` in the artifact metadata read through the `mc://artifact/{artifactId}` resource; its other fields are returned as stored.

A runtime counts as 26.1+ for version targets, 26.1+ Minecraft runtime coordinates, and jar targets proven to be a 26.1+ Minecraft runtime jar (see [Lookup Rules](#lookup-rules)). Artifacts that an earlier release cached under the `obfuscated` label are reported the same way without a rebuild; the cache itself is not rewritten. Pre-26.1 versions keep `obfuscated`. A dependency artifact, Jar-in-Jar shell, or nested jar whose own version only looks like `26.x` is not a Minecraft runtime: it keeps `obfuscated`, together with the `dependency-mapping-unverified` quality flag where that applies.

`requestedMapping` is not relabelled and keeps its existing behavior: an omitted `mapping` reads as `obfuscated` (or the mapping inherited from the target artifact), and an `intermediary` or `yarn` request that the resolver falls back from on a 26.1+ runtime reads as `obfuscated`. For a request that omitted `mapping` or passed `obfuscated`, `requestedMapping: "obfuscated"` next to `mappingApplied: "mojang"` on a 26.1+ runtime is an identity, not a mapping fallback. Sending the reported `mojang` back as `mapping` reads the same names: `get-class-source`, `get-class-members`, `verify-mixin-target` (no namespace-mismatch error), and `validate-mixin` (no class lookup through the empty mapping graph, so no tool issue) behave as they do for `obfuscated`. `mapping: "obfuscated"` remains accepted as input.

Two surfaces keep reporting `obfuscated` on these runtimes:

- `manage-cache` metadata shows the label stored in the cache, which is also the label its `mapping` selector matches.
- `validate-access-widener` and `validate-access-transformer` report `provenance.mappingApplied` as the namespace of the jar the file was checked against (`obfuscated` for the vanilla client jar), next to the file header's namespace in `requestedMapping`.

The artifact's `provenance` carries `unobfuscatedRuntime: true` as the proof that its names are Mojang names; the field is absent for every other artifact. It is set for 26.1+ version targets, 26.1+ Minecraft runtime coordinates, and jar targets proven to be a 26.1+ Minecraft runtime jar, and it appears wherever the artifact provenance is returned: `resolve-artifact` `provenance` (omitted at its default `detail: "summary"`; pass `include: ["provenance"]` or `detail: "standard"` / `"full"`), `get-class-source` / `get-class-members` `provenance` (omitted at their default `detail: "standard"`; pass `include: ["provenance"]` or `detail: "full"`), and `sharedArtifactProvenance` on `batch-class-source`, `batch-class-members`, and `batch-symbol-exists`. A 26.1+ jar that an earlier release indexed without a version gains the version and the flag the next time `resolve-artifact` proves it; lookups by that `artifactId` then accept `mapping="mojang"` and report `mojang`. It is the same flag name as `mappingContext.unobfuscatedRuntime`.

### Lookup Rules

`find-mapping` supports lookup across `obfuscated`, `mojang`, `intermediary`, and `yarn`.

Symbol query inputs use `kind` plus `name` plus optional `owner` and `descriptor`:

- class: `kind="class"`, `name="a.b.C"` by default. `find-mapping` also accepts short obfuscated runtime ids such as `dhl` when `sourceMapping="obfuscated"`. For existence checks only, `nameMode="auto"` allows short names such as `Blocks`.
- field: `kind="field"`, `owner="a.b.C"`, `name="fieldName"`
- method: `kind="method"`, `owner="a.b.C"`, `name="methodName"`, `descriptor="(I)V"`

`mapping="mojang"` requires a source-backed artifact on legacy obfuscated versions. On unobfuscated releases such as `26.1+`, decompile-only/runtime paths are accepted directly for version targets, Minecraft runtime coordinates such as `net.minecraft:client:26.1`, and jar targets proven to be a 26.1+ Minecraft runtime jar.

A `target.kind="jar"` path counts as a 26.1+ Minecraft runtime jar only when the jar's own contents prove it: it has a top-level `version.json` whose `id` is an unobfuscated Minecraft version id such as `26.2`, `26.1-rc1`, or `26w14a`, it contains `net/minecraft/SharedConstants.class`, and it contains no `.java` sources. The file path is never used as evidence. Vanilla 26.x client jars and Loom's 26.x Minecraft jars carry all three. A proven jar reports that `id` as its `version`; a jar reached through a `target.kind="dependency"` target is never treated as a runtime jar. A jar that is not proven keeps the legacy rule: `mapping="mojang"` needs a source jar.

`resolve-artifact`, `get-class-members`, `trace-symbol-lifecycle`, and `diff-class-signatures` accept `obfuscated | mojang | intermediary | yarn` with these constraints:

- `intermediary` and `yarn` require a resolvable Minecraft version context such as `target.kind="version"` or a versioned Maven coordinate.
- For unobfuscated versions such as `26.1+`, including proven 26.1+ runtime jar targets, resolving a target with `intermediary` or `yarn` falls back to the runtime names with a warning, and the artifact and class tools report them as `mojang`. `trace-symbol-lifecycle` and `diff-class-signatures` do not fall back: they keep reporting the requested `intermediary` or `yarn` in `query.mapping`.
- On legacy obfuscated versions, `mojang` requires source-backed artifacts and decompile-only paths are rejected with `ERR_MAPPING_NOT_APPLIED`.
- On unobfuscated versions such as `26.1+`, both `obfuscated` and `mojang` are accepted for version targets, Minecraft runtime coordinates, and proven 26.1+ runtime jar targets; `mojang` uses the runtime/decompile path directly (`provenance.transformChain` includes `"mapping:mojang-runtime-unobfuscated"`) and skips Loom source-jar approximation.
- On unobfuscated versions such as `26.1+`, `obfuscated` and `mojang` name the same runtime names. With `mapping="mojang"`, `diff-class-signatures` (`compare-minecraft task="class-diff"`) and `trace-symbol-lifecycle` therefore use member names exactly as read from the runtime jar. They do not look them up in the empty mapping graph, so members are no longer reported with "Could not remap" or "Could not map" warnings.

When `trace-symbol-lifecycle` omits `descriptor`, the server resolves methods by owner and name and warns if overload ambiguity prevents a unique answer.

If callers accidentally append an inline signature suffix to `trace-symbol-lifecycle.symbol`, the server strips that suffix before splitting `Class.method`. Use the separate `descriptor` field when the workflow needs exact overload matching.

`trace-symbol-lifecycle` rejects class-like `symbol` inputs such as `net.minecraft.world.item.Item` with `ERR_INVALID_INPUT`. Pass `Class.method` and keep exact overload matching in the separate `descriptor` field.

`trace-symbol-lifecycle` evaluates per-version bytecode checks with bounded parallelism. If you only need a narrower historical window, still prefer explicit `fromVersion` / `toVersion` bounds to reduce work further.

`trace-symbol-lifecycle`, `check-symbol-exists`, and `find-mapping` skip intermediary/yarn Tiny graph loading when the request only needs Mojang/obfuscated names, so cold `mojang <-> obfuscated` lifecycle and existence lookups no longer pay the full named-namespace graph cost.

For decompile-only `ERR_MAPPING_NOT_APPLIED` failures, error details include `artifactOrigin`, `nextAction`, and `suggestedCall` so clients can recover without guessing. For a jar target that is not proven to be a 26.1+ runtime jar, a refused request that did not set `scope="vanilla"` gets a `nextAction` saying that `mapping=obfuscated` reads the jar's names as shipped (already Mojang names on Minecraft 26.1+) and that a vanilla Minecraft release is read through `target.kind="version"`; its `suggestedCall` retries the same jar with `mapping: "obfuscated"` and the request's `scope`. A refused `scope="vanilla"` request keeps the scope guidance instead: without a `projectPath`, `nextAction` says that `scope=vanilla` blocks Loom cache discovery and `suggestedCall` retries with `mapping: "obfuscated"` and `scope: "vanilla"`; with a `projectPath`, `suggestedCall` retries with `mapping: "mojang"` and `scope: "merged"`. The one exception is a `projectPath` whose `gradle.properties` names a 26.1+ Minecraft version: that merged retry would repeat the refused request, so a jar or coordinate target is retried with `mapping: "obfuscated"` and `scope: "vanilla"` (a jar with the as-shipped wording above).

If `find-class` or `get-class-source` returns no hit on an obfuscated legacy (1.x) Minecraft runtime artifact for names like `net.minecraft.world.item.Item`, the tool warns that `obfuscated` means Mojang's runtime names and recommends retrying with `mapping="mojang"` or translating via `find-mapping`. Neither tool issues that advice for dependency-resolved or Jar-in-Jar shell artifacts, whose native names are not evidence of Minecraft obfuscation, or for a 26.1+ Minecraft artifact, whose `obfuscated` names already are Mojang names. On a 26.1+ artifact, a `get-class-source` / `get-class-members` miss starts `nextAction` with the nearest `didYouMean` candidate (`Did you mean "<class>"?`) when the index has one, then points at `find-class`; when the artifact was resolved without a mapping or with `obfuscated` (reported as `mojang`, see [Namespace Definitions](#namespace-definitions)) and the caller did not pass a non-obfuscated `mapping`, it adds that retrying with a different mapping will not change the class names. A `find-class` miss on a 26.1+ artifact resolved that way warns with up to three near-miss class names and the same note.

Method descriptor precision is best on Tiny-backed paths (`intermediary` and `yarn`). For `obfuscated <-> mojang`, Mojang `client_mappings` do not carry JVM descriptors, so descriptor queries may fall back to name matching and emit a warning.

Use `symbol-map` with `exact: true` when candidate ranking is not enough and the workflow needs strict `owner + name + descriptor` certainty; with the 8.x tools, that is `resolve-method-mapping-exact`, a strict shortcut for `find-mapping` (kind=method, signatureMode=exact). Both additionally require a **complete** descriptor projection — they report `unavailable` (`resolve-method-mapping-exact`: `mapping_unavailable`) when the descriptor's class references cannot all be projected to the target namespace, whereas `signatureMode: "exact"` without `exact` (`find-mapping`'s exact mode) resolves those leniently. Prefer `signatureMode: "exact"` unless you specifically need that strict-completeness guarantee.

`resolve-method-mapping-exact` is **owner-strict**: the strict set is the candidates matching the query's full advertised triple `owner + name + descriptor`. The owner is compared after projecting it along the same mapping path the candidates travelled, so it is checked in the target namespace, not as a raw string. A same-signature method on a different class is therefore rejected rather than turned into an ambiguous verdict. The cost is that a method the owner INHERITS rather than declares now returns `not_found`: the mapping formats record declarations and carry no class hierarchy. That case is never silent — the result carries a warning naming the owner, the classes that do declare the member, and `find-mapping` as the owner-agnostic lookup.

`resolve-method-mapping-exact` reports the candidate set its verdict was computed FROM, on every status. `candidates` and `candidateCount` are the strict matches — never the wider name-matched list, which previously put a `confidence: 1, matchKind: "exact"` candidate the strict filter had already rejected next to an ambiguous verdict with nothing to distinguish it. On `status: "resolved"` that set is the single match, so `candidates` duplicates `resolvedSymbol` and the default response projection omits it, leaving `resolvedSymbol` and `candidateCount: 1`. Candidates the strict filter dropped are accounted for in `warnings` as counts BY REASON (how many by owner, how many by descriptor); use `find-mapping` when you want the unfiltered list. An ambiguous verdict also carries `ambiguityReasons[]`, the same field `find-mapping` populates. The tool never picks a winner: `status: "resolved"` means exactly one strict match existed.

`resolve-workspace-symbol` delegates its `kind: "method"` lookups to `resolve-method-mapping-exact` and spreads the result, so its method responses carry the same owner-strict semantics and the same `ambiguityReasons[]` on `status: "ambiguous"`. The field is present only on that status and always holds at least one reason, so it never serializes as an empty array.

`disambiguation.ownerHint` and `disambiguation.descriptorHint` narrow ambiguous candidate sets of the 8.x `find-mapping` only; `symbol-map` drops them (see its "From 8.x `find-mapping`" note for the inputs that narrow its candidates).

Use `symbol-map` with a `workspace` target and no `toMapping` (with the 8.x tools, `resolve-workspace-symbol`) when you need compile-visible names from actual Gradle Loom mappings in a workspace.

A Loom project for an unobfuscated version such as `26.1+` has no `mappings` line, because it compiles against the runtime (Mojang) names. When `build.gradle(.kts)` declares no mappings and the version is unobfuscated, `resolve-workspace-symbol` and `analyze-symbol task="workspace"` look the symbol up by name in the runtime jar's bytecode. They no longer return `mapping_unavailable` (`analyze-symbol` status `partial`). The response reports `workspaceDetection.resolved: true` and `mappingApplied: "mojang"` with empty `evidence`, and `mappingContext` reports `targetMapping: "mojang"` and `unobfuscatedRuntime: true`. A warning explains that no mappings declaration is needed. `sourceMapping` is echoed as requested, so the default `obfuscated` stays `obfuscated`. A class that is not in the Minecraft runtime jar, such as the library class `org.lwjgl.glfw.GLFW`, returns `not_found` with a warning that names the jar, and so does a member that the loaded class does not have. A method query named `<init>` is checked against the class's own constructors. `not_found` is reserved for those two answers: a lookup the runtime jar could not answer - a short (not fully qualified) class name, or a class that failed to load for any reason other than being absent - returns `mapping_unavailable` with a warning that gives the reason. `sourceMapping` `intermediary` or `yarn` returns `mapping_unavailable`, because those names do not exist on these versions. If the runtime jar cannot be resolved, the result also stays `mapping_unavailable`. The runtime lookup applies only when `projectPath` holds a readable `build.gradle(.kts)`: a missing, mistyped, or empty project directory keeps the `mapping_unavailable` result with the "No compile-time mapping declaration" warning. Projects that declare mappings, and legacy versions, keep the behavior described above.

## Environment Variables

Path-based overrides treat blank values and the literal strings `undefined` and `null` as unset, so accidental client serialization does not create `./undefined` or `./null` cache roots or broken JAR override paths.

`gradleUserHome` is a per-call path option, not an environment variable. It takes precedence over the MCP process `GRADLE_USER_HOME` for Loom source jars, Loom Tiny mappings, loader/runtime jars, and `validate-project` Loom cache probes. `projectPath` search roots still apply for workspace-local caches.

### Core and Repository Discovery

| Variable | Default | Description |
| --- | --- | --- |
| `MCP_CACHE_DIR` | `~/.cache/minecraft-modding-mcp` | Cache root for downloads and SQLite |
| `MCP_SQLITE_PATH` | `<cacheDir>/source-cache.db` | SQLite database path |
| `MCP_SQLITE_CACHE_KB` | `8000` | SQLite page-cache size in KiB (applied as a negative `cache_size` pragma) |
| `MCP_SQLITE_MMAP_SIZE` | `268435456` | SQLite `mmap_size` in bytes; `0` disables memory-mapped I/O |
| `MCP_SOURCE_REPOS` | Maven Central + Fabric + Forge + NeoForge | Comma-separated Maven repository URLs |
| `MCP_LOCAL_M2` | `~/.m2/repository` | Local Maven repository path |
| `MCP_ENABLE_INDEXED_SEARCH` | `true` | Enable indexed query path for `search-class-source` and `source-search` |
| `MCP_MAPPING_SOURCE_PRIORITY` | `loom-first` | Mapping source priority (`loom-first` or `maven-first`) |
| `MCP_VERSION_MANIFEST_URL` | Mojang manifest URL | Override the Minecraft version manifest endpoint |

Jars downloaded from the repositories in `MCP_SOURCE_REPOS` are cached under `MCP_CACHE_DIR` and identified by a sha256 of their bytes, so the same jar keeps one `artifactId` no matter which repository served it. (Minecraft version jars and mapping archives share that cache directory but sit outside this URL-keyed download-cache identity; a Minecraft version jar's own `artifactId` is covered by the jar rule below.) Jars served from the local stores — `MCP_LOCAL_M2` and the Gradle dependency cache — are identified from their bytes the same way whenever they are reached through a Maven coordinate (`target.kind="dependency"` and `target.kind="coordinate"`), so touching one, or restoring byte-identical contents, keeps its `artifactId`. A jar named directly by path (`target.kind="jar"`) is identified from its bytes as well, and so is a Minecraft runtime jar, because `target.kind="version"` and `target.kind="workspace"` both reach one through that same route. The digest is taken over whichever jar the id is actually about: the named jar's own bytes; or, when the named jar carries no Java sources and its same-name `-sources.jar` sibling supplies them, that sibling's bytes; or, when neither carries sources and the jar goes to the decompiler, the binary jar's bytes under a separate `decompile` identity. The jar's symlink-resolved path still enters the id beside the digest, so one file reached through two names is one artifact, while two byte-identical jars at two real paths stay two artifacts. One bound on "identified from its bytes": within a single server process the digest for a path is reused while that file's size, modification time, inode and inode-change time all still match, so on a filesystem that does not advance the inode-change time on a write, an in-place replacement of the same length whose modification time was restored can be answered from the earlier digest until that memo entry is evicted.

Whether a cached jar is re-checked depends on the coordinate's **version**, not on which repository serves it. A release version is served from cache with no request. A version ending in `-SNAPSHOT` is treated as mutable, as Maven defines it, and is re-checked against every configured repository — including the defaults: where the cached copy recorded an `ETag` or `Last-Modified` the check is a conditional request and an unchanged answer costs no transfer, otherwise the jar is transferred again. A republished jar replaces the cached one and yields a new `artifactId`. If the check cannot be completed — anything short of a definitive answer, including unreachable, a timeout, 5xx, 429, or an authentication failure — the cached copy is still served; if the repository answers definitively about the artifact itself (404 or 410 gone, 403 refused) it is treated as absent there and resolution moves on to the next repository. A definitive answer is also remembered for about five minutes, so a repeat resolve of the same target inside that window is answered from the record instead of asking that repository again. The record is bounded in every direction: only 403, 404 and 410 are eligible, so a timeout, a 5xx, a 429, an authentication failure and a network error are all retried on the next call; a `-SNAPSHOT` coordinate is never recorded; the records are held per cache directory; and they live in memory only, so restarting the server clears them and an artifact published after its rejection was recorded becomes reachable again as soon as the record expires. Note that `MCP_SOURCE_REPOS` replaces the default list rather than adding to it.

### Networking

| Variable | Default | Description |
| --- | --- | --- |
| `MCP_FETCH_TIMEOUT_MS` | `15000` | HTTP timeout in milliseconds. | `MCP_FETCH_RETRIES` | `2` | HTTP request retry count |

| `MCP_MAX_NESTED_JAR_ENTRY_BYTES` | `67108864` | Maximum uncompressed bytes one nested (Jar-in-Jar) entry may expand to during extraction. Checked against the entry's declared uncompressed size before the read starts and again against the bytes actually streamed, since a declared size can be wrong in either direction. A breach fails that one inner jar with `ERR_LIMIT_EXCEEDED`, naming the entry, its size and the limit; the shell jar's other inner jars still resolve. ## Architecture

| Component | Technology |
| --- | --- |
| Runtime | Node.js 22.13.0+ |
| Transport | stdio, MCP protocol revision `2026-07-28` plus the legacy initialize protocol (dual-era, see `## MCP Protocol Support`); newline framing standard, `Content-Length` as a local extension |
| Storage | SQLite for artifact metadata, source indexing, and cache bookkeeping |
| Decompilation | [Vineflower](https://github.com/Vineflower/vineflower) |
| Remapping | [tiny-remapper](https://github.com/FabricMC/tiny-remapper) |
| Mapping Sources | Mojang `client_mappings.txt`, Fabric Loom workspace metadata, Maven Tiny v2 |

The server runs as a long-lived stdio process. Artifacts, mappings, and generated metadata are downloaded on demand and cached locally.
